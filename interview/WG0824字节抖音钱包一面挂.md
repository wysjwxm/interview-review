## 一、问答实录

### Q1. 算法题:拆数字求最大乘积
- **面试官问**:开场直给一道算法题——「给你正整数 N,拆成 K 个数字,保持原顺序、不可重排,让乘积最大」,并给例子 N=1234、K=3 → 12×3×4=144,要求现场在代码界面写、能跑起来。写的过程中持续追问引导:「什么时候算结束?」「MaxK 又是个什么东西?」「你这个 K 一开始传 0 对不对?如果 K 传 1 还要拆吗?」——用提问点出候选人的初始参数错误,而非直接给答案。
- **候选人答**:提出回溯:递归传 K、每取一段减一,K=0 时判断数字用完则更新最大乘积。但初始参数传成 0、命名 MaxK 含义不明,输出不对,打日志调试超时,被面试官打断(思路对、边界两处错)。
- **评分与点评**:35/100 · 回溯方向对,但初始参数/边界错误、未跑通,超时被切断。

### Q2. 项目·系统切换
- **面试官问**:直接念简历原文追问——「你这里提到"设计实现安全可靠、可回滚、无业务中断的系统切换",这个具体指什么?」候选人答数据库切换后,面试官确认:「这个是指这个迁移是吧?」
- **候选人答**:直连支付做数据库切换(Oracle→国产),原系统定时任务扫状态驱动、响应慢,做数据迁移+业务迁移;考虑无中断、灰度、回滚。
- **评分与点评**:75/100 · 答出迁移背景与几维度,偏概念缺量化。

### Q3. 项目·交易保障(防丢/防重)
- **面试官问**:继续追简历——「你那个"交易保障",避免交易丢失或重复,涉及一些什么样的东西去保证呢?」
- **候选人答**:双方各选系统键值做幂等防重;发送侧状态控制——成功即更新、失败落中间态定时重扫重发;区分错误类型:业务失败/重复直接更新状态,非业务异常重试。
- **评分与点评**:85/100 · 幂等+状态机+定时重扫+错误分类,有实际细节。

### Q4. 项目难点
- **面试官问**:开放式——「你觉得在这个项目里面主要难点是什么?」
- **候选人答**:从零设计数据/业务迁移方案:尽量不中断、灰度验证、可回滚、动态数据迁移不可靠;团队没经验,搭方案是难点。
- **评分与点评**:72/100 · 维度对但停留在概念词。

### Q5. TDSQL 分布式 / vs MySQL
- **面试官问**:先问「你们数据库用的是什么?」,得到 Oracle→TDSQL 后连续追问压测:「它跟 MySQL 有什么区别?」「分布式数据库性能就更好吗?」「你说的分布式主要指什么的分布式?」「别的数据库不也是分布式吗?」「那分库分表的分布式是指哪里的分布式?」——连环追问把候选人逼到「不清楚」,最后补一句「不清楚也可以直接说,没关系的」。
- **候选人答**:选 TDSQL 是国产化+分布式、性能好;底层细节没了解,把存储节点分布式、高可用、分库分表混在一起,最后承认不清楚。
- **评分与点评**:45/100 · 只答出表层,被追问分布式含义答不上,概念混淆后放弃。

### Q6. MySQL 默认隔离级别 + RR/RC
- **面试官问**:八股直问——「MySQL 里面默认的隔离级别是哪一个?」候选人答后追问「这个跟可重复读主要的区别是什么?」
- **候选人答**:先说读已提交(受 Oracle 习惯),后更正为可重复读;区别:RR 同事务内多次查询一致,RC 做不到。
- **评分与点评**:60/100 · 一开始答错,更正后只到现象层。

### Q7. RC vs RR 性能 / MVCC
- **面试官问**:连续追问——「有没有工作场景需要可重复读?」(候选人反问切 TDSQL 用什么级别,面试官答 RC)「读已提交相比可重复读有什么优点?」「具体在哪一块更高?」「有更多快照吗?读已提交其实只要一个快照就可以了」「什么样的查询会被什么样的操作阻塞?」最后点破「我觉得你是猜测是吧?——对的」。
- **候选人答**:RC 性能高、锁少;MVCC 猜"RC 保存更多快照"被纠正,转猜"RR 查询被并发阻塞",承认是猜测。
- **评分与点评**:40/100 · MVCC 快照理解错,连续靠猜被点破。

### Q8. 联合索引 ABC 场景
- **面试官问**:抛具体场景让判断——「表有联合索引(A,B,C),判断这些查询能否命中、命中哪些部分」,连续给出 `where B=1 and A=1` / `+ order by C` / `where B=1 and C=1` / `where C=1 and A=1 order by B` / `where B=1 and A>1` 等场景,并追问「C 在索引上有用吗还是完全没有用?」「A=1 and B>1 和 B=1 and A>1 对索引使用一样吗?」。
- **候选人答**:最左前缀、等值后范围、跳列失效大体对;但 order by 走索引、范围后字段、覆盖索引细节靠推理不确信,个别判断偏。
- **评分与点评**:70/100 · 最左前缀尚可,细节靠推理、不自信。

### Q9. 分布式锁 / 分布式事务
- **面试官问**:「你这边涉及过分布式事务,那分布式锁一般怎么实现?」「什么场景会用到分布式锁?」「如果消费的资源是 MySQL 数据,一定要用分布式锁吗,还是可以用别的方式?」
- **候选人答**:生产没用过分布式锁;场景是多实例同消费一资源;被引导后说可用 `for update` 或 CAS 实现。
- **评分与点评**:58/100 · 只有概念无实践,靠引导才补出方案。

### Q10. AI 项目(面试复盘项目)

## 二、面试缺点

1. **算法题未交付(决定性因素)**。回溯初始参数传 K=0、边界条件两处错,只靠打日志试错、未静态跑小样例,超时被切断。字节一面算法不通过权重极高。
2. **数据库原理不扎实、不确定就靠猜**。MySQL 默认隔离级别先说成读已提交(受 Oracle 习惯影响);MVCC 快照机制理解错,连续两次被面试官追问后承认「是猜测」,直到对方明说「不清楚也可以直接说」才坦诚。
3. **分布式概念混淆**。说不清 TDSQL「分布式」到底指什么,把「存储节点分布式」「高可用(多副本备份)」「分库分表(数据分片)」混为一谈,连续追问后放弃。
4. **分布式锁/事务只有概念、没有实践深度**。生产没用过分布式锁,场景与方案都靠面试官引导才补出(`for update`、CAS),缺乏自主组织的体系。
5. **项目难点答得空泛**。只讲「无中断、灰度、回滚、动态数据」几个词,没有落到具体做法。
6. **表达风范(集中)**:
   - 口头禅多:全程大量「呃 / 嗯 / 我想一下 / 我思考一下 / 我不太清楚」,句子零散、节奏拖沓。
   - 不确定时倾向「猜」而非坦诚说不会,被面试官两次点破「是猜测」;面试里猜答案比说不知道更伤。

## 三、下一步学习计划

> 由「可改进点 + 缺少的知识点 + 下一步建议」归并而成,按重要性排序(参考 `知识点统计.md` 频次与权重)。

1. **算法 · 回溯/DFS 与动态规划**(最高优先)—— 本场算法题未交付直接决定走向;暴露初始参数、边界条件、终止条件不稳。动作:专项练回溯/DFS/DP 模板到「不调试一次 AC」,现场先手跑小样例、限时 debug(≤3 分钟超时主动换思路或求助)、规范命名。
2. **MySQL InnoDB 原理 · MVCC / 隔离级别 / 锁 / 索引** —— 本场暴露最严重(MVCC 靠猜、隔离级别答错),且支付场景必考。动作:吃透 read view 生成时机(RC 每条语句新快照、RR 整个事务复用同一快照)、快照读 vs 当前读、脏读/不可重复读/幻读、行锁/间隙锁/next-key、最左前缀/覆盖索引/EXPLAIN;记牢 MySQL 默认 RR、Oracle 默认 RC。
3. **分布式基础 · 锁与事务 + 分布式数据库架构** —— 简历写了分布式事务,面试官必深挖;本场把分布式/高可用/分库分表混为一谈。动作:分清 高可用(副本/主从)≠ 分片(数据切分)≠ 分布式事务/锁;掌握 Redis SETNX/Redisson、DB `for update`、CAS、2PC/TCC/本地消息表/最终一致性;补 TDSQL 分片原理。
4. **国产数据库 · TDSQL 特性** —— 项目在用却答不出细节。动作:了解兼容性、分布式事务、强一致策略,能讲「为什么选它、和 MySQL 差在哪」。
5. **支付业务 · 幂等/对账/状态机与项目量化** —— 项目难点答得空泛。动作:把幂等、对账、防重、冲正/调账、状态机串成完整故事,补灰度比例、回滚时间、数据校验方式等量化指标。
6. **AI/Agent 工程应用(差异化加分)** —— 本场亮点,但缺量化与选型理由。动作:准备模型选型对比、转录准确率/建议采纳率等指标、迭代规划,把亮点讲成有含金量产出。
