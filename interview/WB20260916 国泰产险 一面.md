## 一、问答实录

### Q1. 简历上三个系统的区分与确认
- **面试官问**：开场由简历原句切入并**逐条核对**——「你这边提到了保障交易的时效性、安全性……下面那个是不是用了 TCC 分布式事务?还有个异步可靠性保障,涉及了业务隔离线程池,是吧?是这么做的对吧?」随后确认系统边界:「我看你写的是『直连支付系统重构』和『TDSQL 迁移』,这其实是一件事件对吧?」「你主要负责的是两个系统,一个是跨境支付清算系统,一个是跨境数字人民币报文系统,是吧?」
- **候选人答**：(直连支付重构和 TDSQL 迁移)是同一个系统,既做应用重构、数据库也从 Oracle 换成 TDSQL。负责的其实是三个系统——银企直连、跨境数字人民币、跨境支付清算。
- **评分与点评**：60/100 · 技术内容没错,但**开场就在自己的简历上卡住了**:面试官问「银企的是哪个?我没有看到银企」时,候选人回答「**我看一下简历上顺序啊,我怕给他搞混了**」。面试官手里拿的就是你的简历,你要低头去找顺序,等于承认自己没理顺。**这是本场第一个丢分点,而且是纯表达/准备问题,与技术无关。**

### Q2. 跨境支付清算系统职责与资金流转(共享屏幕画图)
- **面试官问**：要求先讲系统职责与个人分工,候选人提出画图后,**面试官全程参与画图并多次纠正画法**——「你要不业务系统画个三角形?——不对,就是画成三角形的形状」「报文(平台)和(业务系统)之间应该是两条线」「那个报文系统(是)隔在业务系统中间?」
- **候选人答**：系统别名「代理行」,上游/下游都是报文平台(往外发报时是下游、收报时是上游),自己隔在报文平台与业务系统中间。资金流:用户发起 → 业务系统收集业务信息、扣款到自家过渡户 → 记到代理行 → 代理行记到招行内部的花旗影子户 → 组装报文给报文平台外发。往内方向:报文平台登记后给代理行 → 解析 XML 成 Java 对象 → 按业务要素判断下游是对公/零售/同业 → 清分给下游做最终支付。
- **评分与点评**：65/100 · **内容其实是清楚的**——代理行角色、影子户、清分下游这条链路讲对了,「我们是中间一过(手)」这句概括也很准。扣分在**表达**:画图时大量半截话(「我写个」「然后我们的下游给它称之为」),面试官不得不反复纠正画法;这段讲述占了很长篇幅,期间面试官多次尝试收敛节奏。

### Q3. 追问:为什么一笔交易要调账户中心两次
- **面试官问**：**本场最有含金量的追问**,而且面试官明确表示自己不理解这个设计——「我不知道你清不清楚,中心对于这两笔扣款他是怎么处理的?因为我理解这其实是一笔交易,(难道是)你们有分别的两个字段?**我不太理解这里的设计,为什么它要调两次?**」
- **候选人答**：出于**资金安全**考虑——这样能清晰看到资金流向:用户的钱只能流向业务系统,代理行的钱只能通过业务系统流过来,外部银行的钱只能通过代理行流过去,**是单向流转的,也更方便审计**。并且点明:**中间这些都是过渡户,业务做完后理应归零**,只是在过程中短暂增减。
- **评分与点评**：85/100 · **本场最佳。** 面试官是带着「我不理解这个设计」的疑问来的,候选人给出了一个**关于账户隔离与可审计性的设计动机**,而且主动补充了「过渡户理应归零」这个可以用于对账/校验的推论——这是超出提问范围的加分点。**这道题证明了候选人在业务设计层面是有思考的,不只是执行需求。**

### Q4. TCC 分布式事务记账的设计
- **面试官问**：从简历原句切入——「你这边写了 Try-Confirm-Cancel。可以先解释一下为什么要这么设计——比如你的异常,或者说你的取消,都是应对什么样的业务场景?」候选人答到一半,**面试官提示精简**:「可以(精简一点),要不然的话我们(时间不太够)」。
- **候选人答**：
  - **拆分动机**:记账在下游记账系统,不在自己系统内,**无法用一个本地事务保证「记账 + 业务状态」两边都成功或都失败** → 引入 TCC。
  - **Try 阶段**:账务中台把「现有余额 100 → 0,冻结金额 0 → 100」,即冻结资金;我方同步更新业务状态。
  - **Confirm/Cancel**:二阶段由**我方主动发起**(不是下游回调),Confirm 真正扣减冻结金额转入内部户,Cancel 把冻结的 100 还回去。
  - **异常补偿(重点)**:Try 失败 → 整体回滚,重试即可;Try 成功但 **Confirm 报文丢失** → 写 TCC 事务表声明该笔应成功/应失败,下游迟迟收不到二阶段报文时**回查我方异常表**判断状态并补偿;另有**旁路 Kafka** 双发 Try/Confirm 报文供账务中台消费,但**最终仍以 TCC 事务表的状态为准**。
- **评分与点评**：78/100 · **含金量最高的一题**,答出了 TCC 的三个关键要素:补偿事务表、二阶段驱动方向、旁路消息的定位顺序(「最终取决于事务表状态」这句尤其对,说明理解幂等与状态机才是终审)。扣分在**表达**:讲述冗长,需要面试官中途喊停;另外「Try 成功但 Confirm 丢包」这个最核心的异常场景,**在被追问前没有主动作为重点讲出来**。

### Q5. 异步任务调度框架:定时 vs 异步
- **面试官问**：先确认归属——「你实现了一个『定时任务轻量调度』……**我想确认一下,这(个)是你们自己手(写)的一个框架?**」随后确认机制:「我理解你应该是有一张(表)对吧,经常去拉起来重试?」并**先问复用性**:「你只是在一个场景下用,还是你做了一个简单的框架,多种场景我都可以复用这个重试机制?」最后**复述确认自己的理解**:「等于说你是把一件很常用的事情拆分在很多个阶段,每个阶段有个定时任务,然后分配一个线程池专门处理这一种定时任务,每个任务只负责一个小小的事情,做完以后把业务数据推进到下一个阶段?」
- **候选人答**：收到报文先实时入库落库 → 立即向报文平台响应成功 → 后续业务走异步。**不需要单独的重试表,业务表上就带状态机**(初始化 / 解析中 / 解析完成),兜底任务扫「处理中且维护时间超过 5 分钟」的异常记录;有重试次数阈值,超 5 次改为异常状态并告警。每个处理流程有独立线程池(报文解析一个、清分判断一个)。**并纠正了面试官的表述**:「它其实不是靠定时任务,它是直接异步;兜底才是通过定时任务。」
- **评分与点评**：78/100 · **答得好,而且敢于纠正面试官的理解**——「不是靠定时任务,异步是主路径、定时只做兜底」这个纠正很关键,说明对自己设计的边界是清楚的。丢分点在**:「是框架还是单场景」这个复用性问题没有正面回答**,只答了「不同流程有不同线程池」,没有说清这套调度逻辑本身是否抽象可复用。

### Q6. 异构数据迁移的背景与表结构变更
- **面试官问**：先问背景,并**追问一个很实在的点**:「为什么你们会去做迁移数据?因为这是一个很重(的事情)」;随后问——「**为什么会动表结构?我理解一般迁移你不会再去动表结构,为什么还要?**」
- **候选人答**：背景是**国产化改造**——金融基础设施要去除外购系统依赖,Oracle 换腾讯开源的 TDSQL(带分布式能力)。动表结构的原因有三:① **Oracle 表索引加得太多**(七八个),借机重构;② **Oracle 不强制要求主键,而 TDSQL 强制要求有主键**,必须补上;③ 去掉历史冗余字段、还原语义。
- **评分与点评**：75/100 · 三条原因都具体、可验证,「TDSQL 强制主键」这条尤其真实(与简历上「TDSQL 强制主键、字段类型差异」呼应)。扣分在**背景讲述偏薄**:「国产化改造」是信创政策背景,可以一句话点明(去 IOE / 信创),但候选人说成了「可能是国家的一个推进」,显得自己也不确定。

### Q7. 灰度迁移方案:白名单引流 + 原文表回放
- **面试官问**：**顺着简历逐层追下去**——从「整个迁移的方案是什么」开始,候选人讲完白名单后追问「那这个重试、整个调度是谁(做的)?哪个系统的?」,再追问白名单配置的位置:「那个白名单是谁(配的)、这个逻辑(在哪)?」
- **候选人答**：借迁移契机做了应用重构,A(连 Oracle)与 B(连 TDSQL)并存。B 先在测试环境充分测试 → 上线生产但**零流量** → **A 应用加白名单表**,按企业或金额区间等业务要素配置,命中则转发到 B。**加原文表**:转发给 B 的请求原文都存下来,B 处理不下去时把原文**回插到 A 的业务表重新走全流程**。白名单判断逻辑放在 A 应用内。并坦白回插目前是**人工触发**,「想更进一步可以做定时监控 + 自动回插」。
- **评分与点评**：80/100 · **简历亮点兑现得不错**——白名单引流 + 原文表回放 + 灰度逐步放大 + 最后存量数据补迁,这条链路完整,而且主动坦白了「回插目前是人工」这个短板(诚实加分)。可以更强的说法是**把这个方案抽象成通用模式**:双写 / 影子流量 / 可回滚切流 / 补偿回放,面试官在 Q8 一直在往这个方向引导。

### Q8. 切换异常场景与上线前的验证措施
- **面试官问**：**先构造异常**:「有没有考虑过,比如一笔业务你切到 B 了,B 处理了一半处理不下去了?」候选人答完后又**层层逼近一个更难的问题**:「你这个方案其实(起)动算是从配置白名单开始。**那在配置白名单之前,你有没有一些别的措施**……因为我理解银行的业务逻辑会比较严谨,这个东西涉及到金钱,那我理论上放上去之前肯定要做一个充分的、生产环境的验证?」并在候选人答「多轮测试」后**明确不满足**:「但是测试环境始终是测试环境……一旦白名单开启就是真实的业务数据跑到 B 系统去撞了,会真实影响到钱。那有没有一些别的想法?」
- **候选人答**：
  - **已发下游的处理**:如果 B 已经发到下游去了,不能回放,只能**通过一笔反向业务对冲**掉这笔。
  - **未发出的处理**:如果还停留在内部系统,让 A 回放走全流程。
  - **上线前验证**:先答「多轮测试」,被追问后提出「**空跑核对**」——全部业务都走 A,但让 B 也跑一遍,**先切断 B 与下游业务系统的联系**,既能验证又不产生真实影响。并补充「(我们)之所以选白名单方案,可能是因为这个系统业务量少、也充分验证了;别的系统做迁移是有做空跑的」。
- **评分与点评**：72/100 · **「空跑核对」是个好答案**(即影子流量 / shadow traffic),而且候选人知道别的系统这么做过。但**它是被追问两轮后才蹦出来的**,第一反应只是「多轮测试」——在涉及资金的场景下,「测试环境测过了」不足以让面试官放心。**这类问题的正确起手式应该是先讲验证手段(空跑/影子流量/双跑比对/小流量灰度),再讲测试。**

### Q9. B 系统的 update 请求,但数据还在 A 系统
- **面试官问**：**从存续数据迁移切入,构造了一个跨系统的数据不一致场景**——「老数据在 A 系统,因为进了白名单,请求要发到 B 去了,但这条数据我其实是做一个 update,而 B 系统里面又没有这条数据,有没有这样的?」并补充前提:「我理解你所有存量数据是在最后切完 B 以后才做(迁移)」。候选人答完后**继续质疑方案选择**:「我新增协议也是新增数据,为什么不能通过你刚刚那个 A 转到 B 那个方案,而是要通过页面上同时往两个 A、B 应用发两个请求?」
- **候选人答**：确实有这种情况,典型的是「**协议**」数据——企业签约信息两边都维护;新增协议走柜员前端页面,**同时往 A、B 两边发请求**。被质疑为什么不用同步方案时答:「**它有点更类似于是配置,而不是业务,应该两边都是全量**」。企业新增量少,所以暂未遇到同步期间新业务插入的冲突。
- **评分与点评**：70/100 · 承认问题存在、给出实际处理方式,是诚实的。但**「配置 vs 业务」这个理由不够硬**——面试官问的是技术方案选择,候选人给的是概念区分;更好的回答应该落到**数据特征**上(配置类数据量小、变更频率低、允许双写并人工兜底,所以用双写比走异步同步链路更简单可靠)。**这题暴露了「给理由时容易滑向概念而非工程依据」。**

### Q10. 你自发解决的业务痛点(报文解析配置化)
- **面试官问**：**开放式发问**,给了一次主动展示的机会——「你负责了两年的开发,有没有什么东西是由你发起的、去解决一些业务的痛点,或者是一些自发发现的内容?」随后确认动机:「你是发现这个 XML 经常变化,然后你不想做这个东西?」
- **候选人答**：**痛点**:原方案在 Java 代码里写一大串 dom4j + XML 路径 + Java 属性的硬编码,报文标准一升级、字段一变更就要改代码。**方案**:把解析规则**配到数据库**,应用启动时加载,规则里含「XML 路径 → Java 对象属性」「节点类型(嵌套/叶子/重复)」,解析时**用类 DFS 的方式从 root 节点递归展开**。**配套工具**:还写了一个 **Python 脚本,把报文规范整理的 Excel 表格直接生成 .sql**,导入数据库。
- **评分与点评**：72/100 · **内容含金量高**——配置化解析 + DFS 递归 + Python 生成 SQL 这段工具链,是「自驱解决痛点」的扎实证据,`Python(自动化脚本)` 也在简历技能里。失分在**讲述方式**:开口是「我觉得有,有一个解析报文的,我跟你讲一下」,然后从「XML 报文有很多个节点」讲起,**讲了很久才说到痛点和收益**;而且最后没把「**报文标准升级只需改数据库配置、无需发版**」这个最有说服力的结论点出来。

### Q11. Kafka 消费模型与选型对比
- **面试官问**：从简历的 Kafka 条目切入,先要基础——「介绍一下,Kafka 正常的一个消费(模型)」「它跟其他的,比如说 RabbitMQ 和 RocketMQ,它的区(别是什么)?」再问使用深度:「你们是一个消费组还是多个?有没有多消费组的场景?」
- **候选人答**：「**这个我不太清楚。**但我知道 RocketMQ,它可能是更重量级一点,有事务消息这一个概念,Kafka 可能没有。其他的队列没有太(了解)。」消费组方面:「其实我们用到的也不多,(多)消费组也不多。」
- **评分与点评**：40/100 · **本场第一处硬伤。** 候选人简历「专业技能」里写了「消息中间件:Kafka(旁路报文、异步解耦)」,而 Q4 里也确实讲了用 Kafka 做旁路补偿——**说明他是在用 Kafka 的,但只停留在「会用 API」的层面**。而且「Kafka 没有事务消息」这个说法**不准确**(Kafka 有事务,提供 exactly-once 语义,只是机制与 RocketMQ 不同)。用「用得不多」收尾,等于放弃了这道题。

### Q12. HashMap 底层数据结构

### Q13. Spring Bean 生命周期
- **面试官问**：「那 Spring 这块的一个 Bean 的生命周期,可以简单(讲一下)。」

### Q14. 乐观锁的实现
- **面试官问**：「你可以举一个乐观锁的实现嘛?比如你去实现一个简单的乐观锁,你会怎么实现?实现一个悲观锁,你会(怎么实现)?」
- **候选人答**：乐观锁——数据库一条记录状态为 A(初始),两个线程并发处理时,通过与状态机配合的**条件更新(只能从 A 改成 P)**,改成功的那个继续往下处理。悲观锁——`select for update` 锁住这条记录。
- **评分与点评**：70/100 · 方向对、例子也贴合自己项目(与 Q5 的状态机一致)。但**没有说出乐观锁的标准实现**:`version` 版本号字段 + `UPDATE ... SET x=?, version=version+1 WHERE id=? AND version=?`,判断影响行数。候选人用的是**状态机 CAS**,是乐观锁的一种特例,但被明确问「怎么实现」时,应该给出通用形式再补自己的变体。

### Q15. 分库路由:一致性哈希/取模/强制路由
- **面试官问**：从简历原句切入——「你这边提到了一个分库路由的设计——一致性哈希、(取)模,还有强制路由多策略,这个可以帮我解释一下。」
- **候选人答**：报文层(报文前置)是第一个收到报文的,下游有 01 分库、02 分库、99 库(99 库专用于灰度)。**默认路由**:按报文编号哈希取模决定分库。**强制路由**:带灰度标识的强制路由到灰度库。**跟随哈希**:退款报文带上原支付报文的**原报 ID** 做哈希,保证关联报文落到同一个分库。**多因子 + 路由表**:按「报文类型 / 原报 ID / 灰度标识」多因子匹配,规则配在路由表中,**按顺序匹配,匹配不到走默认策略**。
- **评分与点评**：80/100 · **本场第二好的回答。** 四种路由策略都讲清了,尤其「**跟随哈希**」用了具体例子(退款跟随原支付),这说明是真的理解设计意图而不只是背名词;「规则表顺序匹配 + 默认兜底」也说出了策略链的形态。**唯一遗憾**:没讲「**为什么需要一致性哈希而不是简单取模**」(扩容/缩容时的一致性哈希能最小化数据迁移量)——面试官点名问了这个词,大概率在等这个。

### Q16. 高流量场景下的数据库迁移方案
- **面试官问**：**把 Q7 的场景升级难度**——「假设我们现在是一个高流量的场景,你要去做一个这样的数据库迁移,那你的方案(是什么)?」候选人反问「什么是高流量」后,**面试官把条件说死**:「很大,就是无时无刻(都在写)它的数据」,并在候选人答「存量迁移没影响」时**补上关键约束**:「(但是)数据还会发生改变,它的一个业务场景,它会有(更新)。」
- **候选人答**：存量迁移不受影响;若表**没有异构**,可用数据库迁移组件**监听数据库日志**在两边做同步;若**异构**,先看异构程度——轻度转换组件可能支持,但如果需要生成新的组件 ID 之类就用不了。**想了很久**(转录里有明显的「那我想想看……有两个系统……我想到一种」),最后给出:用 **Kafka 做异步双写**,A 接到新请求后丢 Kafka,B 消费。
- **评分与点评**：62/100 · 「监听数据库日志」= CDC,方向对;「异构程度决定工具可用性」也是真实工程判断。但**整体是现场硬想出来的**,中间出现明显的长时间停顿。**这是候选人的强项领域(简历上有完整迁移经验),却没能在熟悉的题上快速组织出结构**——应该先分层作答:**存量(游标分批 + 断点续传)→ 增量(CDC/binlog 追平)→ 双写过渡 → 校验比对 → 切读 → 切写 → 回滚窗口**。

### Q17. 切换瞬间的时序竞争场景
- **面试官问**：**本场难度最高、也最具体的一题**,而且面试官**反复重述了三遍**同一场景,说明他非常在意候选人能不能听懂——「假设有一个插入(和)更新,对同一条数据的操作……A 服务已经处理了这个插入的操作,在这个瞬间,我也同时发了个消息去 Kafka,并且 B 也能消费了。但在这个瞬间我做了个切换。然后 B 这时候**新的 update 的请求来到了 B**,然后 B 去做 update 的时候**失败了,因为它还没有消费到前面那条 insert 的数据**。有没有一些方(法)?」
- **候选人答**：第一反应「你是说对于 B 来说,update 先到、然后 insert 的后到?」(理解基本正确)→ 答「那就是这个 Kafka 的顺序消费的(问题)」(**方向偏了**:问题不在 Kafka 内部顺序,而在两条链路——Kafka 异步 vs HTTP 同步——之间的**跨通道时序竞争**)→ 面试官重述后,候选人说「**update 它是通过 Kafka 到的,但是 insert 它是不(是)——update 通过 HTTP 到的,insert 它通过(Kafka)……**」——**把两者说反了**。面试官追问「你说什么?」后,该题中断,面试官以「时间不多了」转向下一话题。
- **评分与点评**：30/100 · **本场最严重的失分,也是收尾最大的一次机会流失。** 面试官构造的其实是一个经典的**双写通道竞态**:增量同步(异步)与业务写入(同步)走不同通道,切换窗口内 B 可能先收到 update 后收到 insert。**正确方向应该是**:① 识别这是跨通道时序问题,不是 Kafka 顺序问题;② 给出兜底思路——**切换前先追平并暂停同步链路、加版本号/时间戳拒绝乱序写入、按业务主键做串行化路由(同一笔数据的消息发到同一分区)、或对 B 的 update 失败做暂存与重放**。候选人不但在结论上说反了方向,连基本事实描述都出错,**面试官重复三遍仍未对齐,最后只能放弃该题**。

## 二、面试缺点

1. **开场就暴露对自己简历不熟(纯准备问题)** —— Q1 面试官问「银企的是哪个?我没有看到银企」,候选人的回答是「**我看一下简历上顺序啊,我怕给他搞混了**」。面试官正在拿着简历核对,候选人却要低头去查顺序——**这是零技术含量的丢分**,而且发生在面试的第 3 分钟,直接影响第一印象。

2. **表达冗长,被面试官反复打断要求精简** —— 全场面試官至少 5 次收敛节奏:「可以(精简一点),要不然的话我们(时间不太够)」(Q4)、「了解,可以简单点」(Q5)、「稍微轻(一点)」(Q15)、「可以简单点就是我,我还 OK 的」(Q10)。画图环节的「半截话」尤其多(「我写个」「然后我们的下游给它称之为」),需要面试官反复纠正画法。**这与信也科技那场暴露的是同一个问题:项目讲述缺少骨架,容易陷进细节里出不来。**

3. **基础八股连续三题失守,且失守的是简历明写的技术栈** —— Q11 Kafka(40)「我不太清楚」、Q13 Spring Bean 生命周期(30)「这个也不太行」、Q12 HashMap(60)表述含糊。**这三样全部写在简历「专业技能」里**(「Java、Spring Boot、微服务、MyBatis」「消息中间件:Kafka」),连续失守会让面试官怀疑简历的真实性,而不只是「这块没复习」。

4. **收尾的场景题完全没听懂,面试官重述三遍仍未对齐** —— Q17,D为双写通道竞态场景。候选人先答「Kafka 顺序消费」(方向偏),再在面试官重述后**把两条链路的走向说反**(「update 通过 HTTP、insert 通过 Kafka」——实际场景正好相反)。面试官追问「你说什么?」后只能以「时间不多了」收尾。**丢分不在不会答,而在没能准确复述面试官给的场景——这是沟通准确性问题,比知识盲区更伤。**

5. **涉及资金安全的验证问题,第一反应是「测过了」** —— Q8 面试官明确说「测试环境始终是测试环境」「会真实影响到钱」,候选人第一反应仍是「我们肯定有多轮的测试」,被追第二轮才提出「空跑核对」。**在金融场景下,「测试过了」不是有说服力的保证**,应该先讲验证手段(空跑/影子流量/双跑比对)。

6. **给理由时容易滑向概念而非工程依据** —— Q9 被问「新增协议为什么不用 A→B 同步方案」,候选人答「它有点更类似于是配置,而不是业务」。这是概念区分,不是技术论证。**更好的答法是落到数据特征**(配置类数据量小、变更频率低,双写成本低于维护一条同步链路)。

7. **自建的 AI Agent 工具两次机会都没讲出来(跨场次重复问题)** —— Q18 面试官**点名问「你写这个 skill 是用来做什么」**,候选人回了「用来做面试复盘」六个字;B 反问环节面试官又详细介绍了他们的 Harness 平台与 Agent 托管形态。**两次机会都放掉了。** 这与上一场(通联数据 Q15)是**完全相同的失误**——上一场面试官也主动讲了 Agent 产品 / harness 架构。

8. **同一道 HashMap 题,两场分数从 80 掉到 60** —— 通联数据一面 Q1 就是 HashMap 底层,当时答出「哈希表 + 链表 + 红黑树」加转树动机拿了 80;本场再考,只剩「挂上一个链表/红黑树」这种含糊表述,没有任何展开。**说明上一场的复盘结论(「漏掉具体阈值与复杂度量化表达」)没有转化成可复述的答案**,复盘到改进之间断了链。

9. **口头语与自我打断密集** —— 「呃」「就是就是」「比如说」大量出现;「我跟你讲一下」(Q10)、「我看一下能不能(换一张纸)」(Q4)这类过程性话语占了不少篇幅,挤占了有效叙述时间。

## 三、下一步学习计划

> 排序依据:本场暴露严重度(答错 > 靠猜 > 遗漏)优先,并参考 `知识点统计.csv` 累计频次与 `weight=0.4` 权重。

### 1. Spring 核心机制(Bean 生命周期)—— 本场直接放弃,且是必考题
- **暴露情况**:Q13 面试官问「Bean 的生命周期,可以简单讲一下」,回答是「这个也不太行(,不太清楚)」。
- **为什么重要**:简历写明「Java、Spring Boot、微服务」,项目全在 Spring 体系内。这题答不上,面试官会怀疑技术栈真实性。**几乎每场 Java 面试都会以某种形式出现。**
- **具体动作**:
  - 背熟完整链路:**实例化 → 属性注入(@Autowired)→ Aware 回调(BeanNameAware / BeanFactoryAware / ApplicationContextAware)→ BeanPostProcessor#postProcessBeforeInitialization → 初始化(@PostConstruct → InitializingBean#afterPropertiesSet → init-method)→ BeanPostProcessor#postProcessAfterInitialization(AOP 代理在这里生成)→ 使用 → 销毁(@PreDestroy → DisposableBean#destroy → destroy-method)**。
  - 顺着这条链补三个高频追问:**循环依赖三级缓存怎么解、@Autowired 与 @Resource 的区别、AOP 代理在哪个阶段生效**。
  - 结合自己项目说一句「我们项目里用 @PostConstruct 做配置加载」——Q10 提到过「应用启动时把数据库规则拿下来」,**这正好是 @PostConstruct 的真实用例,把两题连起来答**。

### 2. Kafka 与消息中间件(本场 40 分,CSV 高频)
- **暴露情况**:Q11 直接答「我不太清楚」,且「Kafka 没有事务」的说法不准确。CSV 中「Kafka·消息可靠性」本场后累计 2 次。
- **为什么重要**:简历写了 Kafka,项目里(Kafka 旁路补偿)也确实用了——**有实践但讲不出原理,是最亏的一种状态**。
- **具体动作**:
  - 讲清 **消费组与分区的关系**(同组内一个分区只被一个消费者消费)、**offset 提交与重复消费**、**顺序性只在单分区内保证**、**Kafka 有事务**(提供 exactly-once,机制与 RocketMQ 的事务消息不同)。
  - 补一条与项目的连接:**Q4 里用 Kafka 做旁路补偿,为什么最终还要以 TCC 事务表状态为准?**——因为消息可能重复/丢失、Kafka 不保证全局有序,所以消息只能当触发器、状态表才是终审。**这个已经答对了,把它固化成可复述的话术。**
  - 对比表:RocketMQ(事务消息、延迟消息、顺序消息)、RabbitMQ(轻量、路由灵活、可靠性靠 ack)、Kafka(高吞吐、日志式、分区有序)。

### 3. 跨通道时序竞争与数据一致性(本场最严重失分)
- **暴露情况**:Q17 面试官重述三遍场景,候选人把链路走向说反,最终未能对齐。
- **为什么重要**:这是他**强项领域(数据迁移)的深水区**,面试官明显是想在这上面拉开区分度。「双写 / 灰度切换 / 增量同步」这套东西一旦问到时序,答不上就前功尽弃。
- **具体动作**:
  - 把这个场景**完整复述并写出解法**:异步通道(Kafka 增量同步)与同步通道(业务直接写入)并存时,切换窗口内可能出现**乱序**。解法:① 切换前**追平并暂停同步链路**(quiesce);② 按业务主键**路由到同一分区**保证单笔有序;③ 写入路径带 **版本号 / 时间戳**,拒绝旧版本覆盖;④ B 侧 update 失败时**暂存待重放**(与 Q7 的「原文表回插」同构);⑤ 切换前后做**数据比对校验**。
  - 刻意练习:**把面试官给的场景先复述一遍再回答**(「我确认一下,是 A 先处理 insert 并通过Kafka 发出,此时切到 B,B 直接收到 HTTP 的 update 但还没消费到 insert,对吗?」)——**听不懂先对齐,别急着答**,这是 Q17 最该改的动作。

### 4. 项目讲述的骨架化(跨场次重复问题,必须解决)
