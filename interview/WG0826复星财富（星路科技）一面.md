## 一、问答概要

面试按「软性 → 基础八股 → 项目深挖 → 反问」四段展开:

### 1. 软性环节(个人信息 / 薪资 / 求职动机 / 地点)
- **求职动机**:① 涨薪;② 现团队技术偏保守,想看技术更开放的公司。面试官委婉提示「涨薪」这点直接跟 HR 说不太合适。
- **地点/离职**:接受长沙;离职周期三周;终面需到现场(深圳/长沙可选);深圳 HC 紧、长沙概率大。

### 2. 基础八股环节(答得好坏参半)
- **答对**:二分 O(log₂N)、快排 O(N log N)、奇偶分离双指针 O(N)/O(1)、MySQL 索引 B+ 树。
- **答含糊/答错**:MySQL 默认隔离级别(「记不太清,好像是可重复读」)、可重复读幻读与间隙锁(「彻底解决」)、JVM 内存模型(漏本地方法栈、程序计数器理解偏差)。
- **完全答不上**:Java 虚拟线程、Redis、Kafka 高吞吐原理、Python GIL、HTTPS 加密握手。

### 3. 项目深挖环节(最出彩)
- **sql-convert skill**:Oracle→TDSQL 国产化的 SQL 语法转换,交给 AI 推进,讲得清楚。
- **数字人民币系统**:从央行专线接入 → HTTPS 卸载 → 报文处理 → 路由分库 → 报文解析组装 → 记账层 → 清分到业务系统 → 区块链对账,整条链路讲得非常完整清晰。
- **数据迁移**:双系统并行 + 灰度验证 + 回滚机制 + 断点续传 + 动态数据一致性,理解到位。
- **退款流程**:两次请求 + 异步通知 + 重试,讲得清楚。
- **分库设计**(唯一被追问卡壳处):被面试官连续追问「分库到底干嘛」「数据一样吗」「可用性到底怎么解决」,回答前后摇摆、一度没讲明白,最后才落到「重点是扩展性」。

### 4. 反问环节
- 用户量/请求量(新项目未上线,新财付日活约 10 万)。
- 公司 AI 使用情况(已全面推 AI coding)。

## 二、面试缺点

1. **八股基础不牢,多处答不上或答错**
   - 虚拟线程、Redis、Kafka 原理、GIL、HTTPS 握手完全空白;MySQL 默认隔离级别、JVM 内存模型答得不完整。

2. **「分库」问题被追问到卡壳,逻辑不自洽**
   - 先说「提高扩展性和可用性」,被面试官质疑「存的是不同数据,那怎么提高可用性?」后反复横跳,先是「可以做路由选择」,又改口「重点还是扩展性」,最后被引导到「不同报文路由到不同分库、分库之间无数据交互」才收尾。暴露了对「分库解决的是什么问题」想得不清楚,是把可用性(主从/多副本)和水平分库(扩展性)两个概念混在了一起。

3. **对概念理解停留在「听说过」层面,一追问就露怯**
   - 程序计数器说成「统计代码行/代码指针」,不准确;MySQL 可重复读回答「彻底解决幻读」,过于绝对(实际还有当前读等边界);虚拟线程只知道「Java 21 推出」却说不出是什么、解决什么问题。

4. **HTTP(S) 基础薄弱**
   - 问 HTTPS 建立过程,只答了 TCP 三次握手,把传输层和 TLS 加密握手完全混淆,暴露网络基础欠缺。

5. **求职动机表述略生硬**
   - 第一点直接说「涨薪」,被面试官善意提醒;虽然补了「技术保守想成长」,但节奏已经被动。

---

## 三、可改进点

1. **把「分库/分表/读写分离」彻底理清,写进一段 30 秒能说清的话**
   - 明确三者区别:水平分库(数据按路由键散列到不同实例,解决容量/扩展)、读写分离(主从副本,解决读性能与高可用)、分表(单库内拆表)。
   - 被问「为什么分库」时,直接给结论「主要解决单库容量与扩展性」,再补「可用性靠多副本/主从解决,分库本身不承担可用性」,避免混为一谈。

2. **基础八股系统补齐,避免「听说过但说不出」**
   - 每个概念按「定义 → 解决什么问题 → 关键机制/原理 → 局限」四段式准备,而不是只背一个名词。

3. **答不上的问题当场补救**
   - 虚拟线程、Redis、Kafka 这类可以诚实说「没用过/不熟」,但主动接一句「不过我知道它大致解决 XX 问题」,或把话题引回自己熟悉的方向(如「我们团队限制用 Redis,但我了解它的缓存击穿/雪崩场景」),避免冷场。

4. **求职动机先讲成长、后讲薪资**
   - 把「技术保守、想看更开放的技术栈、对成长有帮助」放第一位,薪资作为第二点带过,表述更成熟。

## 四、缺少的知识点

按暴露程度列出:

1. **JVM 内存模型 / 运行时数据区** —— 完整五块(堆、虚拟机栈、本地方法栈、方法区/元空间、程序计数器)没答全,程序计数器作用理解错误(记录当前线程执行字节码的行号,不是「统计代码行」)。
2. **Java 虚拟线程(Project Loom / Java 21)** —— 完全不了解:虚拟线程是用户态轻量级线程、解决 IO 密集场景下平台线程阻塞导致的吞吐上限问题。
3. **MySQL 事务隔离级别与 MVCC/锁** —— 默认隔离级别(可重复读)记不牢;可重复读通过 MVCC + 间隙锁解决幻读,但「彻底解决」的说法过于绝对(当前读/加锁读下仍可能幻读)。
4. **Redis** —— 完全没用过:常用数据结构、缓存击穿/穿透/雪崩、持久化、分布式锁、缓存一致性等均空白。
5. **Kafka 原理** —— 只会用不会讲:高吞吐靠顺序写、零拷贝、分区并行、批量/压缩、ISR 副本等机制。
6. **Python GIL** —— 不知道:全局解释器锁的由来、对多线程并发的限制、对 IO 密集 vs CPU 密集的影响。
7. **HTTPS / TLS 握手** —— 只记得 TCP 三次握手,把传输层与 TLS 层混淆;缺 TLS 1.2/1.3 握手流程、证书校验、非对称+对称加密结合。
8. **分库分表设计** —— 概念边界不清(分库 vs 分实例 vs 分 schema vs 主从),分库解决的到底是「容量/扩展性」还是「可用性」没想明白。

## 五、下一步建议学习的知识点

> 目标岗位是港股行情/交易系统的 B 端 Java 开发,优先级按「高频八股 + 岗位相关 + 简历会用到」排序。

**P0(最优先,基础八股高频必问)**
1. JVM 运行时数据区、对象创建过程、类加载、垃圾回收(标记-清除/复制/标记-整理、CMS/G1)。
2. MySQL:四种隔离级别 + MVCC + 间隙锁/临键锁 + 索引(聚簇/非聚簇、最左前缀、覆盖索引、回表)。
3. Java 并发:线程池参数与拒绝策略、synchronized 与 ReentrantLock、CAS、volatile、ThreadLocal、虚拟线程。

**P1(岗位与简历强相关,面试官已显露出关注点)**
4. 分库分表:分片键选择、路由、跨片查询、数据迁移与一致性(本次被追问,重点补)。
5. Redis:数据结构、缓存三大问题、持久化 RDB/AOF、分布式锁、缓存与 DB 一致性。
6. 消息队列:Kafka 架构、高吞吐与可靠性机制、消息不丢不重、顺序消费。
7. HTTPS/TLS:握手流程、证书链校验、加密算法组合(把「三次握手 vs TLS 握手」彻底分清)。

**P2(加分项,与候选人 AI 技能标签呼应)**
8. 分布式事务:结合简历里的「本地消息表 + 监听器 + Kafka 补发二阶段 Confirm」,把方案讲深、对比 Seata 等,面试官会顺着简历深挖。
9. DDD:领域划分、四层架构(接口层/应用层/领域层/基础设施层)、与三层架构的差异,能举例说明(简历里明确写了 DDD)。
10. Python GIL 等通用概念扫盲,避免「连 GIL 都不知道」的低级空白。

## 总结

这次面试**项目部分很能打**(数字人民币全链路、数据迁移、退款重试、AI skill 落地都讲得漂亮),短板集中在**八股基础和概念精确度**:JVM、MySQL 锁/隔离级别、Redis、Kafka、HTTPS、虚拟线程、GIL 一连串要么答错要么答不上,加上「分库」被追问到逻辑摇摆,把项目建立的优势抵消了不少。

下一步最该做的不是继续深挖项目,而是**把 P0 的 JVM + MySQL + 并发八股过一遍**,同时把「分库分表」这个刚被问卡壳的点单独吃透——这是本次最直接、最容易在二面被再次追问的缺口。
