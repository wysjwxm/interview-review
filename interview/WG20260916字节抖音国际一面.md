## 一、问答实录

### Q1. 团队定位:你处在跨境支付的哪一层
- **面试官问**：从自我介绍切入,连续追问定位——"你是属于交易的上游是吗?"→"那你这边会直接对接外部的渠道吗?"→"是做收单的是吧?"→"你这边是直接为企业提供服务的吗?"→"你直接面向用户是吗?还是说你上面还有一层是专门面向用户的?"→"不是承载说他通过你这个系统去发起交易的对吧?"最后替候选人总结:"那你这个其实是 SWIFT 的下游吧。"(面试官自己在做国际支付,用连续追问逼候选人把"我在链路哪一环"说清楚。)
- **候选人答**：2024 年 7 月毕业入职招银网络科技,银行基础设施团队,对接 SWIFT、数字人民币等外部金融基础设施;做收发报文、记账、对账,记银行间的过渡账,再把报文清分给下游业务系统;也做银企直连接收企业支付指令、发送账单。对"是不是收单"答"还不算收单";对"做的是哪一层"答"最上层是报文层,还有银行间记账入账这一层";承认 SWIFT 只是一个渠道,还有非常多的外部基础设施。
- **评分与点评**：68/100 · 事实都对,但**回答是被面试官一句句"挤"出来的**,自己始终没有一句"我在 X 环、上下游分别是 Y 和 Z"的定位句。面试官连问 6 轮才拼出全貌,最后不得不自己替候选人总结"你是 SWIFT 的下游"——这种"让面试官替你归纳"的体验,在开场就丢了印象分。

### Q2. 项目流程:数字人民币跨境平台架构与职责
- **面试官问**：给了一个很开放的入口——"介绍一下你做的这个项目,比如说你接收到了一个对外的支付报文,进来到出去的流程是怎样的?"随后沿链路逐节点追问:"你这边主要是做的报文这一层是吧?"→"报文的交易的主要元素你会存下来,然后你的核心的下游是什么?"→"你的下游主要是哪些系统?特别多?"→"那你们的职责就是记一下报文,然后转发给下游,然后记一下账单是吧?"→"对账就是基于你们生成的账单跟上游或下游生成的账单去对嘛?跟外部对手去对?"→"你们不会内部对账是吧?"
- **候选人答**：以数字人民币跨境平台为例。行内链路:支付专线 → 前置应用(解密解签、原文管理、HTTPS 卸载成 HTTP、分库分发) → 报文层(解析报文、拆交易要素入库、报文收发解析组装、时序控制回响应) → 记账层(记银行间过渡账,并对接反洗钱、流动性管控等监管系统) → 下游业务系统。辅助模块:对账应用(T+1 拉取报文层需对账信息,与外部数字人民币平台做区块链对账,不一致则推调账报文抹平)、参数管理、额度查询、人工处理界面。下游覆盖行内所有跨境项目(跨境电商、金融市场、国际结算);内部对账不在本平台,由专门的记账中台负责。
- **评分与点评**：78/100 · **本场答得最完整的一题**。能按链路分层讲清楚"前置层做技术活、报文层管报文、记账层记账"的职责切分,并主动补上对账 T+1 与人工兜底,说明对自己系统的边界是有整体认知的。扣分在:全程没有一句量化(日均笔数、报文量、超时率),也没讲清"这条链路上你个人负责改了什么",停留在"介绍系统"而非"介绍我的贡献"。

### Q3. 消费/退款交易流程与"是否动账"的边界
- **面试官问**：念简历原文发问——"这上面写到你做了 DDD 设计,然后有设计实现消费、汇款、退款,这个可以给你详细讲一下吗?你这边有涉及到退款或者消费退款的交易流程吗?"中途不断收窄:"你说你刚说的对手方是谁?"→"就是你直接跟他们对接的是吧?不是通过支付网络?"→"你们行内是有个专门的支付网络这一层吧?还是说就是我们这一层?"然后转向关键质疑:"我是想问一下,你这个是会直接对资金进行动账吗?还是你们只做……因为刚刚之前听你描述下来,你只是记了一个账,只存了一下交易的报文元素,基本上不参与整个交易的流程?"并明确批评提问方式:"就比如说给你一个 XML 结构、一个 XML 文档,它的业务含义是什么呢?……我想要了解的是它的业务含义是什么,是一批支付指令,还是一个什么?"最后要求举汇款的具象例子:"你这一层在这个场景下做了什么事情?"
- **候选人答**：第一期只做消费(境内钱包在境外消费),退款围绕消费搭建。消费分同步报文与异步报文两个阶段:同步报文做消费可行性校验,对方回同步响应后判断能否推进,再发异步记账请求。对手方是数字人民币支付网络中的境外参与机构,由本层决定往哪个境外基础设施发。动账边界:本层动的是银行间过渡账,客户账由下游业务系统/客户账应用处理;汇款的例子是"业务系统发起交易并划转客户账 → 本层记银行间账户划转 → 以支付网络可识别的请求发出 → 对手行解析后做内部账户划转,两边都完成则转账完成"。
- **评分与点评**：70/100 · 汇款的具象例子举得不错,客户账/银行间账的分层是清楚的,但**前面几轮反复在"是不是收单""动不动账""报文是什么"上打转**,候选人几次用"这个要看场景""XML/各种文件都有可能"这类技术细节去回应一个业务含义的问题,被面试官当面点破"报文这个概念太宽泛了"。面试官最终结论是"听你描述下来,不是很能了解清楚你具体是在做什么事情"——这不是没做,是没讲明白。

### Q4. DDD:领域划分依据与四层架构
- **面试官问**：先要拆分的**依据**——"你做领域拆分的依据是什么?""你怎么知道每个领域的职责没有重叠、没有模糊?它有没有耦合或者依赖?"再问**动机**——"那你为什么用 DDD 去做这个?"接着连抛三个 DDD 基础概念:"你的四层架构是哪四层架构?""你知道 DDD 里面的六边形模型是什么样的?""你知道 DDD 里面的战略设计和战术设计分别是干嘛的?"最后问落地:"你里面拆完这些领域之后,你是把拆到不同的服务里面,还是在一个服务里?""你要不讲一下你这个里面最核心的一个聚合是什么,然后它的职责是什么?"
- **候选人答**：按职责功能拆分;先做业务建模,拆出角色与行为,再拆成技术指令,以此定领域以解耦合。选 DDD 的理由是传统设计分业务/技术两层,DDD 领域划分更清晰,能把职责边界划开,并完成三层到四层架构的转变、降低层级耦合。四层架构答:请求接收层、服务层、领域层、基础设施层。六边形模型、战略设计/战术设计均答"没听过"。拆分结果:前置层、报文层、记账层各为一个微服务,另有对账层、参数层。关于"最核心的聚合",候选人答的是报文层的接收方向,列举消费/退款/调账/对账指令各自的领域对象与状态推进。
- **评分与点评**：62/100 · **本场最典型的"标签大于深度"**。简历把 DDD 和"高可用、多分库的系统设计与构建"并列成核心贡献,但两个 DDD 最基础的概念题(六边形架构、战略设计/战术设计)直接答"没听过",面试官立刻改口问"那你用 DDD 主要是用来干啥"——这是在给台阶下。更关键的是**被问"最核心的聚合是什么"时,候选人答的是"报文层接收方向管了哪些领域对象",完全没有回答"聚合"这个概念本身**(聚合根、不变性边界、事务一致性边界一个都没提)。四层架构倒是答对了。

### Q5. 微服务通信与 RPC 框架
- **面试官问**：紧接着拆服务的话题——"你这个拆完之后,你这些微服务之间通信是怎么建的?是用这种微服务调用的方式?"→"有接触过 RPC 吗?"→"你了解现在开源的、或者说市面上常用的 RPC 框架有哪些?"
- **候选人答**：通过远程调用通信;服务间调用走基础设施提供的框架。对 RPC 的理解停在"算不算是 IPC 的一种"的模糊类比;举了 Spring 里的 Feign 作为"HTTP 调用这种远程调用的一种组件",以及 RestTemplate 这类"封装远程调用的组件",自认"我了解的可能就这些了"。
- **评分与点评**：55/100 · RPC 是 Java 后端面试的高频基础题,候选人**连 Dubbo、gRPC 这两个最主流的框架名都没提**,Feign/RestTemplate 更像是在回忆框架名而非理解它们的定位差异(HTTP 客户端封装 vs RPC 框架 vs 服务治理)。更可惜的是介绍自己系统时明明说了"微服务通信",却没顺势讲出注册中心、负载均衡、序列化协议这些真正做过的人至少会碰到的东西。

### Q6. 分布式事务:TCC、本地消息表与协调者
- **面试官问**：从简历场景切入——"你们是在什么场景下用的?"随后**抓住简历原话里的矛盾连追七轮**:"你简历上写的是'采用本地消息表加监听器',这个不是这个场景是吧?"→"为什么又说是用 TCC 啊?"→要核心原理流程→"参与者只有记账中台是吧?事务协调者和参与者分别都是谁?"→"你为什么需要你这边去感知他那边的状态和失败状态?这个不是应该事务协调者去做的?"→"你这个协调的是有你们自己的框架,还是你自己本地实现的?"→"你自己本地有没有 try?"→"他们 try 完之后,你这个状态变更是等 confirm 成功之后才变更,还是怎么变更?"→"你这个时间会不会太长了?"→"到底是实时的重试,还是 T+1 的补偿对账?"→最后把简历原话整句念回来:"你采用这种本地消息表加监听器的方案,极大地改善了 TCC 事务造成资源占用问题。然后你刚刚认为这种方式就是一种 TCC 是吧?那这种方式为什么又改善了 TCC 造成的资源占用问题?"
- **候选人答**：场景是交易状态机从"待记账"流转到"记账"时调记账中台,因一致性要求高选用行内统一 TCC。核心原理打了二阶段:本地业务变更后发 try → 记账中台做资金校验与冻结(预留中间态,非真实扣减)→ 根据预留结果做 confirm(扣减)或 cancel(回滚),并有超时回查与重试。协调者/参与者:参与者是"本平台 + 记账中台",协调者"以 SDK 形式落在业务系统代码里",通过 Spring 事务管理机制实现,本地未自行实现 try/cancel/confirm 三接口。状态变更时机:**try 完就变更本地状态**,理由是"try 成功就一定成功,后面一定做 confirm 不可能 cancel";confirm 失败靠实时重试,超过次数上限后走 T+1 对账 + 人工兜底。关于资源占用的改善,答的是"通过 Kafka 重试消息推送,或由对方来做二阶段、对方查询 TCC 状态来决定二阶段处理,把原来一个比较长的 TCC 流程分开了"。
- **评分与点评**：58/100 · **本场最失分的一题,因为它是简历上最亮的一条**。二阶段流程本身背得没错(cancel 说成"恐怖/恐慌"是 ASR 误差,不扣分),但三处硬伤:①协调者/参与者的边界讲不清楚——被问"为什么需要你感知下游状态,这不是协调者该做的"时,只能反复用"协调者以 SDK 形式放在我们代码里"绕开,面试官其实是在追问**协调者状态的持久化与恢复**(SDK 宕机后谁来推进二阶段),候选人没接住;②"本地消息表记录 TCC 状态"和"Kafka 做补偿"这两件事在回答里始终是并列罗列,没能串成一条因果链,面试官最后不得不把简历原话整句念回来再问一遍,候选人给的"把长流程分开"依然不成立——**把一个二阶段拆成异步消息,减少的是同步资源占用与 RT,不是"资源占用",而且这套方案的本质是"本地事务 + 消息最终一致性 + TCC 语义借用",并不是教科书意义上的 TCC**;③"try 成功即改本地状态、认定必然成功"这个设计取舍,面试官的"时间会不会太长"其实是在质疑中间态的可见性问题,候选人只答了"一定能成功"的信心,没答**资金在中间态时对外可见的状态是什么**。

### Q7. XA 与 TCC 的差异
- **面试官问**："分布式事务除了这种方式,还有别的解决方案?"→"跟你这个 TCC 有啥区别?"→然后设了一个陷阱式追问:"XA 这种方式也是二阶段,那它为什么会比你的一致性要强?你这个 TCC 的一致性要不要强?"→"XA 的实现你了解吗?它怎么实现呢?"→"你是指深入到哪个层面呢?他这个机制是怎么实现起来、怎么搭建起来的?就是你这个 XA 的实现的基石是什么?"
- **候选人答**：知道有 XA,理解为"数据库暴露 XA 接口、由技术组件统一管理多个服务的数据库以做到较强原子性"。差异答:自己这套偏最终一致性、依赖后续补偿,XA 瞬时一致性强,但资源消耗多、网络通信与数据库交互次数更多、更慢。XA 实现层面承认"其实我没用过,只是有去了解过",追问到实现基石时答"数据库提供 XA 接口、XA 请求",被问及接口的实现逻辑时明确承认"确实可能不太熟悉,没有去深入挖掘"。
- **评分与点评**：45/100 · 唯一答对的是"XA 强一致、TCC 最终一致"这句结论,**但这句结论本身也不准确**(TCC 的定位恰恰也是最终一致性方案,只是通过预留资源把不一致窗口压得更小;真正的对立面是 2PC/3PC 的同步阻塞 vs TCC 的异步补偿)。被追问"也是二阶段为什么它一致性更强"时,候选人只是在复述"提交交给 XA 管理器",没说出 XA 的基石是 **X/Open DTP 模型 + 数据库层的 prepare/commit 两阶段提交 + 全局事务 ID 与事务日志的持久化恢复**。这一题面试官把"深入到哪个层面""实现基石"问了两遍,是在给足机会,候选人两次都答不出。

### Q8. 算法题(现场未解出)
- **面试官问**：流程一开始就说明"第三部分就是代码考核的部分,会做一个算法题"。出题后把题目呈现在屏幕上,等待一段时间后问:"怎么样,有思路吗?"在候选人表示想不出来后,继续等待并追问一次,最后说"OK,那你线下下来你可以看一下吧,因为这个是比较经典的一个。"
- **候选人答**：直接表示"不太有思路",尝试性的方向是"可能要把点和其他所有点的是否有交点的情况给找出来",随后承认"有点想不到",**全程未写出任何代码,也未与面试官讨论暴力解法或复杂度**。
- **评分与点评**：25/100 · 算法题是本次面试明列的考核环节,零输出是硬伤。比"不会做"更可惜的是**应对方式**:没有确认题目边界(输入规模、坐标范围、返回什么),没有先给出暴力解再谈优化(哪怕是 O(n²) 的两两比较),没有主动要提示或口述思路。面试官连问两次、又给了一次机会说"这个是比较经典的",候选人两次都停在"想不到"。

### Q9. 反问
- **候选人问**：①团队主要做什么业务,是不是收单;②工作中 AI 的使用率、扮演什么角色、参与度多少;③团队在跨境交易上属于扩张期还是已经比较成熟。
- **面试官答**：团队负责国际支付,覆盖国内、国际的交易与钱包,收钱、跨境(国内转国外/国外转国内)、本地业务都有。AI 已覆盖工作全流程:从业务提 BRD → 产品产 PRD → UI 出设计,技术方案与代码生成也会用 AI 辅助。团队处于上升期扩张阶段——海外很多国家支付基础设施薄弱,而 TikTok 电商、直播、游戏、音乐等产品都需要支付能力,应用场景与交易量都在增长,覆盖国家与渠道也越来越多。
- **评分与点评**：—(反问一般不评分)· 三个问题都算得体,AI 使用率这一问尤其契合字节当下的工程文化,聊到了实际工作方式。可改进的是**没有问任何与"我这次表现"相关的问题**(比如团队更看重算法还是工程深度、候选人能力的短板在哪),错失了一次给自己找补的机会。

## 二、面试缺点

1. **原理深度跟不上简历标签,是本场最致命的问题**。简历上"DDD(领域驱动设计)""分布式事务(TCC/最终一致性)""高可用、多分库的系统设计"是三个最重的标签,但 DDD 的六边形架构与战略/战术设计(Q4)答"没听过",XA 的实现基石(Q7)答"没有去深入挖掘",TCC 的协调者状态持久化(Q6)答不出。面试官的追问路径很清晰:先问概念 → 再问动机 → 再问边界 → 再问反例,候选人基本都在第二到第三层掉下去。**简历上写了的东西,必须能扛住三轮追问**。

2. **回答绕、不先给结论,导致面试官反复澄清基本事实**。Q1 面试官连问 6 轮"你做的是哪一层"才拼出全貌,最后自己替候选人总结"你是 SWIFT 的下游";Q3 面试官直接点破"报文这个概念太宽泛了""听你描述下来,不是很能了解清楚你具体是在做什么事情"。问题不在不知道,而在**习惯从过程和细节讲起,不从定位和结论讲起**。改进动作很具体:每个回答先用一句话给结论(如"我是 SWIFT 的下一跳,做银行间清结算记账层"),再展开细节。

3. **对"业务含义"和"技术实现"两个层次不敏感**。Q3 面试官明确说"我想要了解的是它的业务含义是什么,是一批支付指令,还是一个什么",候选人仍在答"XML 格式、放到 HTTPS 请求里往外发""不同场景可能是 XML 也可能是各种文件"。**面试官问业务语义时不要退回到技术格式**。

4. **被追问时容易自我否定、中断回答**。Q6 被指出简历矛盾后,回答里多次出现"差不多是这样吧""其实他把 try 和 confirm 都包在 SDK 里,我们没有去实现,我们不需要去实现"这类收缩性表述;Q7 直接说"这个接口有点烂了,确实不太熟悉"。承认不会本身没错,但**不要一边承认一边把话题往回收**,更好的做法是说明"我理解到 X 层,再往下没接触过,但我的猜测是 Y"。

5. **算法题应对方式消极**。零输出之外,没有做任何"不会做但显得专业"的动作:没确认题目约束,没给暴力解,没口述复杂度,没主动要提示。面试官给了两次机会("怎么样有思路吗""这个是比较经典的")。

6. **缺少量化表达**。Q2 把系统链路讲清楚了,但全程没有日均笔数、报文量、迁移数据量、提升幅度这类数字。简历上写了"日均处理 1000+ 笔跨境交易、4000+ 笔跨境账单""百万级/千万级数据迁移",口头复盘时一个都没用上,可信度和分量都打了折。

7. **紧张度整体可控,但长回答中段逻辑跳**。Q2 讲行内链路这一段是全场最流畅的,说明准备过的内容能讲好;但一旦离开准备范围(Q6 的状态变更时机、Q7 的 XA 实现),语速明显变快、句式变碎,出现"我们其实调完 try 就应该是认为这笔交易它是一定能成功的"这类没有信息量的话。

## 三、下一步学习计划

> 排序参考 `知识点统计.csv` 的累计频次(`weight=0.4`)与本场暴露严重度:**本场答错 > 靠猜 > 遗漏**优先。

### 1. 分布式事务:把 TCC 从头到尾讲到自己能反驳自己(最高优先级)
- **暴露情况**:Q6、Q7 连丢两题,且这是简历上最亮的一条。三个具体缺口——协调者的状态持久化与故障恢复、本地消息表与 Kafka 补偿各自的职责边界、"本地消息表 + 监听器"到底是不是 TCC、它改善的到底是什么。
- **为什么重要**:字节、蚂蚁、美团这类公司,交易/支付类团队几乎必问分布式事务,而且一定会沿简历往下追三轮。"本地消息表 + 监听器 + Kafka 补偿"这套组合恰恰是最容易被抓自相矛盾的地方。
- **学习动作**:①把 **TCC(阿里 Seata TCC 模式)**、**本地消息表 / 事务消息(RocketMQ 事务消息)**、**Saga**、**XA/2PC**、**最大努力通知**五种方案画成一张对比表:一致性强度、中间态可见性、阻塞性、协调者位置与故障恢复、适用场景;②用自己的系统写一份答辩稿,必须能回答:协调者宕机了二阶段谁来推、消息表存的是 TCC 状态还是业务消息、Kafka 在这里是"重试通道"还是"事件总线"、try 成功但 confirm 永久失败的最终兜底;③准备一句能自洽的定位:"我们这套是**本地事务 + 消息可靠投递 + 下游预留资源**的混合方案,借用了 TCC 的二阶段语义,严格说不是标准 TCC",并说明为什么这样取舍(避免长事务占资源、避免同步阻塞)。

### 2. 算法:恢复刷题,优先经典题型与"不会时的整套应对动作"
- **暴露情况**:Q8 现场零思路、零代码、零沟通,是本次未通过的决定性因素。
- **为什么重要**:字节每一面都有算法环节,且是硬门槛;即使方向聊得好,算法挂等于整场挂。
- **学习动作**:①**每天 2 题保持手感**,优先数组/双指针/哈希/二分/DFS-BFS/DP 六大类高频题,固定用 Hot 100 或 CodeTop 按公司筛;②**针对性补齐几何/扫描线类**(本场题目涉及点集关系,候选人的第一反应"两两比较是否有交点"方向对但没走下去),重点看**矩形/区间重叠、扫描线、平面最近点对、凸包**这类经典题的 O(n log n) 做法;③**练"不会做时的标准动作"并形成肌肉记忆**:复述题目确认理解 → 问边界与规模 → 给暴力解并说复杂度 → 请面试官确认是否可以先写暴力 → 再要提示优化。哪怕最终没 AC,这套动作也能把 25 分拉到 50 分以上。

### 3. DDD:补齐概念体系,把"我做过"变成"我懂为什么这么做"
- **暴露情况**:Q4 中六边形架构、战略设计/战术设计答"没听过";"最核心的聚合是什么"答成了"我管了哪些领域对象"。
- **为什么重要**:DDD 已连续多场出现(`知识点统计.csv` 累计 3 次),且候选人简历把它列为项目核心贡献,答不上基础概念反差极大。
- **学习动作**:①精读《领域驱动设计》(Eric Evans)第 1–4 章 + 《实现领域驱动设计》的**战略设计**(限界上下文、上下文映射、通用语言)与**战术设计**(实体/值对象/**聚合与聚合根**/领域事件/仓储/工厂)两套概念;②重点吃透**聚合**:为什么聚合是事务一致性边界、聚合根的作用、聚合要设计得小;③补齐**六边形架构(端口与适配器)/洋葱架构/整洁架构**与"四层架构"的关系,并能说出自己项目为什么选四层;④把数字人民币项目按 DDD 重写一遍建模:画一张限界上下文图 + 挑一个聚合画聚合根与不变性约束,作为面试可展示的材料。

### 4. Java 微服务基础设施:RPC、注册中心与服务治理
- **暴露情况**:Q5 只答出 Feign/RestTemplate,连 Dubbo/gRPC 都没提,把 RPC 说成"算不算是 IPC 的一种"。
- **为什么重要**:微服务通信是 Java 后端必问基础题,也是候选人简历里"Spring Cloud"标签的直接支撑点。
- **学习动作**:①理清概念分层:**RPC 框架(Dubbo / gRPC / Thrift)** vs **HTTP 客户端封装(Feign / RestTemplate / WebClient)**,讲清各自定位、序列化协议(Protobuf/Hessian2/JSON)、通信层(Netty)、服务治理(注册发现、负载均衡、熔断限流、超时重试);②结合自己项目回答"我们微服务间怎么调用的、为什么这样选";③顺带补齐 **Nacos/Zookeeper 注册中心**原理,以及一次 RPC 调用的完整链路。

### 5. 表达训练:结论先行 + 一句话定位 + 量化
- **暴露情况**:Q1 被追问 6 轮才说清定位;Q3 被点破"不了解你具体在做什么";Q2 全篇无一个数字。
- **为什么重要**:本场面试官多次不得不替候选人总结或重新定义问题,这会直接影响"表达与沟通"这一项的评分,而它往往是不通过理由里的隐性一条。
- **学习动作**:①为简历上每个项目准备一段 **30 秒结论先行版**:"我在 X 项目的 Y 层,上游是 A、下游是 B,负责 C 这件事,带来了 D 结果(数字)";②把自己讲的内容**录音回听**,专门挑"差不多是这样吧""可能就""这一类的"这类虚词;③每个项目补 3 个量化点(日均量、数据规模、性能/时效提升、故障率下降),写进面试小抄。

### 6. 银行/支付业务抽象能力:从"报文"升维到"支付指令与清算层次"
- **暴露情况**:Q3 面试官两次强调"报文这个概念太宽泛了""我想了解业务含义",候选人仍回到 XML/HTTPS 的技术层。
- **为什么重要**:国际支付、跨境清算类岗位,面试官关心的永远是**资金流和账务层次**:谁动客户账、谁动行内账、谁动银行间账、清算窗口与结算最终性。技术格式不是他们想听的。
- **学习动作**:①画出跨境支付的完整资金流与信息流示意图(SWIFT MT/ISO 20022 报文 → 代理行清算 → 账户行划转 → 收报行入账),标注自己系统所处位置;②练三个"业务语义"版本的回答:用一句话说清"一笔跨境汇款进来,我这一层改变了什么状态";③补充 **SWIFT MT/ISO 20022、CIPS、代理行模式、清算窗口、结算最终性(settlement finality)** 等基础概念(累计频次已达 7 次,是最该吃透的业务知识点)。
