## 总览

- **评估依据**：一面为「项目深挖(分库路由 / 支付链路 / 报文解析 / 慢 SQL 排查)+ 业务一致性 + AI 认知」结构,几乎无八股基础题。Q2 分库路由、Q5 数字人民币扫码支付全流程、Q12 慢 SQL 排查三题是本场亮点:路由讲了"报文分类 + 取业务无关位做 hash + 二阶段报文按原报文路由"的完整取舍,支付链路能按 同步/异步/终态/次日区块链对账 分步讲清,慢 SQL 覆盖了执行计划驱动表选择、优化器为何"选错"主键索引、显式指定索引与半年分界,深度到位。失分与风险主要在引导型题目:Q1 开场铺垫过长被面试官打断、Q6 网络超时方案靠引导才收敛到"超时判定在数研所侧 + 状态机"、Q8 消费确认与重复消费机制未深入。逐题平均 78.2;作为一面、且岗位(to B 流程复杂度 > 高并发)与候选人背景高度契合,综合给 65%。
- **一句话结论**：项目方案讲得真实、有层次,SQL 排查深度超过同经验段平均水平,是本场最大加分;短板不在技术而在表达结构(开场被打断)与分布式方案细节(超时兜底、消费位点)需要面试官引导才能点透。

## 一、问答实录

### Q1. 开场·被要求聚焦项目产出
- **面试官问**：开场让候选人介绍,候选人正从"领域驱动设计做系统搭建"讲起时被面试官打断——「可以主要讲一下,你在这个项目里主要负责的产出是什么?」
- **候选人答**：团队收支付网络报文,做收发、解析、记账对账、清算,再清分给下游,是行内跨境交易的上游端;入职后做现有平台迭代优化,并从零搭了数字人民币支付平台(Java + MyBatis)。被要求聚焦后答:参与设计搭建与库表设计,主要做报文接收模块(校验→分发给下游),并对接调账、退款等有复杂度的流程。
- **评分与点评**：70/100 · 团队定位说得清楚,但开场先铺 DDD、平台大背景再讲自己,信息前置铺垫过长,面试官不得不打断二次提问;被引导后"产出"是答出来了,主动性差一点。

### Q2. 项目·分库路由设计(路由依据 / hash 位选择)
- **面试官问**：看到简历写"多分库场景的报文路由",追问「这个分库是根据什么路由的?路由表里的设计是按报文分类吗?取哪几位做 hash?是你主导设计的还是参考以前系统?」
- **候选人答**：每笔报文带唯一报文标识号;路由不写死,路由表放数据库、应用启动加载缓存,动态分发。分两个维度:① 按报文类型配置路由策略,单阶段报文取标识号中"与业务含义不挂钩的两位"做 hash(日期、机构名会聚片,故避开);② 有同步/异步两阶段的流程(如扫码先同步确认、按指纹后异步真交易),异步追加报文打标识"找原报文",按原报文路由策略与标识号路由,保证同库。
- **评分与点评**：85/100 · 主动说出"为什么选业务无关位"(分布均匀)与"二阶段必须同库",是真实设计而非背概念,深度在本场属上乘;扣分在叙述仍偏散、靠面试官一句句拆,「不同报文类型 vs 同报文多阶段」的分类框架没先亮出来。

### Q3. 项目·路由倾斜与历史兼容(改策略 / 保留旧策略 / 为何不迁移)
- **面试官问**：确认"主要按业务类型路由"后反问「有没有出现路由倾斜(某类数据堆到某库)?改配置切策略的话,历史数据怎么找回来?这样遍历查询效率不是会变低?有没有考虑做数据迁移?」
- **候选人答**：目前没倾斜;当初不写死路由就是为可调。倾斜时可改配置表切新策略;历史兼容靠保留旧策略、按序遍历,前一个路由找不到再找后面的。系统上线约六七个月,境外交易量不大、分库容量够,新系统暂未做数据迁移。
- **评分与点评**：76/100 · 应对合理,「多策略遍历做历史兼容」是贴业务的方案;但三个追问(历史数据、遍历变慢、为何不迁移)都是面试官递台阶才逐层给出,缺主动的完整兜底陈述,「遍历多策略的代价 / 何时必须迁移」没有自己算账。

### Q4. 项目·动态报文解析与报文升级
- **面试官问**：看到"动态报文解析、XML 转 Java 对象",问用什么类/库转的;并设陷阱「报文升级突然多一两个字段,整个链路会不会出问题?」
- **候选人答**：用动态解析工具(底层 dom4j 一类)读报文,映射路径配在数据库、动态加载,报文每年升级不改代码;配置时把路径字段映射到 Java 类/属性。字段升级:协议升级会提前公告,若自动映射不了会在上线前配好;新增字段不会被解析到,且报文规范不会凭空加关键主流程字段。确认靠上游提前通知、不能上线即生效。
- **评分与点评**：78/100 · 「DB 配置驱动映射、升级不改代码」是能落地的方案,字段升级的边界答得稳(先公告、先配置、新字段非关键);但没有点出兜底(解析失败/未知字段的容错与告警),深度一般。

### Q5. 项目·数字人民币扫码支付全流程
- **面试官问**：要求把一次汇款从进入到最后回报确认的完整链路讲一遍。
- **候选人答**：分四步——① 扫码发汇率查询报文:数研所专线 → HTTPS 前置卸载/解密验签 → 路由应用把报文原文扔 Kafka 异步落盘(可查阅/重拉)→ 按路由策略发报文平台解析 → 分发给汇率查询系统取回组装;② 用户输金额点确认支付,发同步交易请求,同步发给下游校验并等响应,超时由数研所网络推定失败、作废已校验交易;③ 成功则用户输密码/指纹,真正账务发生,对方发"带账"异步报文,先落库、行内处理不通拉起重试,各平台异步下传做业务与清结算;④ 次日对账:报文平台落库全量交易,对账系统拉走做区块链对账,差错发调账报文处理。
- **评分与点评**：88/100 · 结构完整、分同步/异步/终态/对账讲清,把「同步校验 vs 异步记账必须保终态」「原文异步落盘不阻塞主链路」的动机都带出来了,是本场最佳的一整段设计表达;扣分在仍有个别自我修正与绕,未先给一句"同步异步两条线 + 次日对账收口"的总纲。

### Q6. 一致性·网络超时兜底与状态机
- **面试官问**：连环逼极端场景——「超时你确认成功怎么兼容?它还没推失败报文前你们干等吗?等待中其实已超时、之后又回了呢?那幂等性你们有做吗?」
- **候选人答**：超时未回会收到对方失败报文、作废交易;未收到前是等待其结算/失败报文。被追问"已超时又复回":先想了一阵,承认超时判定不在己侧、由数研所中心统一做,先到哪个收哪个,一般不会重复;随后补上幂等——状态机固定流转,交易只能"交易中→成功/失败",置失败后不能再流回成功。
- **评分与点评**：74/100 · 状态机约束是对的,但对「异步确认双方都收不到(悬挂交易)时本侧怎么办」先给不出、靠"超时在数研所"归因带过,本侧的对账扫单/挂账兜底没有主动讲,是全场被引导最多的题之一。

### Q7. 幂等·并发重复报文的唯一性校验与疑似重复兜底
- **面试官问**：追问「有没有考虑并发、两条消息重复发送的兜底?」
- **候选人答**：有预先校验、分系统规则:数人民币平台按报文标识号做唯一性判断;其他系统不用唯一编号,按对手行身份标识号 + 报文 + 交易金额 + 币种组合判重;判定疑似重复则打人工处理标记,由业务人员选择处理动作。
- **评分与点评**：80/100 · 「标识号唯一 vs 多要素组合判重 + 疑似重复走人工」是真实业务里两种典型做法,能讲出差异很加分;但对"高并发下唯一校验本身如何做才不漏"(数据库唯一约束 / 去重表 / 锁)没有展开。

### Q8. 中间件·Kafka 异步落盘 / 消费与重试机制
- **面试官问**：指出「你们链路很需幂等、不允许重复,接收与下发过程中有没有消费确认、重复消费怎么兜?」
- **候选人答**：Kafka 那块只用于异步保存报文原文(动作重、非关键路径,保存与否不影响交易推进,故异步消费落盘以便查阅/重拉);主流程仍是应用内实时调用,失败给延迟重试、上限约 10 次,再不行标失败回失败回执给中心端。
- **评分与点评**：72/100 · 异步落盘的"关键/非关键路径"取舍讲得好,但没答到面试官真正点的「消费确认 / offset / 重复消费」:未讲消费位点、未讲重复投递在消费侧如何靠幂等承接,重试上限也无具体值;把"为什么用 Kafka"讲清而未把"消费一致性"讲透。

### Q9. 架构·固定 vs 动态清分与平台端定位
- **面试官问**：对比数字人民币系统与之前清算系统后问「你们承接上下游,是通用化设计还是按下游业务定制?下发格式是谁迁就谁?」
- **候选人答**：分两类——固定类型报文发固定平台(数币平台一种报文对应一种业务);一种报文类型要分发多平台时,按业务要素写动态清分规则表,配在数据库、给运营维护界面配置。格式统一按我方,定位是平台端而非纯中转。
- **评分与点评**：80/100 · 清楚回答了「固定路由 vs 动态清分」两种模式的取舍与平台定位,呼应岗位"to B 平台方"画像;若能补一句这种清分与配置如何保障正确性/灰度会更深。

### Q10. 上线稳定性与当前规模
- **面试官问**：支付系统上线后会有稳定性/延迟类生产问题吗?现在每天流量多少?(简历未写量级)
- **候选人答**：数字人民币系统目前还没出现过(此类)问题;每天流量还很少,国家还没大规模推广,未到大规模使用阶段。
- **评分与点评**：70/100 · 回答简短诚实、不虚报流量,是加分项;但主动把"目前是低流量期"延伸为对高并发/稳定性设计的展示机会没有抓住,白白放掉一个表现点。

### Q11. 项目·数据迁移方案的主导程度
- **面试官问**：三个项目都体现"参与设计",追问直连支付/清算的数据迁移方案「是你主责、从方案到落地跟进,还是负责执行?」
- **候选人答**：也有参与设计,是团队一起做的;直连支付那个负责得比较多,方案选取、迁移方案设计都有参与讨论和执行。
- **评分与点评**：74/100 · 坦诚、把责任边界说清了,但"一起做/负责比较多"偏虚,没给出他在选型(为何选某方案)或落地里的具体取舍,说服力弱于前面讲方案时。

### Q12. 排查·慢 SQL(驱动表 / 索引选择 / optimizer hint)
- **面试官问**：让讲一个最近/印象深的排查生产问题的链路与思路。
- **候选人答**：慢 SQL 整改——业务是报文表(三四百万~500 万行)join 小协议表(几千行)带出机构号过滤,查询还要按报文编号排序 + 分页。排查:先带参在生产试跑、看执行计划发现没走预期索引;分析出优化器选报文表(大表)当驱动表、且因"要排序 + 取前 N 条"而选主键索引而非"日期 + 三要素"联合索引——期望是先按日期过滤出少量再 join,实际却从最早的报文按主键顺序扫到合法范围,白扫几百万行。验证去掉排序条件确实回走日期索引;最终不改驱动表,用 optimizer hint 显式指索引,并验证长/短时间范围后取"半年"分界:半年内指日期索引、半年以上指主键索引(二级索引长区间回表 + server 层大排序更慢)。
- **评分与点评**：88/100 · 全流程闭环:现象→复现→执行计划归因→假设验证→双策略分界,把"优化器为何选主键"(排序省 + 提前停止)讲得比很多面试者透彻,是本场最强答;扣分在个别术语口误(索引构成前后表述有跳)与篇幅偏长,框架若先给一句"驱动表选择 + 排序导致索引误选"会更利落。

### Q13. 排查延伸·数据归档与 Oracle→TDSQL 国产化迁移
- **面试官问**：听完慢 SQL 后引导「有考虑业务上限查询/数据归档吗?数据量到量级技术方案会有瓶颈」。
- **候选人答**：有的系统限制 3~4 天查询范围,本场景查三天已出问题;今年正做数据库国产化——应国家要求把 Oracle 迁到腾讯 TDSQL(MySQL 内核),旧数据归档到 OLAP(ClickHouse),半年内高频 + 可能退款的留当前库;用代码迁移,后续做成日终任务每天归档。
- **评分与点评**：80/100 · 能把"正在做的国产化 + 归档分层"接住面试官的业务化建议,落地真实、区分维度(访问频率 + 退款可能性)合理;若说明"新旧库并行/切量/校验"会更有说服力。

### Q14. AI/Agent·工具使用与提效认知
- **面试官问**：见简历写 Agent/MCP/Skills,问「现在用哪个 AI 工具?怎么看 agent 开发后的真实提效?是帮你写简单代码,还是能需求到落地?」
- **候选人答**：银行不让用外部流行工具,公司自研基于千问大模型二次开发的 Agent、效果差,自己把它用在重复流程(数据库改造语法变更,写 skill 沉淀固定流程让 Agent 推进);认可市面上 Agent 已能需求→落地,但工作内模型不够强仍靠人;工作模式从写代码转向 code review;业余小项目已大量交 AI,从最小可用产品迭代。反问岗位 AI 参与度时还问了公司是否开放外部 AI。
- **评分与点评**：80/100 · 认知成熟、不吹不黑(区分"公司弱模型 vs 市面强模型"),「写 skill 沉淀流程」「从编码转 code review」有实践抓手,与本项目(Claude Code 复盘流水线)呼应;若把"自己项目里 MCP/Agent 怎么拆任务"具体讲一个例子会更出彩。

### Q15. 候选人反问
- **候选人问**：项目组做什么业务?是跨境电商系统、交付给客户自用吗?技术栈?工作里 AI 参与度?主要是系统维护还是有新产品开发?
- **面试官答**：具体项目组后面 HR 沟通、未定;公司主营跨境电商(to B)大产品、行业排名第一;流量与并发要求不高、复杂度在业务流程,大量是系统/数据/客户问题维护;技术栈 Java 后端为主;AI 侧开放外部工具、不设限,能用多强就用多强。
- **评分与点评**：—(反问不评分)· 提问始终紧扣个人诉求(技术栈一致性、AI 可用性、是否有新产品/维护占比),与离职动机呼应,也借机确认了"岗位 = 维护偏多 + to B 流程复杂度"的画像,互动主动、信息收获大。

## 二、面试缺点

1. **开场铺垫过长、被面试官打断(Q1)**:从"领域驱动设计、系统大背景"绕起才讲自己,面试官一句「可以主要讲一下你主要负责的产出」直接打断。项目介绍习惯先铺平台/方法论再定位自己,结论先行与"先讲我"的结构意识不足——本场最先暴露、也是观感上的首个扣分点。
2. **分布式兜底方案靠引导收敛(Q6)**:对"等待期间已超时、对方之后才回/一直不回"这种真实悬挂场景,先答"等待对方报文",被追问才承认超时判定在数研所侧,本侧的对账扫单、挂账、定时兜底没有主动设计陈述;Q8 同理——被点"消费确认/重复消费"时仍停留在异步落盘动机,未接住 offset 与消费侧幂等。两处都是"会把业务讲对,但把边界场景与系统兜底讲不全"。
3. **数据迁移等"参与度"类回答偏虚(Q11)**:多个项目都标"设计实现 XX 迁移",被问方案是否主责时只答"一起做/我负责比较多",给不出选型取舍或落地细节,与其讲方案时的深度不匹配,容易让面试官怀疑简历标注的含金量。
4. **多策略遍历、低流量阶段的主动展示不足(Q3/Q10)**:路由倾斜的历史兼容策略是面试官逐层问出来而非主动兜底讲;被问流量时只答"还很少",未顺势把"低流量期反而做好的分库/幂等设计"反转为亮点。整体偏"答问"而非"讲方案"。
5. **表达口头禅与自我修正仍在(跨场共性、本场略轻)**:大量"呃/然后/对/相当于",个别关键句自我推翻重说(如索引构成),虽比上一场(易点云)流畅,但大段方案(尤其 Q5/Q12)仍缺"一句话总纲 → 分点 → 边界"的稳定结构。

## 三、下一步学习计划

> 排序依据:本场暴露严重度(答错 > 靠猜 > 遗漏/引导)为首要,并参考 `知识点统计.csv` 累计频次与 `weight` 注释(分布式·数据库架构、跨境报文系统、支付幂等/对账、数据迁移均为高频历史项)。

1. **分布式消息消费一致性(Kafka 消费位点 / 至少一次 / 消费侧幂等)——Q8 被点名没接住**。
   - 暴露:面试官直接问"消费确认、重复消费",候选人只答了"为什么用 Kafka 落盘",没讲 offset 提交、重复投递在消费侧如何承接。
   - 动作:把「生产端重试/投递 → 至少一次语义 → 消费端幂等」串成一条线:唯一业务号 + 消费去重表/数据库唯一约束做幂等,附 Kafka 手动提交位点、重复消费的典型成因(处理完没提交/消费超时 rebalance);再用本项目"原文落盘"举一个"消费侧若重复落盘怎么办"的例子。
2. **分布式一致性极端场景:悬挂交易 / 超时 / 对账兜底 —— Q6 全场被引导最多**。
   - 暴露:对"双方都收不到确认的悬挂交易"先答等待,归因给数研所,本侧兜底未讲。
   - 动作:整理一套自己的兜底话术:超时判定可下沉中心侧,但本地要有定时对账扫单 → 挂账/人工 → 差错调账的闭环;把状态机(交易中→成功/失败单向流转)与"次日对账发现后补终态"串成可讲的完整设计,能在下次被逼问时主动给出而不再等人递台阶。
3. **MySQL 执行计划与索引选择(驱动表 / 覆盖索引 / 优化器代价 / hint)—— Q12 答得好,值得体系化成稳定表达**。
   - 暴露:本场答得深,但仍是"背自己这一次案例",术语偶有跳,缺可迁移框架。
   - 动作:把 Nested-Loop Join 驱动表选择、二级索引回表成本、order by + limit 导致优化器"选错主键"、USE INDEX/optimizer hint、长短区间索引取舍,整理成一页"慢 SQL 排查清单"(现象→explain→归因→验证→方案),可套用到任意慢 SQL 场景;补覆盖索引能否消除回表的判断。相关历史项:MySQL·索引(最左前缀/覆盖索引)、MySQL·索引(字段选择/区分度)。
4. **分库分表体系化:hash/取模 vs 一致性哈希、倾斜治理、扩容与历史迁移 —— Q2/Q3 高频题,答得实但收尾偏被动**。
   - 暴露:本场把"业务无关位 hash + 多策略历史兼容"讲出来了,但倾斜扩容、何时必须迁移没主动算账;该知识点历史频次已是全表最高(分布式·数据库架构)。
   - 动作:补一致性哈希与取模的对比、扩容时的双写/搬迁方案、路由表动态化的灰度与回滚;把本场"旧策略保留遍历 + 配置表切换"扩展成一套可应对"倾斜→扩容→迁移"的完整演进叙述。
5. **数据归档与国产化迁移(TDSQL / OLAP 归档 / 代码式日终任务)—— Q13 真实在做,值得讲成完整故事**。
   - 暴露:答出归档分层,但没讲新旧库并行、切量与校验,面试官若深挖易露怯。
   - 动作:整理一条可复述的国产化迁移全链路:存量 → 按热度/退款可能性分层(当前库 vs ClickHouse 归档)→ 代码迁移 + 日终增量归档 → 校验与回滚;与已有历史项「数据迁移·断点续传/灰度/双写」「国产数据库·TDSQL特性」归并成同一段可讲的材料。
6. **表达结构:结论先行 + 三段式(跨场持续重点)**。
   - 动作:开场自我介绍与项目产出,统一改成"我是谁 / 我负责 XX / 产出是 1、2、3"的顺序,杜绝先铺 DDD/平台背景;把 Q5 支付链路、Q12 慢 SQL 各写成"一句话总纲 + 分步"的 90 秒腹稿;刻意在每段答案首句先给结论再展开,录音回听去掉"呃/然后/相当于"。
