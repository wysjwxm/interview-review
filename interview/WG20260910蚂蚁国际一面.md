## 一、问答实录

### Q1. 英文自我介绍
- **面试官问**：开场即明确流程——「我们面试大概四十五分钟到一个小时左右,分为三个阶段。第一个是英文的自我介绍。」不做任何题目引导,直接开始计时。
- **候选人答**：从 2024 年 7 月毕业入职讲起,公司(China Merchants Bank Network Technology)→ 团队职责(跨境交易、行内业务、对接 SWIFT 等外部金融机构、报文收发/清算/往账/对账、按业务字段分发下游)→ 个人工作(迭代优化现有系统、应用迁移与国产化组件替换 Oracle→TDSQL)→ 团队从零搭建 e-CNY 跨境交易平台。全程 `And... And... Besides...` 串联,句式破碎,名词读错;讲完补一句「平常不怎么用英语交流,比较少」。
- **评分与点评**：65/100 · 信息点齐全(公司/团队/职责/项目都提到了),但**没有结构、没有重点、语法错误密度高**(「I join the China Merchan Bank when IGraduate」),2 分钟里几乎没有一句完整正确的句子;面试官无法从中抓到"这个人最擅长什么"。

### Q2. 项目·数字人民币跨境支付系统概述
- **面试官问**：「介绍一下你一个比较擅长的项目。」开放式,不限项目、不限时长。
- **候选人答**：选数字人民币跨境支付——今年年初央行推动数字人民币跨境交易,招行作为首批搭建行搭建通道。前期功能:境内钱包境外扫码消费 + 消费退款、信息查询、对账;后期加转账。平台对接数币研究所支付网络,本平台负责:①报文前期对接(加解密、加解签);②报文原文管理(持久化);③XML 报文解析、交易信息落库,再按业务匹配规则分发给下游业务系统(电商交易走电商、线下消费走线下消费);④次日区块链形式对账。
- **评分与点评**：76/100 · 把"平台在链路中的位置 + 四件事"讲清楚了,有业务视角;弱点是没有给量级、没有划清"我做的"与"团队做的",为后面 Q3 被追问埋了伏笔。

### Q3. 项目·你负责设计的模块
- **面试官问**：直接追问产出边界——「所以你设计的是什么?你从设计的哪些模块,哪些模块你设计的?」
- **候选人答**：整体参与设计,参与较多的是报文汇入流程(报文接收、解析、响应),以及数据库表/字段设计。
- **评分与点评**：74/100 · 回答诚实、没有夸大,但**依然停留在"参与"层面,没有给出可验证的产出**(如"设计了 X 表结构""实现了 Y 模块的 Z 能力")。面试官问的是边界,候选人给的是范围。

### Q4. DDD·怎么建模、划分了哪些领域
- **面试官问**：念简历原文发起——「我看你上面说你参与了使用领域驱动 DDD 的思想,对吧?那你给我介绍一下你是怎么使用 DDD 设计这个系统的,设计了哪些领域?」
- **候选人答**：从业务建模走起——先看报文进来的业务流程、行员操作交易的流程;把报文的行为拆成动作(报文发进来/解析报文/下发报文);再按动作做技术划分。领域要素:汇入报文(接收报文)、账户(银行间账户)、清分给业务系统的规则、对账报文。给对象填行为:账户有记账、调入调出;报文有解析、获取信息;跨领域的如账户间转账用领域服务。之后做模块划分(前置报文路由、报文汇入汇出、记账、对账、报文管理、查询),再做数据库设计。
- **评分与点评**：74/100 · 这是一段**背得很顺的 DDD 标准答案**,要素(实体/领域对象/领域服务/模块划分)都对得上,所以给了 74;但全是名词堆砌,没有一处落到本系统的具体业务规则上——面试官显然听出了这一点,于是从下一题开始逐层拆。

### Q5. DDD·怎么抽象实体 / 报文是不是实体
- **面试官问**：**三层递进追问**——①「领域驱动设计,首先它要有领域,对吧?领域对应的现实世界上面就是实体,对吧?所以说我问你第一个问题,就是你怎么抽象领域,怎么抽象出实体来?」②「OK,那我问你,报文是实体吗?」③「它对应的物理世界的是什么?……我们会给它一个状态来控制它这个流转」→「**那为什么报文要有状态呢?**」④ 抛出让候选人无法回避的质疑:「**那不是应该是流水吗?报文先转换成流水存下来,流水才有状态。**」
- **候选人答**：①围绕行为识别实体:「解析报文是围绕报文来做的,记账是围绕账户来做的,所以把这些识别成实体 entity。」②确认报文是实体。③因为要记录报文落没落库、发没发、推进到哪一步,所以需要状态。④面对"应该是流水"的质疑**当场改口**:「那也可以这么叫吧,可能是我们叫法不一样。那可能你嘴里的报文,我们叫它叫原文、叫报文……你说的流水,那可能是我刚刚讲的报文。」
- **评分与点评**：64/100 · 前两问方向对;第三问开始含糊;**第四问是分水岭——候选人没有守住自己的建模口径,顺着面试官改口,反而暴露"原文"与"流水"在他脑子里是一个东西**。正确答法应是把两者职责分开:报文原文(XML 落库,不可变、只做留痕与审计)与业务流水(承载状态机、可变更、驱动流程),这是两个实体/聚合,不是一个东西的两种叫法。

### Q6. DDD·退款与支付是不是两个领域、划分原则
- **面试官问**：继续沿着实体追问——「如果一个退款跟一个收款——或者叫支付,一个退款跟一个支付,它是两个领域吗?」得到答复后紧追:**「对,那怎么区分是一个领域还是两个领域呢?」**（这是在要"原则",不是在要例子）再补一问确认:「所以你知道原则吗?」
- **候选人答**：是两个领域,因为流程区别很大,没必要杂糅在一起。区分依据是业务属性——汇率查询报文、支付报文、退款报文、对账报文各自划一个领域比较合适。被问到原则时直接承认:「原则可能一下子想不到用什么非常精辟的语言去提炼……一下子想不到怎么比较好的描述方法。」
- **评分与点评**：60/100 · **举得出例子、提炼不出原则**,是典型的"用过没想过"。「各自建领域」这个结论本身也可能被质疑——支付与退款共享账务与账户聚合,更常见的做法是同一支付领域下的不同交易类型;候选人没有意识到这里存在设计取舍,因此答不出判据。

### Q7. DDD·领域事件怎么设计
- **面试官问**：从领域服务自然过渡到领域事件——「除了实现这个领域抽象,然后领域服务的一些事件也是你完成,对吧?比如说我有一笔退款,退款肯定要做很多的事情嘛,比如钱还回来再干啥再干啥,对吧?那我想问一下,这个领域事件是怎么设计的?」候选人反问「领域事件吗?」后,面试官重复确认:「对,领域事件,你知道吗?」
- **候选人答**：先答「我知道」,随即承认系统当时没有把领域事件单独抽出来设计,主要还是给系统填充行为和一些领域服务;再补充一个想法——报文层发给记账层这个动作,他认为也可以被抽象成领域事件。
- **评分与点评**：45/100 · **本场最低分**。简历写了 DDD、上一题刚讲完领域服务,却答不出领域事件,且"我知道"之后立刻自认没做,前后矛盾;最后那句"报文层发给记账层可以抽象成领域事件"是**在被追问压力下现造的例子**,面试官没有接。这一题基本坐实了 DDD 只是"用过名词"。

### Q8. 动态报文解析·XML→Java 对象的实现
- **面试官问**：念简历条目点名——「那我看一下动态报文解析,XML 格式报文到 Java 类对象。就是将 XML 格式的报文转为 Java 对象,对,那你怎么转的?」
- **候选人答**：要做动态转换,因为每年会有报文升级,不能写死。用 XML 读取工具(dom4j)读取字段,字段路径配在数据库里,启动时加载到内存;再通过反射把值放进 Java 对象,完成"参数树到 Java 树"的结构映射。面试官复述确认「就是你有个配置,字段到 Java 属性的配置放在 DB 里,然后加载去反射,通过这种方法是吗?」候选人确认。
- **评分与点评**：80/100 · 本场答得最完整的技术题之一。**有动机(报文每年升级)、有方案(dom4j 读 + DB 配路径 + 内存缓存 + 反射)、有取舍(配置化避免改代码)**,面试官能一次复述确认,说明表达到位。

### Q9. 动态报文解析·字段映射规则多变怎么做
- **面试官问**：从 Q8 的方案上**模拟一个演进需求**并逐步加压——①「如果我有一个经常改动的字段,并且这个字段是有逻辑的,一会儿可能映射成 a,一会儿可能映射成 b,这个要怎么做呢?」②候选人没听懂,面试官换说法:「我同一个报文可能做好几个业务,对吧?不同的业务赋给不同对象,对吧?这个怎么解的呢?」③候选人给出方案后立刻反问压制:「**那你不是每次都要改代码吗?你现在是希望每次都要改代码吗?**」④最后给出提示:「有没有什么原生的方法你知道吗?……**你可以直接把 JavaScript 嵌入进去**,嵌入这种代码,对吧?」
- **候选人答**：①先理解成"路径会变动"。②给出粗暴方案:「直接写几个 if 判断,或者多个实现类的机制去实现这种多种途径。」③被反问"那不是每次改代码吗"后,候选人先反问「怎么会改代码呢?你刚刚不是 if 吗?」(理解偏差),再重新组织:可以在路径配置里加一列"映射规则",配 if 开头匹配什么字段,新增就加配置规则、改数据库的值、刷一下内存。面试官复述「所以你是准备搞一套解析规则,放在 DB 里,每次来了我都变更这个解析规则?」候选人确认,并承认弊端存在。④对原生方法明确表示「不太了解」。
- **评分与点评**：62/100 · **本场最能看出思维习惯的一题**。第一反应是 if/多实现类(能跑就行),被点破才转向配置化;配置化方向对,但候选人自己也承认要自建一套规则解析引擎——**面试官提示的"内嵌 JS 引擎/Aviator 这类脚本做动态映射"才是业界常见解**,候选人完全没有这个知识储备。这题从"会不会做"掉到了"知不知道"。

### Q10. 分库分表·分片键与分片方式
- **面试官问**：四连问把"分库分表"逐字拆开——①「实现多分库分表,怎么分库分表的?」②「你是怎么分库分表的?就是多少库多少表。」③「几个表?」④「分库分表,你要把表分的数量——**我问的是表分的数量,不是说总共有几张表**。」⑤「所以一个库里面就一张表,是吧?」「比如说有一张交易表,一个库里面只有一张交易表,是吗?」(反复确认三遍)
- **候选人答**：按报文标识号里"不会变动且无业务含义"的某两位做哈希分库,避免数据集中。目前是两个业务库 + 一个灰度库,共三个库。表很多:交易类报文有表、信息类报文有表、对账类报文有表,一个库十几张表。**最后承认:没有做分表设计,只做了分库设计。**
- **评分与点评**：68/100 · 分片键的选取理由讲得好(取不变且无业务含义的位,避免倾斜),但**"分库分表"这个词被用了三轮才说清楚只做了分库**——面试官不得不连问三遍"一个库几张表"。这在面试里是很伤的沟通失分:不是不会,是没主动交代边界。项目实际体量(三库、无分表、日均 1000–5000 笔)也撑不起"分库分表"这个词,建议简历改为"多分库路由"。

### Q11. 分库·分片键含字母的兜底
- **面试官问**：针对 Q10 的哈希方案挑边界——「如果你的分库分表的那个键里面有字母怎么办?」
- **候选人答**：目前没有字母,因为 ID 规则是写死的、不能乱给 ID;选键时就要选"能成功做分库计算的数值位",不能选会出现预期外内容的位。如果真出现(有字符串),就取哈希值,或者通过 ASCII 码转成数字,用一些手段处理。
- **评分与点评**：70/100 · 前半段"选键时就规避"是正确的设计前置思路,后半段兜底方案(哈希/ASCII)也是常规手段,方向没问题。扣分在于**第一反应是"这也没有字母"**(否定问题的存在),而不是先接住假设再给方案——防御性设计意识偏弱,和后面编程题"并发问题?"的第一反应是同一种模式。

### Q12. 分库·一笔交易跨库与次发报文跟随路由
- **面试官问**：给出具体反例场景——「有没有一种情况是你有一个交易,它要落两笔单据,一个落到了 A 库,第二个落到了 B 库,有这种情况吗?」追问:「那怎么确保一定在一个库呢?」再引导归纳:「所以是你要取原报文,次发流量要取首发流量的原报文,统一去构建是吗?」
- **候选人答**：不会让这种情况发生。以退款流程为例:先来一个同步请求,给它应答;之后还有一个代账的异步请求。前置路由会让后续报文跟随前一笔报文落到同一个库。确保手段是字段关联——后续报文都带原报文类型 + 原报文 ID,每种报文类型有路由规则,取原报文类型和原报文 ID,按原报文类型的路由规则计算跟随报文的目标库。并进一步说明:原报文信息就在本笔报文里带着,**不需要反查原报文**。拿不到原报文 ID 就回 NAK、不接收,因为信息不完整无法推进业务。
- **评分与点评**：82/100 · **本场最佳**。一阶段/二阶段报文同库、按原报文路由、信息自带不反查、拿不到就 NAK——四层都答到了,而且"不用查原报文"这一点主动澄清了性能与依赖问题,说明是真做过。

### Q13. 报文落库链路与异常报文处理
- **面试官问**：从上一题的"不接收"往下挖落库——「有没有处理异常的情况?」→「那这种你们没有落单呀?」→候选人反问"什么叫落单"后说明:「我说的落单是没有落流水单,只是把请求落下来了,对吧?」→「那在落报文的这一步,是不是没有分表呀?没有分库分表了?」
- **候选人答**：前置库收到报文后有行为把报文原文推到 Kafka,起一个原文管理应用异步消费 Kafka 队列做持久化——因为落库是重操作,扔到 Kafka 异步做,且**允许它失败**,不影响交易推进。完整链路:报文进前置库 → 解密解签 → 原文推送与存储 → 分库计算 → 发到报文解析层 → 解开报文(必须先解开才知道报文类型、往哪回、回什么)→ 落库;有问题就打异常状态、不推进后续流程,组一个异常回执报文回给支付网络、推给对手。异常报文也会落流水单。原文管理那一步确实没有再分库分表,因为它和后面的流程并不紧密。
- **评分与点评**：76/100 · Kafka 异步落库 + 允许失败 + 异常回执 NAK,链路讲得完整且有设计理由。扣分在于**"落单"这个词被面试官引用了两轮才对齐语义**——又一次出现术语没对齐就往下答的问题。

### Q14. 多库聚合查询·实现与分页续传
- **面试官问**：「好多库聚合查询,多库聚合查询是你们做的吗?还是中间件自己做的?」→「怎么聚合的?」
- **候选人答**：自己写的聚合查询应用。业务页面要求按报文 ID + 时间排序并限制条数。查询应用收到请求后去服务中心拉取对应的分库实例列表,把请求分发到各实例,拿到 n 个有序列表;在应用内做归并排序,同时标记每个分库返回了多少条、用到多少条,把每个分库的"最后一位"回传界面;界面下次带着这个标记回来查,实现分页续传。
- **评分与点评**：84/100 · **本场第二高分**。分库实例发现、请求分发、n 路归并、游标标记回传、分页续传,整条链路闭合,是自己真做过的项目细节。唯一没展开的是"归并时为什么能直接利用各分库有序"——但下一题补上了。

### Q15. 多库聚合·数据量过大时的空间/时间优化
- **面试官问**：继续加压——「如果你有很多个库,导致你最终查询的结果过大了怎么办呢?」
- **候选人答**：**空间上**先看内存是否撑得住,一般撑得住(一百个库查两百条,内存可接受);撑不住就扩内存或控制查询量。**时间上**要利用每个分库数据有序的性质——通过键值拉数据时直接用索引拉出有序数据,归并时不要把所有列表揉在一起再排序(n 复杂度会高);可以用小根堆控制多分库数据的比较,每次从堆顶取最大/最小元素,从而降低复杂度。
- **评分与点评**：80/100 · 主动分了空间/时间两个维度回答,小根堆多路归并是标准解(等价于 LeetCode 23 合并 K 个有序链表)。扣分在于**开头把"库多"等价成了"结果集大"**,面试官问的是分库数量增大导致聚合结果膨胀,候选人用"一百个库查两百条"来回应,略微偷换了问题;`n` 的复杂度表述也含糊(实际是 O(N·k) vs O(N log k))。

### Q16. 编程题·转账(失败留痕/防死锁/并发超支)
- **面试官问**：屏幕共享后在本地 IDE 完成场景设计题,题干两个硬约束——「支付转账」**「保存转账记录,即使是失败」**「防止死锁」。候选人写完框架后,面试官追加一问:**「我再问一个问题,有并发问题吗?」**
- **候选人答**：
  - **思路**:设计账户表 + 交易流水表;转账记录无论成败都先写。
  - **防死锁**:同一事务内按用户 ID 从小到大顺序加锁更新,避免 A→B 与 B→A 的循环依赖。
  - **失败留痕**:意识到"保存流水"和"业务事务"若在同一事务,失败回滚会连流水一起回滚,于是**另起事务先存流水**;定义流水状态机 W(wait 等待转账)/ C(成功)/ F(失败),初始状态 W 先入库,成功改 C,异常改 F。
  - **代码结构**:两个 DAO(账户、流水);先技术校验 → 查用户 → 初始化并保存流水 → 业务校验(余额)→ 操作两个领域对象(from 减钱、to 加钱)→ 事务内按 ID 排序加锁更新 → 更新流水为 C;异常捕获后置 F。
  - **并发追问后**:先答"会有问题"——业务校验在事务外,两个线程同时校验通过会超支;随后给出修正:把校验挪进事务,加当前读锁(`for update`),校验通过才执行;后到的事务会被阻塞,拿到锁后发现余额不足,走改 F 的分支。
- **评分与点评**：72/100 · 主干完成度不错:**失败留痕用"另起事务"解、防死锁用"ID 有序加锁"解,两个考点都命中**,状态机也用上了。扣分有三处:①**并发超支问题是面试官追问才发现的**,而且发现后只是口头补方案、没有真的改代码;②把校验放事务外又放回事务内,暴露对"校验与加锁必须原子"这件事没有形成条件反射;③`for update` 加锁时没有讨论锁顺序与索引——如果查询不走索引会退化成表锁/间隙锁,这点没提。

### Q17. 反问
- **候选人问**：①团队日常主要用什么技术?②AI 的使用多吗?以什么形式嵌入日常工作流程?③团队处于新产品搭建探索期还是旧系统维护期?④主要做哪些业务?⑤日常请求量/数据量多大?⑥(补问)刚刚那个 JavaScript 规则,你打算放在什么地方让它加载后能不停机生效?
- **面试官答**：①常见中间件都有;②一线同学以提效为主(AI coding、AI 写文档),自己可选择公司内部或外部工具(公司报销);③两者兼有,互联网公司既要支撑业务又要更快支撑业务,只能不断优化系统;④国际收单——阿里国际电商、淘宝、AliExpress、天猫国际;⑤天猫国际双十一几十万笔,Google Pay 一天几千万笔很正常,下单/支付/结算都在团队内;⑥「常见的 ZK 呀啥都可以,还有 Nacos 呀,就这些分布式的配置中心,它就可以实时地推到你内存中去,改变你内存中的配置。」
- **评分与点评**：—(反问一般不评分) · 前五问质量不错,问到了团队阶段、业务量级、AI 落地形式,是有效的双向了解。**第六问把"补答 Q9"包装成反问**,虽然思路取巧,但直接暴露了对分布式配置中心不了解——面试官给的答案(ZK/Nacos 配置中心推送到内存)恰恰是 Q9 的标准解,这一问相当于当面承认"该知识点缺失"。

## 二、面试缺点

1. **英文自我介绍是硬伤(最致命的一项表达问题)**:语法错误密度极高(`I join the China Merchan Bank when IGraduate`)、名词读错(China Merchants、TDSQL、e-CNY)、`And / And / Besides` 全程串联、没有层次(公司→团队→职责→项目全部平铺)。面试官把它排在第一个阶段,等于开场就给了负面印象,容错空间被压缩。

2. **简历主打项被三层追问击穿**:简历第一卖点「结合 DDD 思想实现高可用、多分库的系统设计」,在 Q4→Q5→Q6→Q7 连续四题里从 74 分滑到 45 分,并引出面试官的结论式评价「相当像是完成了业务整个流程的串联,并没有整体去对它建模」。**这是本场失分的决定性因素**——问题不在于没用过 DDD,而在于简历把它写成了自己的设计成果。

3. **术语没对齐就往下答(反复出现)**:Q5 被质疑"应该是流水"时改口「那也可以这么叫吧,可能是我们叫法不一样」,放弃了自己的建模口径;Q10 的"分库分表"被问到第三遍才承认只做了分库;Q13 的"落单"被追问两轮才对齐语义。三次都是**不主动交代边界、顺着面试官的口径走**,导致面试官必须反复杂问确认。

4. **回复追击时先给"能跑的",不给"能扩的"**:Q9 的字段映射规则,第一反应是 if / 多个实现类;被反问"那不是每次都要改代码吗"才转配置化。这属于**工程直觉层面的短板**,不是知识问题——面试官对这种回答的容忍度很低。

5. **否定问题的存在,而非先接住假设**:Q11 问"分片键里有字母怎么办",第一反应是"这也没有字母";Q16 问"有并发问题吗",第一反应要先"想一下"再答。**防御性设计与并发意识都偏被动**,需要被追问才启动。

6. **概念只到名词层**:Q7 答不出领域事件、Q9 不知道脚本引擎做动态映射、Q17 反问时暴露不清楚 ZK/Nacos 配置中心热更新。三个知识点都停在"听说过名字"。

7. **表达冗余、自我修正多**:「就是」「那其实」「比如说」「这样子」高频出现,一句话内多次重启(如 Q5 的"那可能你嘴里的报文……那可能是我刚刚讲的报文")。讲项目时缺少"先给结论再展开"的习惯,面试官需要自己去拼。

8. **面试环境准备不足**:开场花了较长时间排查钉钉与网页冲突、共享屏幕、本机没装 Chrome,还出现"钉钉被挤掉"的情况。虽然面试官也在同步调试(有双方因素),但候选人在环境适配上偏被动,挤占了本已紧张的面试时间。

### 2. 动态映射规则引擎(报文解析的进阶解法)
- **暴露情况**:Q9 先答 if/多实现类,被反问"那不是每次改代码吗"才转配置化,且不知道脚本引擎方案。
- **为什么重要**:这条正对着你简历的"动态报文解析",下次被问到概率极高;`知识点统计.csv` 里「支付业务·跨境支付链路/报文系统架构」已累计 7 次,是最热知识点。

### 4. 分库分表的完整概念与边界表述
- **暴露情况**:Q10 被连问三遍"一个库几张表"才承认只做了分库;分片键兜底方案(哈希/ASCII)是现场想的。
- **为什么重要**:`知识点统计.csv` 里「分布式·数据库架构(分片/高可用/分库分表)」已累计 6 次,是仅次于报文链路的高频项。
- **具体动作**:①把"分库"与"分表"彻底分开讲清楚:各自的收益(连接数/单表数据量)、代价(跨库 JOIN、分布式事务、扩容);②补齐常见分片算法(取模 / range / 一致性哈希 / 基因法)与**扩容时的 rehash 问题**;③准备一张"我的项目实际做到哪一层"的边界表(3 库、无分表、日均 1000–5000 笔),坦率说清体量,避免用大词撑场面;④简历措辞从"分库分表"改为"多分库路由"。

- **暴露情况**:Q16 编程题的并发超支问题是面试官追问才发现的;校验放事务外再挪回事务内,说明没有形成条件反射。
