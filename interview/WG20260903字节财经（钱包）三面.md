## 一、问答实录

### Q1. 自我介绍与职责定位
- **面试官问**：开场让"先简单介绍一下吧";追问确认毕业年限("毕业两年是吧?")。
- **候选人答**：24 年毕业入职招银网络(招行信息技术部独立出的子公司);团队是行内跨境交易上游端,对接 SWIFT、数字人民币跨境、跨境人民币等设施;平台收报解析、控时序、记过渡账、按业务要素清分给下游;做银企直连,给企业提供支付指令与账单;技术栈 Java + Oracle/MySQL。
- **评分与点评**：80/100 · 信息完整、定位清楚,但与二面开场几乎同一套话术,只讲"做什么"没讲"我做到什么程度";有填充词、句子被打断重起。

### Q2. 离职动机与职业考虑
- **面试官问**：怎么考虑看新机会?
- **候选人答**：银行监管要求多;AI 发展起来但行内不让用外部 AI 工具/模型,不利技术发展,想换环境。
- **评分与点评**：85/100 · 动机真实、落到"成长",与二面表述一致、不抱怨,姿态健康;若能补一句"想做的方向"更完整。

### Q3. 绩效情况
- **面试官问**：有没有绩效考评、怎么样、上浮占比多少?
- **候选人答**：季度评,大部分拿平均,固定比例下浮、少数上浮;自己有一次半年上浮、几次季度提效上浮;上浮占比不了解、公司没公开。
- **评分与点评**：82/100 · 直率可信,主动给出"半年上浮+多次季度提效"的亮点;占比答"不了解"略被动,但如实不吹,可接受。

### Q4. 项目深挖·数字人民币系统与个人分工
- **面试官问**：讲一个最有挑战的技术项目;随后连追「你做的哪一块?」「几个人做?」「什么时候开始?」「现在上线了吗?」。
- **候选人答**：从零搭建的跨境数字人民币系统(对接数字人民币研究所支付网络,打通消费/汇款/退款/调账);个人:参与系统设计 + 负责报文解析组装、报文处理模块、调账流程对接;团队约 20 人,去年年底做到今年年初,已上线、国家尚未正式推。
- **评分与点评**：85/100 · 项目是真实深度参与、可讲细节;个人分工边界在被追问后才交代清楚,主动讲"我负责什么、规模多大"偏弱。

### Q5. 系统设计·业务建模→领域对象→三层模块
- **面试官问**：引导候选人按系统设计展开介绍。
- **候选人答**：业务建模(识别操作人员/交易报文/交易系统→划分任务)→抽象领域对象(资金报文/对账指令/账户行/账户关系/清分规则)→模块划分:**报文路由层**(前置校验/加解密/原文管理/分库路由)、**报文层**(解析/落库/时序控制)、**记账层**(银行间过渡账/调中台记账/反洗钱/流动性风控),再清分给下游业务系统;另有参数、报文管理、人工操作模块。
- **评分与点评**：85/100 · 是典型的 DDD 落地打法,层职责清晰、与简历「DDD 高可用多分库设计」吻合,本场技术亮点;仅表达仍靠填充词推进。

### Q6. 全链路讲解与同步/异步、难点
- **面试官问**：请讲完整交易链路;追问确认扫码"确认付款未输密码"的同步请求,并问难点。
- **候选人答**：扫码→查询请求(汇率等)→研究所专线→前置 HTTPS 软卸载转 HTTP→路由层解密解签→原文投 Kafka,异步应用消费落库(避免重操作掺入主流程)→按分库路由到报文分库→报文层解析并持久化交易/币种/金额(平台要对账)→记账层记过渡账+监管操作→按清分路由表按业务要素发下游(如汇率系统)→组包按原链路返回。难点:流程复杂、交易数据要保证不丢失。
- **评分与点评**：83/100 · 链路完整、Kafka 异步 + 分库路由 + 对账驱动落库都有工程细节,是强项题;"难点"答得泛(只抛"复杂/不丢失"),未顺势展开"如何保证不丢",错过一次展示机会。

### Q7. 幂等防重·防重表与两套方案
- **面试官问**：怎么保证不重复、不遗漏?追问表结构、设计几个字段、讲关键字段,确认"只用一个编号防幂等?"。
- **候选人答**：报文带唯一编号→入库前查幂等校验表→DB 唯一索引兜底→有则跳过回重复应答、无则插入;防重表字段=报文编号(核心)+ 报文类型/时间/机构;另有一套业务要素防重(对手行身份标识+账号+币种+金额),防不干净时打"走人工"标志由人工判断推进,看业务要求二选一。
- **评分与点评**：84/100 · 唯一索引兜底 + 两套防重策略 + 人工兜底,方案成熟、有取舍;但只答了"防重复",面试官问的"防遗漏"(不丢)基本没接,被追问表结构时先答"数不清"稍显含糊。

### Q8. 数据库选型·Oracle→TDSQL
- **面试官问**：用的什么数据库?
- **候选人答**：入职时多为 Oracle,推国产化后换腾讯 TDSQL,内核是 MySQL。
- **评分与点评**：70/100 · 一句话带过,没有借"国产化迁移"展示任何经验(正是简历里最重的经历),回答偏薄,面试官因此转去问 MySQL 原理。

### Q9. MySQL 事务原理(MVCC/redo/binlog/锁)
- **面试官问**：MySQL 内核里事务大概是什么原理?
- **候选人答**：(以可重复读为例)**隔离性**靠 MVCC——事务建 ReadView、指向 undo log 版本链,读时按事务标识定位可见范围;锁上给索引位置加记录锁/间隙锁;**原子性**讲成——提交时先写内存再写 redo log,redo log 设 prepare、回 server 层记 binlog、打成 commit 标记、落盘;持久性靠日志、定期刷盘。
- **评分与点评**：60/100 · 术语全中(ReadView/undo/redo/binlog/prepare/commit/记录锁间隙锁)但**因果错位**:把"原子性"讲成了 redo+binlog 两阶段提交与落盘,而那是崩溃恢复一致性/提交协议;redo 真正对应持久性(WAL),binlog 是逻辑日志,原子性靠 undo log 回滚;隔离性也只讲了 MVCC 快照读、未提 current read 的 next-key 锁防幻读。像背过的知识点拼在一起、没建立起"每个日志解决什么问题"的图景,面试官只要再深问就会露底。

### Q10. 编码题·排序(现场未完成)
- **面试官问**：来写点代码。先问「平时用 AI coding 吗?平时写 Python?」,随后开共享网页编辑器给一道**排序题**(题目具体类型转录中未明)。
- **候选人答**：起初在 Python 编辑器,主动说"思路可以讲一下吗?Python 语法忘了,平时写 Java";面试官允许换 Java 后仍称"换 Java 要久一点""用网页编辑器不习惯",两次请求加时;面试官离场去洗手间回来仍未完成,最终面试官以"下一个会开始"收场,让其"下来自己调一下"。全场未提交可运行代码。
- **评分与点评**：40/100 · 先弃 Python、换 Java 依旧多轮加时未落地,暴露出**裸环境手写 + 不依赖 AI 的基本功缺失**(面试官前一句专门问 AI coding 占比,后一句排序做不出,直接印证其担心);叠加二面 TopK 同样的"思路会说、实现崩",这是连续两场最重的失分信号,并把本场时长压缩、仓促结束。

### Q11. 反问·团队业务方向
- **候选人问**：团队业务方向是新产品还是旧产品迭代?
- **面试官答**：岗位主要是抖音钱包方向,可能做独立的抖音钱包产品;目前是抖音内嵌页面,是否独立"再考虑"。
- **评分与点评**：—(反问一般不评分)· 问题合适,拿到团队定位关键信息;若能追问一句"当前内嵌页面的技术栈/团队规模"会更主动。

## 二、面试缺点

1. **手写编码"思路会说、实现不会",且依赖 AI 被坐实(最致命)**：全场唯一编码题(基础排序)在 Python 语法遗忘、换 Java 后仍两次加时、面试官离场返回都未完成,直接导致面试提前结束。配合面试官前问「平时用 AI coding?」,几乎是在验证"编码都交给 AI、手写退化"的担心——二面 TopK(中文逗号语法错、引包受阻)已经是预警,本场进一步证实。**裸环境写不出最基础的题,是三面(bar raiser 式筛人)的硬伤。**
2. **MySQL 原理停留在背诵、因果错位(Q9)**：ReadView/undo/redo/binlog 等术语都能报出,却把原子性讲成 redo+binlog 两阶段提交+落盘、把持久性与"定期刷盘"混谈,说不清各日志职责;隔离性也只讲 MVCC 快照读、漏了 next-key 锁防幻读。面试官由"用的什么库"追问到"事务原理",本意考国产化/内核理解,候选人没接住,反成最大技术失分。
3. **表达仍有结巴、填充与自我打断,结构靠面试官拼凑(延续二面未改善)**：全场高频"呃/嗯/啊"、句子说一半换方向;Q4/Q5/Q6 信息量大但全靠面试官一句句"你做的哪块/几个人/什么时候/难点是啥"牵引成形,自己很少一次性讲出"背景—分工—做法—难点—结果"的完整结构。
4. **答问偏被动、被问才展开(Q4/Q8/Q10)**：项目分工、规模、难点都是被追问才补;"数据库选型"一句话带过,浪费了展示国产化迁移(简历最大经历)的机会;"难点"只说"复杂、数据不丢失",没主动给出"Kafka 落库不丢、幂等防重、对账兜底"的具体机制。
5. **编码请求方式略欠火候(Q10)**：开头就用"换语言要时间""编辑器不习惯"找台阶,在编码题还没开始就传递了不自信的信号;更优的是直接说"我平时写 Java,我用 Java 写"然后利落开写。

## 三、下一步学习计划

> 排序依据:本场暴露严重度(答错/未完成 > 靠猜 > 遗漏)为首要,并参考 `知识点统计.csv` 累计频次与 `weight` 注释。

1. **裸环境手写基础算法(最高优先级,救命项)** — 本场直接致命:编码题未完成、面试被压缩。二面 TopK、三面排序连续两场"思路会说、手写崩"。
   - 动作:以 Java 为手写主语言,在**无补全的网页编辑器**(可用 leetcode / 牛客在线)上把最基础的 20 道题写熟——快排/归并/堆排序、链表反转/合并、栈队列、两数之和、TopK、简单 DP 等;每道限时 5–10 分钟一次过、不查 API;刻意戒掉"让 AI 先写"的习惯,面试前两周每天 1–2 道裸写。可把常用 API(Collections.sort、PriorityQueue、String 操作)默写一遍。

2. **MySQL 事务与日志机制理顺(Q9)** — 本场被问到概念混淆,也是多场高频考点(知识点统计「MySQL·MVCC与隔离级别」本场累计第 3 次)。
   - 动作:按"解决什么问题"重搭知识图:①**undo log**——事务回滚(原子性)与 MVCC 版本链;②**redo log**——WAL 先写日志、崩溃恢复(持久性);③**binlog**——逻辑日志、主从复制/归档;④redo prepare→binlog→commit 两阶段提交是为了**崩溃时 redo/binlog 一致**;⑤隔离级别中 MVCC(ReadView+快照读)与 next-key/间隙锁(current read 防幻读)各自的分工。对着简历里的 TDSQL 迁移经历,把"MySQL 内核原理"讲成自己的故事。

3. **幂等/防重的"不重复 + 不遗漏"完整闭环(Q7)** — 本场只答了防重复,面试官问的"不遗漏"没接上。
   - 动作:把"消息/报文防丢失"补齐——消费后落库顺序、本地消息表/事务消息、失败重推与对账扫描兜底;结合"先查再插 vs 直接插"的竞态本质(二面 Q8 也栽过),把唯一索引 + DuplicateKeyException、业务要素防重 + 人工兜底两套方案各写一页可复述笔记。

4. **项目叙述"主动给结构、主动亮个人贡献"(Q4/Q6/Q8)** — 本场多次被追问才具体,数据库选型白送一次展示机会。
   - 动作:给 3 个代表项目各写一段"结论先行"腹稿——**背景 3 句 + 我具体负责什么 + 关键设计/难点怎么解 + 规模与结果(团队 20 人、百亿/百万级、灰度回滚)**;面试里主动先说"我做了 X、团队 Y 人、耗时 Z",不要等面试官逐个问。

5. **表达风范持续练习(二面已列,未见改善)** — 结巴、口头禅、句子说一半换方向,是本场主观印象分的持续拖累。
   - 动作:对 4 的腹稿做"2 分钟版 + 5 分钟版"口述练习,用"第一/第二/第三"强节奏;录音回放数自己的"呃/嗯"次数,目标降到每 30 秒≤1 次;可请朋友扮演面试官连环追问"你做哪块?几个人?难点?上线了吗?",练到不靠对方牵引也能成段。

6. **反问与收尾(保持,微调)** — 反问本身合适;可在时间紧张时主动收尾("今天时间关系,我没有更多问题了,谢谢您")避免显得被动。
