# WB0824 平安银行一面 · 面试复盘

> 岗位方向:财富管理/投顾(to C 交易系统,含基金/证券/债券/黄金),团队在用 AI 建投顾
> 面试形式:技术面(视频) ｜ 候选人:黄文广(招银网络科技,跨境支付 SWIFT 代理行开发,2 年经验)

---

## 1. 问答概要

按时间顺序梳理本次面试的核心问答:

**① 自我介绍与离职原因**
- 候选人概述:24 年 7 月毕业进入招银网络科技,在跨境支付平台开发室做 SWIFT 代理行开发,负责跨境交易上游端的报文解析、反洗钱调用、记账与分发;近一年参与项目迭代优化与国产化(组件、数据库)改造。
- 列举三个项目:SWIFT 直连支付、央行数字人民币跨境报文平台、跨境支付清算系统。
- 离职原因:想涨薪,现公司调薪慢。面试官确认后转入正题。

**② 项目中最棘手的问题与架构设计(核心大问题)**
- 面试官要求讲一个复杂问题的思考与解决过程,并追问是否参与架构设计。
- 候选人以**直连支付系统重构**为例,主动讲了两个重构原因(数据库国产化替换 + 批量交易回执效率低)、三个难点(加快回执、保证持续可用、灰度控制),以及对应方案:
  - 灰度:新应用 + 旧应用白名单表 → 命中配置的交易转发到新应用验证 → 逐步扩大范围至全量;
  - 回滚:旧应用保留完整交易数据,新应用出问题时可把已放行数据推回旧应用主流程重跑;
  - 提速:设计**异步任务表**,记录"总交易数 / 已完成交易数",下游完成响应时累加,相等即出回执,替代定时任务轮询。
- 这一段结构清晰、方案完整,是本场最高光的部分。

**③ 追问一:回滚场景与账务处理**

- 面试官指出支付环节有入账/出账,追问"已产生的交易怎么办、账务怎么处理"。
- 候选人区分了两类:报文解析类问题可回滚;**动到资金的不直接重跑**,而是把新应用已生成的交易数据手动同步回旧应用,补做生成回执等后续流程。承认"回滚是有范围的"。
- 面试官继续追问:新旧应用是否单写、如何把数据推回旧应用 —— 候选人补充:提供界面接口,给业务人员一个"交易重试"按钮。白名单匹配的是对公客户(账号/支付机构标识号),灰度量小,仅两三家企业。

**④ 追问二:数据库替换(Oracle → TDSQL)**
- 候选人说集中在两点:索引使用不当调整 + 新增字段调整,外加 SQL 语法兼容改写。
- 数据类型:字符串可直接映射;数值类型需注意(Oracle 小数 vs TDSQL 的 number);Oracle 大字段(BLOB 等)团队统一改写成字符串。
- 上线切换流程:按版本单写/双写,灰度放量 → 旧库转为静态数据 → 整体迁移。交易数据用"旧应用连 Oracle、新应用连 TDSQL"双库方案,待 Oracle 无新写入后统一迁移;界面提供"查历史 / 查新数据"的开关切换数据库。

**⑤ 账务系统**

- 候选人自评"了解一些":本系统不直接记账,通过幂等重试保障不丢,具体记账由下游调账务系统完成;定位是"渠道"。面试官确认。

**⑥ Agent / AI 使用(第二大主题)**

- 候选人介绍:行内提供类 Claude Code 的编程 Agent;他针对国产化迁移写了 skill 沉淀重复工作(如 SQL 语法切换后的单测生成、代码规范参考),并推广到小组团队使用。
- 面试官深挖"实际业务落地"与选型判断:**skills 与 SOP 的区别** —— 候选人坦诚对 SOP 不太了解,仅讲 skill 原理(Markdown 文档 + 参考文档 + 脚本供 AI 识别执行);强调实践主要落在"代码编写提效",未落到业务。
- **RAG**:候选人不熟悉召回率，表示不深入了解RAG,只知道是知识库。

**⑦ 个人 AI 实践**

- 候选人分享:与同事用 Claude Code + 免费 ASR 模型做了"面试复盘"小工具 —— 上传简历 PDF + 录音,转录后用 LLM 做说话人切分与技术名词修正,再结合简历生成复盘。被面试官评价为"自己的小工具项目"。

**⑧ 团队规模与反问**
- 小组 6 人 → 上一级 20 人 → 再上一级 300 人。
- 反问:业务方向(财富管理/to C、基金证券债券黄金交易 + AI 投顾)、数据量(日均几千万)、新项目 vs 现有系统维护(两者都有)、AI 工具管控(集团白名单、不能连外网)。

## 2. 面试缺点

1. **表达零散、口头禅多**:通篇大量"呃、然后、那、嘛",句子经常说半句重开,需要听的人拼凑意思。虽然后段直连支付重构部分结构化较好,但整体流畅度和专业感不足。
2. **关键概念边界一开始不清**:回答"回滚场景"时,没有第一时间主动区分"未动资金(报文解析类)"与"动到资金"两类,而是被面试官用"入账/出账、账务怎么操作"反复引导才说清楚,暴露对资金安全边界思考不主动。
3. **数据迁移细节被追问才补充**:面试官明确问"数据怎么推回旧应用""交易数据表怎么切",候选人才补充界面按钮、"旧库无新写入后统一迁移";说明方案细节准备不够,靠临场挤牙膏。
4. **数据库类型知识不够系统**:面试官点名问"比较常见的哪些类型需要替换",候选人只答出字符串/数值/大字段,未给出成体系清单,且"number 统一命名"的说法含糊。
5. **Agent 领域深挖乏力**:对 **SOP 完全不熟悉**直接认输;对 **RAG 只知道"知识库"**;面试官两次想把话题引向"业务指标落地(召回率、多轮性能、减少人工干预)",候选人都停在"编码提效"层面,未能展示业务价值。
6. **简历与实际能力存在落差**:简历写"熟练使用 Agent 开发、掌握 Agent/MCP/Skills 技术原理、有开发实践经历",但面试中被问及 skills/SOP 选型与业务落地时,呈现深度不足,容易被质疑简历夸大。
7. **没有把 AI 实践与目标岗位挂钩**:反问环节得知对方在做 AI 投顾,但候选人没有顺势把自己 Agent/skill 经验往"业务智能化、投顾场景"上靠,错失展示匹配度的机会。

## 3. 可改进点

1. **用 STAR 结构重写三个项目故事**:每个项目固定"背景 → 难点(2-3 个)→ 方案与取舍 → 量化结果(如回执耗时从 X 降到 Y、迁移 N 万数据)"。面试前背熟,回答时先给结论,再用"第一、第二、第三"展开。直连支付重构这段已够好,把其余两个项目(数字人民币报文、清算系统)也补齐到同等颗粒度。
2. **提前预演追问链**(支付/账务类面试必考):
   - "动了资金怎么办?" → 分「未动资金(可重放)」与「动资金(走对账/冲正/幂等)」两套话术;
   - "怎么保证不丢不重?" → 幂等键、MQ 确认、二阶段 confirm;
   - "回滚的边界与触发条件?" → 讲清回滚不适用于资金类,且有人工审批。
   - 用"抛观点 + 举实例"的方式,不等面试官挤牙膏。
3. **整理 Oracle → TDSQL 类型映射表**:字符串、NUMBER/数值、日期时间、CLOB/BLOB、序列、索引/分区等各列一张对照清单,并配合 1-2 个实际踩坑案例讲。
4. **补齐 Agent 体系知识**:至少能对比 **skills / SOP / MCP / workflow** 的区别、各自适用场景与选型依据;能说清 **RAG**(知识库 → 向量检索 → 召回率评估 → 减少人工干预),并准备一个"从提效到业务落地"的完整案例(哪怕是自己小组内的小场景)。
5. **控制口头禅与节奏**:把"呃/然后/嘛"列为戒断目标;回答前默念"结论 → 分点 → 例子"。用手机录音试讲一次项目故事,回放自查。
6. **主动向岗位靠拢**:反问环节结合对方 AI 投顾业务,补一句"我的 Agent/skill 沉淀能力可以迁移到投顾场景的自动化与知识库建设上",把个人实践变成卖点。

## 5. 下一步建议学习的知识点(优先清单)

结合目标岗位(财富管理/to C 交易 + AI 投顾)与简历,建议按优先级学习:

1. **Agent 工程体系(本周优先)** —— MCP / skill / SOP / workflow 的定义、区别与选型;补齐"为什么用 skill 而不是 SOP"这类问题,把简历里的"掌握技术原理"落到实处。
2. **RAG 与业务落地** —— 向量检索、chunking、召回率/准确率评估、知识库与人工干预的减少;设想一个"投顾场景 + Agent/RAG"的结合点。
3. **金融交易资金安全** —— 幂等设计、账务记账(借贷)、对账、冲正、动账场景的最终一致性;这是支付/金融类面试必问,本次已暴露短板。
4. **数据库国产化迁移方法论** —— 类型映射、双写/灰度切换、数据校验、回滚,整理成可复述的完整流程。
5. **目标岗位业务面** —— 基金/证券/债券/黄金交易系统的常见业务流、AI 投顾行业现状,准备 2-3 个对岗位的理解问题,在反问环节体现匹配度。

---

> 一句话结论:候选人在"项目重构 + 灰度回滚 + 批量回执提速"上的实战讲述是本场亮点,基础业务表达能力尚可;短板集中在 Agent 体系知识深度(SOP/RAG)、数据库迁移细节与资金安全边界,以及表达的结构化与自信度。目标岗位在 AI 投顾方向,建议把 AI 实践从"编码提效"往"业务智能化"迁移,补齐金融账务与 Agent 体系知识,下次面试表现会显著提升。
