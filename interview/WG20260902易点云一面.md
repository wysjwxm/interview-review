## 一、问答实录

### Q1. 自我介绍
- **面试官问**：开场核对身份后,直接「我们开始,先简单做个自我介绍」。
- **候选人答**：24 年 7 月毕业加入招银网络科技(招行科技部门独立子公司);团队做境外交易,是行内跨境交易的上游端,对接 SWIFT、央行数币系统;平台职责 = 收报文→解析→控时序→记账对账→把交易数据发给下游业务系统,另做直连支付(接企业批量指令、发账单);技术 Java + MySQL。
- **评分与点评**：76/100 · 定位清楚、把「上游 / 清结算 / 记账对账」讲出来了,模块覆盖简历;但表达碎、「然后/就/呃」多,信息靠铺垫推进而非结论先行。

### Q2. 离职原因与职业规划
- **面试官问**：确认「正式工作两年左右、还在职?」追问换工作原因;再问「你是走技术吗?现在想做什么提升?」
- **候选人答**：在银行系公司受监管约束:网上资源限制访问、AI 工具(Claude Code 等)不让用,不利接受新技术与积累,故想换;规划 = 深耕交易/支付业务方向 + 想接触流量大的系统(现跨境资金量大但流量不高)+ AI 保持与前沿同步。
- **评分与点评**：78/100 · 动机具体、理由可信,与「想用更多中间件/新技术」的诉求一脉相承;若能顺带把「想补的基础短板」讲出来会更完整。

### Q3. 项目·直连支付国产化改造(系统切换/切量/数据迁移)
- **面试官问**：让挑一个参与度高的项目;候选人选直连支付(依赖上下游少、流程完整)后,要求讲「有技术复杂度、有难度的功能是怎么实现的」,并追认「是纯业务转换吗」「响应慢是什么原因」。
- **候选人答**：去年年底做系统改造——监管要求数据库与组件国产化,趁机重构 + 迁移。目标四条:迁移期交易不丢、尽量无业务中断;设计回滚策略、缓慢逐步验证地做流量切量;数据迁移方案调研选型;改造提高交易响应时间。
- **评分与点评**：76/100 · 四条目标与简历「安全可靠、可回滚、无业务中断的系统切换 + 百万级数据迁移」对应,骨架在;但多为点到为止、未主动展开量化与机制,深度依赖面试官挑方向。

### Q4. 项目·提高响应时间(汇总任务表触发回执 + 退款处理)
- **面试官问**：锁定「响应慢」追问——原系统为什么慢?改造怎么做?
- **候选人答**：系统接批量报文、每笔交易回下游响应时间不一;原先靠**定时任务扫全量交易到终态才回执**,频率低、慢。改为设计**汇总任务表**:交易落库时登记总数,每笔返回触发更新状态并推进「已完成数」,总数=已完成即触发回执。处理退款边界:回执未发→把对应交易置为退款;已发→**补一个回执**单独告知客户退款。
- **评分与点评**：80/100 · 从「定时扫描」到「计数触发」的优化思路清晰、边界(退款)也考虑到了,是全场最完整的设计表达;扣分在叙述绕(先铺垫再给点),量化(节省多少时间)缺失。

### Q5. 技术栈与 Kafka 异步落盘
- **面试官问**：项目用什么技术栈?
- **候选人答**：Java;库 Oracle→国产化后为腾讯 TDSQL(内核 MySQL);框架为公司基于 Spring Boot 的自研封装;中间件主要一个 Kafka——存报文原文很重且非关键路径,报文投队列、单独应用异步消费落盘。
- **评分与点评**：78/100 · 能讲清「关键路径/非关键路径」的取舍与异步解耦动机,落地合理;对中间件整体用量坦诚(「用得不多」)。

### Q6. Spring Cloud 框架与网关负载均衡
- **面试官问**：框架是公司封装,对开源的如 Spring Cloud 组件有了解吗?比如 Gateway 的负载均衡策略?
- **候选人答**：公司也是 Spring Cloud 形态,有网关、远程调用、注册中心/配置中心,只是换名字、底层一致;负载均衡 = 网关探测可用实例、选健康实例转发、屏蔽不可用。
- **评分与点评**：70/100 · 意识到「换皮同源」是好的;但负载均衡只讲了健康探测这一层,没说出轮询/加权/一致性哈希/最小连接等策略,也没有客户端(LoadBalancer)与服务端(网关)之分的概念,「了解」停在概念层。

### Q7. Redis 用途与本地缓存做法
- **面试官问**：Redis 了解过吗?缓存一般能用来干嘛、实际用过吗?
- **候选人答**：团队是核心交易系统、不让用 Redis;实际缓存放在应用内——参数配置加载进 Map/映射结构;报文每年升级,把「XML 路径→Java 树结构」的映射做成配置表加载到应用,避免写死。
- **评分与点评**：68/100 · 坦诚 Redis 实战为零,但把应用内配置缓存与报文映射讲得有条理;短板在于没把「这些场景在 Redis 里怎么做」接住。

### Q8. Redis 数据结构
- **面试官问**：Redis 支持哪几种数据结构?
- **候选人答**：先说自己用得不多,再开始猜——「数组肯定有吧?字符串应该也有;为了可用性应该也有 Map/KV 这种结构,应该主要就这些」。
- **评分与点评**：55/100 · 靠猜作答:把「数组」当成 Redis 类型,漏掉 List/Set/ZSet/Hash 主体,字符串也说得犹豫。团队禁用不能解释为何没有面试级知识储备——高频中间件的基本盘缺口,本场明显失分题之一。

### Q9. MySQL 索引设计(字段选择/区分度)
- **面试官问**：平常创建索引用哪些字段建、怎么评估?(追问)怎么评估区分度大小?
- **候选人答**：① 主键索引选键——有序(减少页分裂)、几乎不变动,是重要选择因素;② 按查询/定位频率给日期、账户等字段建索引;③ 区分度要高,性别这种不要建;举账单系统的账单日、联合索引为例。
- **评分与点评**：78/100 · 主键「有序 + 不变动 + 少页分裂」、区分度两个判断标准都说对了,例子贴切;未覆盖最左前缀、覆盖索引、回表等延伸,停留在字段选择层。

### Q10. MySQL update 的锁范围(全场核心追问)
- **面试官问**：不同 where 条件的 update,锁的范围你会评估吗?——连串引导:你怎么知道锁的是这一行?找的过程中不只锁这条吧?锁的范围取决于查的范围;查的范围由谁决定?「只要跟了条件大概就不会锁表,是吗?」
- **候选人答**：初答「InnoDB 改哪行锁哪行、等值定位锁一行」;被引导后答出 DML=先 DQL 查询定位再变更、锁表场景=无 where / DDL;但对「锁范围取决于检索是否走索引」始终没点透,反问面试官意图,「特殊情况想不到、生产没见到过」。
- **评分与点评**：55/100 · 只掌握「等值锁一行」的直觉与「没条件锁表」的粗规则,缺「执行计划 + 索引」决定锁粒度(无索引等值也可能锁多行/间隙)的核心认知;面试官在 Q 尾及收尾两次补讲、候选人最后才「哦,是这个啊」。本场最大失分题。

### Q11. 线程池参数与大小评估
- **面试官问**：线程池一般怎么创建、定义多少?大小你怎么评估?
- **候选人答**：核心/最大线程数按业务分组(交易大、对账小);拒绝策略不允许交易请求丢弃,拒绝后靠上游重试兜底;大小看业务流量 + 物理机 CPU 数;线程工厂、队列等用默认。
- **评分与点评**：72/100 · 按业务与 CPU 定大小、交易请求不许丢这两点是对的;但队列类型/容量、keepAliveTime、CPU 密集 vs IO 密集的经典权衡没覆盖,拒绝策略描述含糊(具体用了哪种策略没讲清)。

### Q12. 并发安全集合(ConcurrentHashMap 的 null key/value)
- **面试官问**：线程安全的集合了解哪些、用到哪些?ConcurrentHashMap 的 key 能为 null 吗、value 能为 null 吗?
- **候选人答**：只说出 ConcurrentHashMap 一种,概括为「对桶加锁防并发变更」;key 能否为 null 靠「空桶判断」反推、方向接近,value 无法给出确定结论,最终未答出。
- **评分与点评**：62/100 · 有「按实现原理反推」的意识是优点;但结论不稳、对 HashMap(允许一个 null key / 多个 null value)与 ConcurrentHashMap(key/value 均不允许)的差异没有成型的知识,属于「会说不会讲透」。

### Q13. 候选人反问
- **候选人问**：公司主要做什么业务/产品?技术栈?平均业务量多大?工作用 AI 多吗?主要做维护迭代还是新项目开发?
- **面试官答**：办公设备租赁(to B、硬件为主),软件围绕业务运营(商城、订单、发货、库存);技术栈含 gateway、nacos、Redis、MQ/Kafka、ES(自建技术中台集群);to B 请求量不大、复杂度在业务;内部大量用 AI;工作大部分是迭代。
- **评分与点评**：—(反问不评分)· 提问紧扣自己的诉求(技术栈广度 + AI 使用 + 新开发机会),与离职动机呼应,互动主动;面试官也以这段反问了解了候选人对「技术广度」的期待。

## 二、面试缺点

1. **Redis 数据结构基本盘空白(Q8)**:答不出 Redis 的几种基础数据类型,把「数组」当类型、靠猜作答,List/Set/ZSet 均未提及。直接原因是银行核心团队禁用 Redis、实战为零,但对目标岗位(公司明显重度用 Redis/MQ/ES)属于必须补的中频基础。
2. **MySQL 锁范围与索引/执行计划脱节(Q10)**:把「update 等值就锁那一行」当唯一模型,被「先查后改 → 锁范围由查的范围决定 → 查的范围由谁决定」多轮引导仍不到位,最终由面试官两次点破「无索引字段即使等值也可能不止锁一行」。对锁机制缺系统性认知,且当场没有主动向面试官确认的追问,处于被动接招。
3. **并发集合概念粗、结论靠猜(Q12)**:ConcurrentHashMap 只记住「桶上锁」一句话;null key/value 的规则现场推不出,HashMap 与 ConcurrentHashMap 的差异无成型答案。
4. **网关负载均衡、线程池、Kafka 高级特性都停在表面(Q6/Q11/Q5)**:负载均衡说不出具体策略与客户端/服务端之分;线程池不覆盖队列/keepAlive/密集类型权衡;Kafka 直言没用过事务消息/顺序消息。属于「用过的场景能讲、没用过的讲不深」。
5. **表达碎、铺垫多(跨场共性)**:开场与 Q4 等大段叙述靠「然后/就/呃」推进,先绕后点,面试官需多次确认核心;口头表达结构化程度是本场整体观感的隐性扣分项。

## 三、下一步学习计划

> 排序依据:本场暴露严重度(答错 > 靠猜 > 遗漏)为首要,并参考 `知识点统计.csv` 累计频次与 `weight` 注释。

1. **MySQL 锁机制与执行计划(update 锁粒度 / 索引决定锁范围)** — Q10 本场最重失分,被面试官两次补讲。
   - 动作:建立「锁范围取决于执行计划所选索引」的框架:走唯一索引→行锁;无索引/走全表→可能锁多行甚至表级;再补间隙锁/临键锁、当前读与快照读的区别;用自己项目里的 update 语句对照 explain 结果,能回答「这条语句锁几行」。
2. **Redis 数据结构与使用场景** — Q8 靠猜、零实战;且目标岗位自建 Redis/MQ/ES 集群、属高频必问。
   - 动作:把 String/Hash/List/Set/ZSet 五种结构与典型场景(缓存、计数、排行榜、分布式锁)各配一个自己项目可移植的例子,能解释现在应用内 Map/报文映射缓存「放 Redis 会怎么设计」。
3. **Java 并发集合与 HashMap 底层** — Q12 结论靠猜。
   - 动作:明确 HashMap(允许 1 个 null key、多个 null value)vs ConcurrentHashMap(key/value 均不允许,并发下无法区分「没有」与「为 null」);过一遍 ConcurrentHashMap 的锁粒度演进(synchronized 桶 + CAS)与 JDK8 实现;顺带补线程池队列/拒绝策略类型。
4. **MySQL 索引设计体系化** — Q9 方向对但不完整,且该知识点历史频次已在积累(与「最左前缀/覆盖索引」同族)。
   - 动作:在现有「字段选择 + 区分度」基础上补最左前缀原则、覆盖索引与回表、联合索引列序;用账单表设计一两个联合索引并讲清理由。
5. **网关负载均衡与中间件高级特性** — Q6/Q5 停在概念。
   - 动作:整理 Spring Cloud LoadBalancer 负载均衡策略(轮询/权重/一致性哈希)与网关侧的区别;Kafka 补事务消息、顺序消息、消费幂等的场景与实现,能把「异步落盘」之外再讲一个应用。
6. **线程池配置与评估(补全)** — Q11 只答到核心/最大线程数与 CPU/流量。
   - 动作:补队列类型与容量、keepAliveTime、线程工厂、CPU 密集 vs IO 密集的经典公式;明确交易类场景用哪种拒绝策略 + 为何 + 兜底链路。
7. **表达结构化(跨场持续重点)** — 表达碎是跨场稳定短板。
   - 动作:大段方案答案练「结论 → 分层(第一/第二/第三)→ 边界」三段式;把 Q3/Q4(改造 + 响应优化)写成 90 秒分点腹稿,录音回听去掉「然后/就/呃」。

## 复盘备注

- 通过率依据:项目叙述与动机表达清晰、Q4 设计有亮点、反问主动;但 Redis 数据结构、update 锁范围、ConcurrentHashMap null 语义三道 2 年经验后端应具备的基础题明显失分,且锁一题由面试官引导两次才点破,按中级 Java 岗位标准构成主要风险,故逐题平均 70.7 分对应通过率下修至 50%。
- 候选人当场「不懂即认、点破即收」的学习姿态较好(Q10 结尾「我知道了,是这个啊」),态度项不扣分;真正短板在知识储备广度与表达结构。
