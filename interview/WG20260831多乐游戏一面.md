## 一、问答实录

### Q1. 自我介绍与负责模块
- **面试官问**：开场确认简历项目时间(24 年 7 月至今、都在做支付相关),然后要求「简单介绍一下,在整个项目里负责哪些功能模块、解决过哪些问题」。
- **候选人答**：24 年 7 月入职,负责跨境支付能力,对接 SWIFT、央行数字人民币报文系统;平台收发/解析报文、记账对账、再清分给下游业务系统,是跨境链路的上游;另做银企直连(接收企业支付指令、发账单)。三个系统:银企直连支付、数字人民币、SWIFT 记账。
- **评分与点评**：82/100 · 定位清晰、模块罗列完整,把「上游/中台/对账/清分」讲出来了;但开场啰嗦(「其实这个」「主要就是做的」「就是我讲的」反复),第一印象略碎。

### Q2. 对接不同金融机构的兼容与扩展性
- **面试官问**：对接 SWIFT、央行等不同机构,处理逻辑上有什么异同?有没有考虑互相兼容?报文格式、报文类型会变化,你们怎么支撑扩展性?
- **候选人答**：① 对接一类系统建一个应用(不同模块不同应用),因规范/标准/支付流程差异大、各自有维护期需分别压测;② 报文每年升级、解析路径实时变,不在代码里写死——提供映射表,XML 结构映射到 Java 树状结构,映射关系存数据库、配置加载实现动态调整。
- **评分与点评**：85/100 · 答出「应用隔离 + 配置化映射」两个层次,有落地细节,方向对;若再补充映射的版本管理与升级灰度会更完整。

### Q3. 报文升级后发现问题如何回滚不影响用户
- **面试官问**：举例——报文升级通过动态配置+插件/策略模式改造后上线,发现要回退,怎么不把系统停了去回滚?部署或运营层面怎么考虑?
- **候选人答**：① 切量期间不一把切,新旧方案**两个一起跑**——旧方案结果做后续交易,新方案结果只做对比,不一致就报错关注,运行一致后才正式切量;② 大系统把交易报文前置保存进内部报文平台,记账层/业务层出问题时,报文层提供界面+人工重试按钮,把报文重新拉起解析再推送。
- **评分与点评**：88/100 · 答出「灰度对比 + 前置留存 + 人工重试」完整闭环,面试官正面评价(「切量这个也很好」)并分享了自己逐步提量 1%/2%/5% 的做法——全场亮点之一,且双方方案互相印证。

### Q4. 分布式事务(本地消息表 + 实时监听器 + 旁路 Kafka 补发二阶段 Confirm)
- **面试官问**：简历写了分布式事务——本地消息表+实时监听器+Kafka 实现二阶段提交,这是服务之间的事务吗?(并提及以前也用过两阶段、三阶段、TCC)
- **候选人答**：是和记账中台的交互:我们改报文记账状态、记账中台调我们的记账层入账,两件事要同时发生,但跨应用/跨物理机无法靠数据库原子性保证。用二阶段提交:先发 try 请求做资源预留,行内自研框架的事务监听器监听到 try 结果后执行二阶段(入账/撤销);Kafka 兜底——try 成功但下游没收到时消费重试;本地消息表保存二阶段状态与错误快照做校验。
- **评分与点评**：78/100 · 场景、机制、兜底讲得完整可信,但**术语混乱**:描述的是 TCC(try→confirm/cancel)却全程叫「二阶段提交」,没区分 2PC 与 TCC,也没说清「本地消息表+Kafka」与二阶段各自解决的问题,概念边界是明确的失分点。

### Q5. 数据迁移 / 断点续传(全量迁移期间数据持续更新)
- **面试官问**：基于什么字段做迁移?我关注一点:全量迁移时数据还在更新,怎么保证最新数据也同步过去?(后追问)数据要提供用户访问,A 迁 B 直接指向 B 是空的,迁移期间更新到 A 的数据 B 得不到怎么办?
- **候选人答**：① 允许中断:近一个月先迁、中断期间剩余以后迁;不允许中断:旧应用连旧库+新应用连新库,旧应用提供**灰度转发**,命中灰度的交易转发到新应用验证,验证通过全量转发,旧库变静态后再迁移;② 面试官追问读写场景后:起临时新应用写新库,查询做**穿透**(新库没有就穿旧库查回给用户);更新从业务上避免(更新多是近期数据),新流量先留一个月到新库,保证旧库静态;真有更新找不到就先持久化请求,迁移完再拉出来重推。
- **评分与点评**：88/100 · 多轮追问全部接住,业务方案层层递进、落地可信,面试官明确评价「你这个业务方案是没问题的」;唯一缺口是数据库底层同步技术(面试官提示 MySQL binlog、中间件双写),候选人坦言「不太了解」——业务方案强、底层机制弱。

### Q6. 分库分表维度 + 动态路由 + 数据倾斜
- **面试官问**：分库分表按什么维度?哈希方式扩展性有局限,动态加库复杂——某个用户一天请求 1 万次导致数据倾斜,涉及动态路由,你考虑过这种方案吗?
- **候选人答**：数字人民币应用按**报文编号**路由,专门写了路由层;要解决同一交易流程的多个报文(同步请求/响应+异步请求/响应)落到同一分库,通过原报文编号从业务要素分发。动态路由:不写死,写路由表,针对每个报文类型设路由方案,可改数据库配置;改规则后旧报文怎么路由——新旧两种路由方案都保存,新方案路由不到就用旧方案再查一次。
- **评分与点评**：84/100 · 分库维度与「同流程同库」讲得清楚,动态路由/新旧兼容接住了面试官的扩展性追问;但**数据倾斜、哈希扩展性局限是面试官主动抛出**的,候选人没有先讲到这一层,主动设计深度略欠。

### Q7. 收尾
- **面试官问**：你是福建人,想过来北京这边吗?
- **候选人答**：工作地不挑,主要是想换换工作;福建人、还没成家,地点自由。
- **评分与点评**：—(不评分)· 面试官明确说「技术面试第一轮到这里就结束,HR 会再约时间跟其他同事聊」,收尾信号积极。

## 二、面试缺点

1. **表达碎、口头禅多(跨场共性)**:全场高频「呃」「就……就……」「其实这个」「然后」「嘛」,开场自我介绍尤甚,句子常说到一半换方向。Q5 信息量大时靠面试官追问才把方案拼完整。
2. **分布式事务术语混淆(Q4)**:把「二阶段提交」与 TCC 混着用,描述的是 TCC(try/confirm)却叫二阶段提交,没分清 2PC、TCC、本地消息表、最终一致性各自解决什么问题——概念题「会说不会讲透」。
3. **数据库底层同步机制盲区(Q5)**:面试官提示 binlog 增量同步、中间件双写时,候选人直接承认「不太了解」,只能给业务方案,技术深度暴露不足。
4. **主动设计深度不足(Q6)**:哈希的扩展性局限、数据倾斜/热 key 由面试官抛出,候选人没主动覆盖;动态加库、一致性哈希等扩展话题被动接招。
5. **开场表达冗长**:自我介绍开头「其实这个」「主要就是做的」等填充词多,前三句信息密度低。

## 三、下一步学习计划

> 排序依据:本场暴露严重度(答错 > 靠猜 > 遗漏)为首要,并参考 `知识点统计.csv` 累计频次与 `weight` 注释。

1. **分布式事务概念体系(TCC / 2PC / 本地消息表 / 最终一致性)** — Q4 术语混淆,且这是简历已写、面试必深挖的高频考点。
   - 动作:梳理 2PC(两阶段提交)、TCC(try/confirm/cancel)、本地消息表、Saga 四者的异同与适用场景;把简历方案「本地消息表 + 实时监听器 + 旁路 Kafka 补发二阶段 Confirm」用准确术语重讲一遍,说清每层各自兜什么。
2. **数据库迁移/同步的底层机制(binlog / CDC / 双写)** — Q5 面试官提示后答不出,业务方案再完整也缺技术纵深。
   - 动作:学 MySQL binlog 增量同步、CDC 工具(Debezium/Canal)、中间件双写、全量+增量迁移流程;把自己项目的「灰度转发 + 穿透 + 持久化重推」映射到底层同步机制上,能讲出「业务方案 + 技术手段」双轨。
3. **分库分表与动态路由(一致性哈希 / 热 key / 扩容)** — Q6 数据倾斜、扩展性局限由面试官抛出,主动覆盖不足。
   - 动作:掌握分片键设计、一致性哈希、热 key 与数据倾斜的处理(读写分离/本地缓存/二级索引)、动态加库与路由平滑迁移;复盘自己「报文编号路由」的边界与不足,补一套通用回答框架。
4. **表达结构化(持续重点练)** — 口头禅与碎句子是跨场最大主观失分。
   - 动作:答案「结论先行 + 第一/第二/第三」;把 Q2/Q4/Q5 三个核心题写成 90 秒分点腹稿,录音自检去掉「呃/就/其实」;自我介绍压缩成信息密度高的三句开场。
5. **保持并固化强项:灰度 / 回滚 / 兼容设计** — Q3、Q5 获面试官正面反馈,是稳定亮点。
   - 动作:把「新旧方案并行对比 + 前置留存 + 人工重试」「业务不中断迁移」整理成可复述的方法论案例,后续面试主动展示。
