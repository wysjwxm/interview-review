## 总览

- **评估依据**：这是一场**候选人主导叙述**的面试——面试官全程只给短问句和打断式追问(「你能具体展开讲讲」「我打断问一下」),把舞台交给候选人讲项目。候选人讲清了银企直连的完整链路(解析 → 落库 → 异步推进 → 兜底重试 → 清分 → 账务),异步调度与线程池兜底这一段答得扎实(拒绝策略、兜底线程扫 A 状态超时 10 分钟都对得上);**但核心失分点与易宝那场完全一样:Q3 自己说出「TCC 事务保证资金一致性」,面试官立刻追问「你怎么保证呢?能具体展开讲讲」,回答却是「同一个事务内通过幂等或状态机控制,就是一个顺序的处理」——连续第二场在同一块石头上绊倒**。Q4 描述串行却说成并行,被面试官当场纠正;Q13「有没有出现过重复打款」含糊回避。加分项是 Q16 的面试复盘工具讲得完整具体,面试官明显有兴趣,连续追问了 skill 的文件构成。
- **一句话结论**：**项目叙述能力和工具实践是强项,但每次一碰到「资金一致性」这个自己抛出来的话题就接不住**——把最有分量的词说出来,却没有配得上的展开。

## 一、问答实录

### Q1. 自我介绍
- **面试官问**：先确认在职状态与 base(「一直在招银这边对吧」),再问「现在看机会是(为什么)」,听完动机后让候选人做自我介绍。
- **候选人答**：银行监管要求多、技术偏封闭,AI 编程等新工具用不了,想找更开放的环境;想换 base 到上海。自我介绍覆盖:24 年 7 月电子科大毕业、24 年 3 月提前实习入职招银、2.5 年、跨境支付、数据迁移、参与跨境数字人民币从 0 到 1、AI 编程实践;结尾交给面试官选项目。
- **评分与点评**：80/100 · 离职动机答得比上一场好——**「技术封闭、用不了新工具」这个理由既真实又贴合对方的技术氛围**,而且直接铺垫了后面 AI coding 的话题;自我介绍信息完整、主动交棒。扣分在于依然没有针对岗位做取舍,信贷科技和跨境支付的结合点一个没提。

### Q2. 项目展开:银企直连(背景与整体流程)
- **面试官问**：开放式出题——「基于你之前做的、你个人认为比较有挑战或者有亮点的某一个项目,具体展开讲一讲」,讲的过程中只做确认(「是你简历上的 SWIFT(那个)」),不打断。
- **候选人答**：银企直连让企业直接发 SWIFT 报文给招行付款,并提供账单服务。链路:企业在自己系统组装 SWIFT 报文 → 发到招行 → 从前置机读入 XML → 按规则解析成 Java 对象,取出收款人账号等要素。解析用开源组件 + **解析规则配到数据库**(应对标准升级:加字段、改路径)。进系统后先实时登记落库、打「待处理」标志、实时返回报文平台;内部再走异步推进:待处理 → 解析 → 生成付款人/收款人表 → 清分给下游。异步可能失败,用几个线程池扫超时/失败状态做兜底重试。账务层:企业钱记在我们这层 → 按付款人决定下游系统(对公/零售)→ 清分时把钱转给下游系统的过渡户。
- **评分与点评**：75/100 · 内容其实很全(接入、解析、编排、账务四块都讲到了),而且「解析规则配到数据库以应对标准升级」是个有说服力的设计点;问题是**没有主线、平铺直叙**——一口气把链路、解析、异步、兜底、账务全铺开,面试官只能靠「我打断问一下」来收束。缺一个开头:「这个系统解决的问题是 X,我负责 Y 这块,分三层讲:接入 / 编排 / 账务」,再补一个量化结果。

### Q3. 项目难点:状态机与资金一致性(TCC)
- **面试官问**：顺着项目问「那你觉得难点是什么?」,候选人答完后**立即深挖**:「你怎么保证呢?能具体展开讲讲」;候选人答得空,面试官**再追一次**:「然后具体展开讲讲嘛,用一个(例子)。」
- **候选人答**：难点是状态机设计,还有一些 TCC 事务要保证资金的一致性;保证方式是「同一个事务内,在我们应用里面你可以通过幂等或者说一些状态机的控制来保证它——就是一个顺序的处理,它不会多(做)」。
- **评分与点评**：55/100 · **本场最严重的失分,和易宝那场是同一个病**。「TCC 事务保证资金一致性」这句话是候选人自己抛出来的,面试官给了两次机会要求展开,回答却是「同一事务内 + 幂等 + 状态机 + 顺序处理」——这套说辞既不解释 TCC 的三阶段,也没回答一致性,而且「同一个事务内」本身就否定了分布式事务的前提。简历第二个项目第一行的 Try 冻结 / Confirm / Cancel / 错误影像表 / Kafka 旁路补偿,一个字都没提。

### Q4. 落库与处理的先后关系(被纠正串行/并行)
- **面试官问**：用共享屏幕画图讲流程时,面试官切入具体细节:「你现在处理落库,你们用(的是什么数据库)?」→「我落没落库成功,和你这里报文处理两边有什么用(关系)?」→ **当场给出判断**:「所以这是一个串行的动作,并不是你刚刚描述的这是一个并行的动作。」
- **候选人答**：之前 Oracle、现在迁移到 TDSQL;要先落库成功才可以处理;承认「嗯,是串行的,先落库完,然后异步去做处理」。
- **评分与点评**：65/100 · 数据库演进(Oracle → TDSQL)答得干脆;但**被面试官抓住表述矛盾**——前文把落库与异步处理描述成并行,实际是串行。这类矛盾杀伤力不小,会让面试官怀疑你对系统时序的理解是否清晰,而不是仅仅口误。

### Q5. 用版本号 / 状态做并发控制
- **面试官问**：抓住候选人自己提的「版本号或者状态」连追两问:「能具体说说吗?怎么用版本(号)?你刚刚提到的什么版本号,或者是还有什么?」「具体哪一条——你拿一个具体的报文来展开讲一下。」
- **候选人答**：以解析步骤为例,记录进来是初始状态 A,把状态从 A 改成 P 表示处理中,其他线程就无法再从 A 改成 P——这样保证只有一个线程处理它的解析。解析完成后业务要素落库(一个付款人、多个收款人的一对多),再把状态置成初始态,异步交给下游做清分。
- **评分与点评**：72/100 · **「A → P 状态的条件更新即乐观锁」这个例子讲得具体、可验证**,是本场技术回答里质量较好的一段;不足是只说了一种手段(状态条件更新),没说版本号那条线怎么用,也没提更新影响行数 = 0 时的处理。

### Q6. 异步用的是什么消息系统
- **面试官问**：「系统用的是什么消息(系统)?」候选人没听清,面试官补一句「就是对您的消息(队列)」。
- **候选人答**：这个是我们系统内部的异步,我们会有线程池,用线程池去做不同的阶段。
- **评分与点评**：68/100 · 如实回答「内部用线程池、不是消息队列」是对的,没有硬凑 Kafka;但这里其实是**主动展示的好机会**——简历上写了 Kafka 旁路报文,顺手补一句「主流程用线程池,另有 Kafka 旁路做监控与补偿」就能把话题带到自己熟的领域,候选人放过了。

### Q7. 线程池挂了怎么办(兜底线程)
- **面试官问**：「如果线程池挂了呢?」
- **候选人答**：还有兜底线程——线程池挂了,这一步的任务还是 A 状态,没被丢进线程池,那就仍有兜底的线程把它捞起来再做处理。
- **评分与点评**：78/100 · 答得干脆且逻辑自洽:**任务状态不依赖内存中的线程池,依赖数据库状态**——这正是正确的设计思路。这一段是本场技术深度的亮点。

### Q8. 线程池打满 / 拒绝策略
- **面试官问**：「如果线程池被打满了,你一般会怎么处理?像你这种场(景)。」
- **候选人答**：有拒绝策略——让提交任务的线程自己去执行,尽量不把任务丢掉。
- **评分与点评**：80/100 · 准确答出 `CallerRunsPolicy` 的语义(调用者线程执行、不丢弃任务),而且能说出**取舍理由**(「尽量不要把这个任务丢掉」)。与简历「异步可靠性保障」那一条完全对得上。

### Q9. 任务状态维护在哪 / 为什么不用定时任务
- **面试官问**：连环三问——「你往下分发任务的这个状态是维护在哪里?」「这里为什么又要从(数据库查)?」最后直接给替代方案质疑:「那就不需要从(数据库查)了,(如果)前面这个(异步)走了,你直接通过定时任务、普通 job 按状态把它捞起来继续处理,(不就行了吗)?」
- **候选人答**：状态维护在数据库;把消息 ID 丢到线程池,线程拿到 ID 后回数据库查完整业务数据;查的时候要带上处理状态做判断。对面试官的替代方案:**「这样也是可以的。但定时任务你可能需要过一段时间——其实我们早期的系统就是定时任务的,后面改了一版才是这样异步的,因为定时任务不是固定周期触发一次嘛,触发的这期间有一段时间的空档,你就不能那么及时。」**
- **评分与点评**：78/100 · **「早期是定时任务、后来改成异步事件驱动」这个回答是本场最好的技术回答**:承认替代方案可行,再用「定时任务有调度空档、时效性不够」给出真实取舍依据,而且带着演进历史(早期版本 → 改版),可信度很高。建议把这段打磨成可以主动讲的亮点。

### Q10. 系统重启后的兜底
- **面试官问**：「如果线程池挂了,或者是系统服务重启了,这里你会(怎么处理)?」
- **候选人答**：会有兜底线程去扫各张表的记录,比如报文表里 A 状态的、更新时间超过现在 10 分钟的,扫描起来做兜底处理。
- **评分与点评**：76/100 · 「状态 + 超时阈值」这个兜底扫描条件说得很具体,和简历「定时任务扫描处理中(超时)、待处理、处理失败三类异常记录」一致。扣分在于只答了机制,**没说重启期间是否会造成重复处理**(兜底捞起的任务与内存中残留任务如何互斥)——面试官问的是重启这个具体场景,应该顺势补上幂等/状态条件更新兜底。

### Q11. 清分给下游系统怎么做
- **面试官问**：「这里清分给业务下游的系统,是怎么做的?能展开讲(吗)?」
- **候选人答**：根据付款人的账号、信息做策略匹配,匹配到同业/零售/对公系统;清分时既把消息给他们,也把钱转给他们——拿到他们的过渡户,把我们的钱转过去,生成一个 ID 连同业务信息一同给他们。
- **评分与点评**：72/100 · 策略路由 + 过渡户转账这两层说清楚了;不足是没提**路由规则存数据库支持热加载、新增规则无需发版**(简历上明确写了),也没说清分失败的补偿。

### Q12. 下游幂等与唯一标识由谁生成
- **面试官问**：两问——「我想问一下这里的幂等(怎么做的)?」「就是你说下游怎么不会重复处理?」候选人答完后追问「是谁生成、在哪(生成)?」
- **候选人答**：通过唯一的幂等标识,每一笔交易都有一个唯一标识,下游根据这个标识去做;标识由我们的系统生成,在落库前的那个步骤生成。
- **评分与点评**：68/100 · 答对了基本事实(唯一业务号 + 落库前生成),但停在定义层面。同样的位置,上一场你答的是「数据库唯一索引兜底」,这一场答的是「唯一标识」——**两次都没有把「防重复打款」的完整链路说出来**:唯一键约束 → 冲突后反查返回首单结果 → 状态机单向流转 → 对账兜底。

### Q13. 有没有出现过重复打款
- **面试官问**：直接问「你这边有出现过重复打款(的情况)吗?」
- **候选人答**：「重复打款,还是因为……有各种措施去(避免)。」
- **评分与点评**：55/100 · **典型的回避式回答**。面试官问的是「有没有出现过」,这是一个是非题,不是「你怎么防止」;含糊带过反而暴露底气不足。正确的答法是给结论 + 给依据:「在我负责的范围内没有出过;我们靠 X、Y、Z 三层防护,而且日终对账会兜底,我这个方向经手的量大概 N 笔」。

### Q14. 系统容量与性能测试
- **面试官问**：「那你当前这个系统的存储量是多大呀?性能这一块有做过测试吗?」
- **候选人答**：有;日常业务没有那么多,峰值大概十出头(10+)的 TPS;看过压测报告,大概能达到 100 多。
- **评分与点评**：78/100 · **比易宝那场进步明显——终于给出了具体数字**(峰值 10+ TPS、压测 100+)。扣分在于「存储量」这个问题**没有回答**(只答了性能),而且数字说得偏保守、没有说明是单机还是集群。「日常 10 TPS、压测 100+」这个差距本身是很好的故事(容量有 10 倍余量),但没有展开。

### Q15. AI coding 经验(行内)
- **面试官问**：「AI coding 这一块,你这边有什么经验积累?」候选人讲完后追问「千问(吗)?」「你这边呢?你自己有什么经验?」「那你平时怎么用?」最后落到具体:「我这么问吧,你的 coding agent 现在用的是哪个?」
- **候选人答**：行内有团队基于开源 Agent(千问的 Agent)做二开、部署在行内;大模型部署了 DeepSeek 等开源模型。自己的 coding agent 叫 **deep agent**,基于千问 Agent 二开,是命令行工具,也能集成在 IDEA 插件里(自己用 IDEA 多一些)。
- **评分与点评**：72/100 · 行内 AI 平台的构成讲得清楚(Agent 二开 + 开源大模型部署),「类似 Claude Code 的命令行工具」这个类比也让面试官快速理解。但有一个概念混淆需要纠正:**「千问的 Agent 做二开,不是根据大模型做二开」**这句反复强调反而把面试官绕进去了——二开的底座本来就是大模型 + Agent 框架,直接说「基于通义千问做 Agent 二开」即可,不必切割。

### Q16. 自写程序:面试复盘工具
- **面试官问**：「你自己写过哪一些?」
- **候选人答**：做了一个跟面试复盘相关的工具。流程:每次跑一个页面上传简历 PDF + 面试录音 mp3 → PDF 做文字识别生成简历 md → 录音传到硅基流动做云端文字识别、声纹分轨 → 根据两者生成面试总结。总结有规范:面试官问了哪些问题、我的回答是什么,下面再总结考察了哪些知识点。
- **评分与点评**：82/100 · **本场最高分,也是全场面试官反应最积极的时刻**。「有输入(简历 + 录音)→ 有处理(OCR + ASR + 分轨)→ 有规范(总结模板)→ 有产出」这条链路讲得很完整,是一个真实在用、自己迭代的工具,这比任何八股都能体现工程热情。扣分在于讲得还是偏「功能清单」,没有说**为什么做**(面试复盘的信息密度问题)、**解决了什么痛点**(人工整理录音要几小时 → 现在几分钟),缺少动机叙事。

### Q17. Skill 的文件构成
- **面试官问**：「那我能具体问一下,你这个 skill 里面写的内容是哪些?」候选人讲完后还追问了「Skill 你是怎么(写的)?」
- **候选人答**：CLAUDE.md 是它 skill 的东西……(被追问后)呃,不对,是 SKILL.md,SKILL.md。哦不对,就是这个名字——这个是 skill 的名字,点 md,叫 **interview-review**;它在一个 `.claude` 的目录下面,还有一些 Python 文件,负责 PDF 解析和调用硅基流动转写。Skill 是「把需求告诉他,然后让他(写)」。
- **评分与点评**：62/100 · **这是对自己项目的细节问题,却答得最不流畅的一题**:「CLAUDE.md」「SKILL.md」「点 md」来回纠正了三次才说出 `interview-review`。你天天在用的东西,却说不清文件叫什么、放在哪、由哪几部分组成——这会让面试官怀疑你对这个工具的掌控程度。**这一题完全是送分题,却丢了分。**

### Q18. 薪资
- **面试官问**：「你这边的薪资情况是(多少)?」「那月 base 呢?」
- **候选人答**：年包 28 万;月 base 因为薪资结构复杂(有各种补贴和节日费),简约说大概 20k × 14。
- **评分与点评**：80/100 · 数字给得干净利落,还主动解释了结构复杂度,沟通上很得体。唯一可优化的是可以先给一个「总包 28 万、折合月 base 约 20k × 14」的整体印象再补充结构。

### Q19. 反问:业务范围 / AI 实践
- **候选人问**：你们主要做什么业务?→ 有具体一点的吗,在哪个地方做?→ 你们对 AI 有什么实践、怎么用的?→ 模型是自己部署还是买?→ 能再详细说一下它怎么赋能业务的、用在哪一方面?→ 这些借款人信息是自己填的还是别的渠道获取的?
- **面试官答**：信贷业务(百万级);覆盖东南亚、澳洲、拉美等多个国家,「可以理解成支付宝的借呗」。AI 分两块:工程侧 AI coding;业务侧 AI 赋能,比如审核场景——判断申请人是否符合风控要求,写一个审核 Agent 结合用信政策做判断。模型部分是自部署、部分走订阅服务。用户信息有自己填的,也有 API 导流、电商合作等渠道。
- **评分与点评**：—(反问一般不评分) · **六连问,层层递进,而且问到了「AI 怎么赋能业务」的具体场景和用户数据来源**——这是本场最好的提问质量,和上一场的反问一样是亮点。注意一处措辞:「就是有这么宽泛吗?」听起来略像质疑,改成「能再具体一点吗?比如主要在哪个地区」会更得体。

## 二、面试缺点

1. **又一次「说出 TCC 却讲不出 TCC」(连续第二场,最致命)**。Q3 是你自己把「TCC 事务保证资金一致性」说出口的,面试官给了**两次**展开机会,你回的是「同一个事务内通过幂等或状态机控制,就是顺序处理」。这套话术有两个硬伤:① 完全没有 TCC 的三阶段(Try 冻结 / Confirm / Cancel 释放);②「同一个事务内」直接否掉了分布式事务的前提,逻辑上自相矛盾。简历上 Try 冻结资金、事务监听器驱动二阶段、错误影像表、Kafka 旁路补偿、资损零发生——这些一个字都没出现。**易宝那场是没提,这场是提了但讲不出,性质是同一个:这块知识没有内化成能讲的话。**
2. **项目叙述没有主线,靠面试官打断来推进**。Q2 一个开放式题目,你从背景讲到解析、异步、兜底、账务,信息量大但**没有骨架**,面试官只能靠「我打断问一下」「再打断问一下」来收束。正确做法是先给一句话价值 + 分层(接入 / 编排 / 账务),再按层展开,每层留一个可深挖的点等面试官来问——把主动权握在自己手里。
3. **表述前后矛盾,被当场纠正**。Q4 把「先落库、再异步处理」描述成并行,面试官直接指出「这是串行,不是你说的并行」。这类口误在**描述系统时序**时特别危险,会让面试官怀疑你对自己系统的理解。
4. **是非题被答成回避题**。Q13 面试官问「有没有出现过重复打款」,这是要一个 yes/no + 依据,你答的是「重复打款,还是因为……有各种措施去(避免)」。回避反而显得心虚。
5. **对自己天天用的工具说不清文件名**。Q17「CLAUDE.md → SKILL.md → 点 md」来回纠正三次才说出 `interview-review`,还漏了 `.claude/commands/` 这个目录位置。这是你亲手做的项目里**最不该卡的一题**。
6. **概念表述绕**。Q15 反复强调「不是根据大模型做二开,是千问的 Agent 做二开」——把面试官绕进去了,其实一句话「基于通义千问做 Agent 二开」就够。技术沟通里这种「越解释越模糊」的表达要警惕。
7. **表达:口头语与重启句依然密集**。原稿中「我们我们」「就是就是」「呃」出现频率很高;句子经常起了个头又重来(「比如说就是同一个事物内嘛,就是比如比比如说没没出本没就是在我们应用里面」);另外**「异步」这个词被识别成「转移步/转移部/转吏部」**,源头是你发音含混,面试官在 Q6 也出现过「你再说一次?」——咬字清晰是这类远程面试的硬要求。
8. **存储量问题漏答**。Q14 面试官问的是「存储量多大 + 性能测试做过吗」两个问题,只答了性能。漏答是面试中的常见减分项,即便不知道也该说明原因。

## 三、下一步学习计划

> 排序依据:本场暴露严重度为主(答错 > 靠猜 > 遗漏),并参考 `知识点统计.csv` 累计频次(weight=0.4)。括号内为该知识点当前累计出现次数与最近出现场次。

### 1. 分布式事务 TCC 与资金一致性(连续两场暴露,优先级最高)——累计 4 次
- **暴露情况**:易宝场「面试官递台阶仍未提 TCC」;本场「自己说出 TCC,被连追两次仍讲不出」。两场合计,这块已经是**最稳定的失分点**。
- **为什么重要**:累计 4 次,且是你简历上最有分量的项目内容;面试官对它的敏感度极高(一见「资金一致性」必深挖)。
- **具体动作**:① 写一份**能两分钟讲完的 TCC 口述稿**,必须包含:为什么资金系统要强一致 → 为什么选 TCC 而不是 2PC(锁资源、跨异构系统成本) → Try 冻结不占数据库锁 → 二阶段由 Spring 事务监听器(afterCommit)驱动 → Confirm/Cancel 失败写错误影像表 + Kafka 旁路 + 延迟重试 → **空回滚、悬挂、幂等三个经典异常怎么处理** → 回查与对账兜底;② 把 Q3 那句错误话术「同一个事务内通过幂等或状态机控制」**明确划掉**,它既不是 TCC 也不成立;③ **找人大声讲三遍**,直到不用看稿。这一条是纯捡分。

### 2. 项目叙述的结构化表达——本场最大暴露(新知识点)
- **暴露情况**:Q2 开放式讲项目,内容全但无骨架,面试官被迫连续打断;Q11、Q12 也都是被追问才补出来。
- **为什么重要**:信也这场是**候选人主导叙述**的面试形态,未来遇到同类型面试(开放题、让你挑项目讲),叙述结构直接决定第一印象。
- **具体动作**:① 为银企直连写一版**结构化口述稿**:`一句话价值` → `我负责哪块` → `分三层:接入(协议解析)/ 编排(异步状态机+兜底)/ 账务(清分与记账)` → `每层一个亮点 + 一个数字`;② 每层**主动留一个钩子**(如「解析规则配在数据库,支持标准升级不发版」),等面试官来问,把节奏握在自己手里;③ 准备 2 分钟版和 5 分钟版各一份,复述到不用看稿。

### 3. 幂等与防重复打款的完整链路——累计 6 次,出现频次最高
- **暴露情况**:Q12 只答到「唯一标识」;Q13 被问「有没有出现过重复打款」时含糊回避。
- **为什么重要**:累计 6 次,是所有知识点里出现最多的;而且两场面试都被追到了同一层。
- **具体动作**:① 把「防重复打款」写成一条完整防线:**唯一业务号生成时机(落库前)→ 数据库唯一键约束 → 冲突后反查返回首单结果(不抛异常)→ 状态机单向流转防回退 → 下游幂等 → 日终对账 → 冲正**;② **准备「有没有出过问题」的正面回答模板**:结论(有/没有)+ 依据(哪几层防护)+ 数据量级 + 如果出过,怎么发现(对账/监控)和怎么处理(冲正);③ 补齐乐观锁的两条线:状态条件更新(A→P)**和**版本号,并说清影响行数为 0 时怎么办。

### 4. AI/Agent 叙事打磨:把工具讲准——累计 6 次,本场是强项却丢了细节分
- **暴露情况**:Q16 讲得很好(82 分,面试官最感兴趣),但 Q17 连文件名叫什么都不确定,三次纠正才说出 `interview-review`。
- **为什么重要**:累计 6 次,信也这场面试官明显吃这一套(连续追问 skill 怎么写);这是你的**差异化亮点**,不能因为细节卡壳而打折。
- **具体动作**:① 把工具的文件结构背下来:`CLAUDE.md`(项目约定)/ `.claude/commands/interview-review.md`(编排流程)/ `templates/面试复盘模板.md`(文档模板)/ `scripts/`(transcribe.py、pdf2text.py、upload_server.py、start_review.py)/ `知识点统计.csv`,一句话说清每个文件干什么;② 补上**动机叙事**:面试录音人工整理要几小时、信息密度低、复盘容易漏 → 现在全自动几分钟出报告,而且跨场次能汇总薄弱点;③ 讲清技术选型(为什么用硅基流动做 ASR、为什么本地跑上传服务、为什么用声纹分轨模型解决角色混淆)。

### 5. 异步任务 vs 定时任务:把本场最好的回答打磨成亮点——累计 2 次
- **暴露情况**:Q9 回答得最好(承认替代方案可行 + 给出「调度空档、时效性不够」的真实取舍 + 带演进历史),但没有主动摆出来。
- **为什么重要**:这是你**在本场唯一被认可的架构判断**,应该变成可主动输出的内容,而不是等面试官质疑方案时才被动解释。
- **具体动作**:① 把这套「为什么从定时任务改成事件驱动」整理成一页对比:时效性(空档 vs 实时)、失败恢复(定时任务天然重试 vs 异步需兜底)、实现复杂度、对数据库的压力(定时全表扫 vs 按 ID 捞);② 顺带准备「如果量再大 10 倍怎么改」(分片扫描、消息队列、状态机驱动的独立调度),应对延伸追问。

### 6. 线程池兜底与拒绝策略:已答好,补深度——累计 3 次
- **暴露情况**:Q7(兜底线程)、Q8(CallerRunsPolicy)都答得扎实;Q10 只说了机制,没说重启时如何避免重复处理。
- **具体动作**:① 补齐四要素的具体数值:核心数、最大数、队列长度、拒绝策略,以及**为什么是这几个值**(这场没被问到,下场一定会);② 补「任务状态不依赖内存线程池、只依赖数据库状态」这个设计原则的表述——这正是 Q7 答对的原因,值得说出来;③ 补监控:队列积压、拒绝次数、兜底扫描命中量的告警阈值。

### 7. 系统容量与压测——新知识点,本场给了好开头
- **暴露情况**:Q14 首次给出了具体数字(峰值 10+ TPS、压测 100+),但**漏答了「存储量」**,也没展开 10 倍余量的意义。
- **具体动作**:① 补齐数据:表数量级(千万级历史数据?)、单表行数、日增数据量、存储占用;② 把「日常 10 TPS、压测 100+」讲成一个容量故事(余量充足、扩容预案);③ 准备「TPS 再涨 10 倍怎么办」的答案(分库路由、异步削峰、连接池与线程池联动)。

### 8. 表达:咬字、去口头语、避免前后矛盾
- **暴露情况**:「异步」被 ASR 识别成「转移步」(咬字含混);「我们我们」「就是就是」密集;Q4 把串行说成并行被当场纠正。
