## 一、问答实录

### Q1. HashMap 底层结构 / 链表转红黑树
- **面试官问**：抛经典开场题——「HashMap 的底层是怎么实现的?」候选人答完后立刻追问设计动机:「它为什么会设计一个『链表转红黑树』这样的结构?」——**问的是设计意图,不是背结论**。
- **候选人答**：哈希表 + 链表(JDK8 起)加红黑树。转红黑树的原因:哈希冲突时多个 key 映射到同一槽位,冲突多了链表变长、访问变慢,「我记得是大于多少个节点」就转成红黑树。
- **评分与点评**：80/100 · 结构答对、动机方向也对。漏掉:**具体阈值记不清**(链表长度 ≥ 8 且数组长度 ≥ 64 才树化、退化阈值 6),以及树化解决的是**查询复杂度从 O(n) 降到 O(log n)** 这个量化表达。

### Q2. HashMap 线程安全 / ConcurrentHashMap 实现
- **面试官问**：顺着上一题转进并发——「HashMap 不是线程安全的吧?那我们(要)线程安全一般用 ConcurrentHashMap,它是怎么保证线程安全的?」候选人卡住后,面试官**换了个更宽的引导**:「就 JDK 里面吧,它提供的那套同步机制」,给了第二次机会。
- **候选人答**：「我记得是有一些锁的机制,比如插入的时候会去锁它的头节点」。随后主动承认「我们这边业务上用得不太多」,只能报出 synchronized 关键字和「可重入锁的 API」。
- **评分与点评**：55/100 · 「锁头节点」沾到 JDK8 `synchronized` 锁首节点的边,但**JDK7 的 Segment 分段锁 / JDK8 的 CAS + synchronized 演进这个核心考点完全没答**。更关键的是**用「业务上用得不多」回避了问题**——面试官已经把范围放宽到「JDK 里有的、三方的都行」,仍然没接住。

### Q3. JDK 及三方并发安全机制
- **面试官问**：进一步放宽——「更宽泛来说,因为服务端代码肯定要考虑并发安全问题,你们这边用到的、涉及到并发安全的机制有哪些?也可以重点介绍 JDK 里面有的,包括你用到三方那一块。」
- **候选人答**：项目里「比较少用多线程并发」;有并发的地方是在**数据库层面**用幂等、状态机保证不重复处理。随后被追问线程池场景时,答出「先往数据库插唯一键记录,靠冲突拦截」「或用乐观锁,把待处理改成处理中」。
- **评分与点评**：55/100 · **答案本身转移得聪明**——用数据库层的幂等/乐观锁回答并发安全,这是真实有效的工程手段,也是他项目的真实做法。但面试官问的是 **JDK 并发原语**,整个话题(锁、CAS、AQS、volatile、并发容器、ThreadLocal)一个都没展开,暴露的是**基础面而非经验面**的空白。

### Q4. 线程池任务并发访问共享资源 · 数据库幂等实现
- **面试官问**：就着候选人举的例子**往真实场景里钻**——「就在你刚才举的那个 case,你们真实场景中你会往数据库插记录,这个具体的实现是怎么做的?」候选人答完后,**面试官复述了一遍自己的理解来确认**:「就是说(在)数据库层面直接用异常?就是两者都调 insert,然后检测到 SQL 异常,就认为是一(回事)?」
- **候选人答**：上游给的报文带唯一键 → 据此生成数据库记录并插入 → 再往下处理;另一线程再插入会抛 `DuplicateKey` 异常 → 对该异常做特殊处理 → 说明已有线程在处理 → 返回幂等异常。
- **评分与点评**：85/100 · **本场最佳。** 落到真实场景而非背八股:唯一键落库 + 用 `DuplicateKeyException` 当幂等信号,是标准的「先落库后处理」防重方案,答得具体、可验证。可补强处:**异常驱动的幂等在吞掉异常时容易掩盖真实错误**,生产上通常会配唯一索引 + `INSERT IGNORE`/`ON DUPLICATE KEY UPDATE`,以及区分「幂等命中」和「真冲突」的埋点——这是能往上再讲一层的地方。

### Q5. Oracle 与 MySQL 的差异
- **面试官问**：由简历的 Oracle→TDSQL 迁移切入——「两者之间会有哪些大的差异呢?从应用层面(说)。」
- **候选人答**：SQL 语法不同——Oracle 分页 `fetch first 10 rows only`,MySQL 是 `limit 10`;字符串转换、取当前时间的函数也不同。底层组织数据的形式也不同:MySQL 是 B+ 树,Oracle 是另外一套,没有聚簇索引这种结构。
- **评分与点评**：68/100 · 分页语法差异举例准确,「Oracle 默认堆表、没有 MySQL InnoDB 那种聚簇索引」的判断也对。但**答得太浅**:被问的是「大的差异」,没覆盖**事务隔离级别的默认值差异(Oracle 读一致性 vs MySQL RR)、锁机制(行锁升级/间隙锁)、NULL 与空串语义、自增主键、DDL 事务性、执行计划与优化器差异**——这些才是迁移里真正会踩的坑。

### Q6. OLTP→OLAP 迁移 / 不停机迁移方案
- **面试官问**：先确认背景——「这个只是把数据迁过来、原本的库也在用是吧?还是直接替换?」候选人澄清是历史归档后,面试官**主动构造了一个更难的场景**:「假如我们要迁移某个库的数据,但这个数据同时也在线上、也在用,可能有数据插入——你了解有什么方法能保证我不停机完成这部分迁移?」并在候选人反问「CDC 是吗」后**明确收窄**——「不一定是 CDC,比如从一个 MySQL 库迁到另一个 MySQL 库,或者迁到 TDSQL,同时有数据插入」。
- **候选人答**：存量迁移好办——定时任务扫旧数据,或走接口、或用数据库同步工具。增量同步「应该是有一些工具,它可以监听你数据库的一些日志来做这个」。
- **评分与点评**：75/100 · **正确区分了「存量迁移」和「增量同步」两个子问题**,也知道 CDC 这条路径,方向对。但被明确要求给方案时**停在了「应该是有(工具)」**,没有落到具体设计:**双写(新老库同时写)+ 全量搬历史 + 增量追平 + 校验 + 切读 + 切写 + 回滚**这个标准迁移流水线,以及影子表、影子库、灰度切流、数据比对与补偿。候选人简历上明明有「白名单引流 + 报文重放补偿」的灰度迁移设计经验,**却没在这里拿出来**。

### Q7. MySQL 为什么用 B+ 树
- **面试官问**：由候选人自己提到的「MySQL 二级索引用 B+ 树」切入——「选择这个存储结构的主要优点(是什么)?」候选人答完三点后**追问「还有别的吗」**,再给了第三次补充机会。
- **候选人答**：① 层级矮,不像二叉树那么深,适合磁盘读取特性,更适合顺序读而非随机读;② 最底层叶子节点连起来,像双向链表,可以顺序遍历。被追问后答「可能暂时想不起来」。
- **评分与点评**：78/100 · 三点都对(矮胖树 / 磁盘友好 / 叶子链表支持范围扫描)。**漏掉最关键的一条:B+ 树非叶子节点只存键、不存数据,所以单个节点能容纳更多键、扇出更大,树高才能压到 3 层左右**——这才是「层级矮」的**原因**,候选人只说了结果没说机制。另外可提:与 B 树的区别、与哈希索引的权衡。

### Q8. 范围查询(between / IN)是否走索引
- **面试官问**：明确进入「索引应用层面」——「范围查询会走索引吗?比如我用一个日期用 `between`,或者用 `id in` 一个 id 列表,这两种 case 会走索引吗?」(问的是**会不会**,即优化器的选择判断。)
- **候选人答**：日期 `between`「哦,我觉得是会的……我觉得走索引没问题」。`in` 列表「如果整个字段都是有索引的话,我觉得也可以,就是每一个都走」。「没想到有什么不走索引的(情况)」。
- **评分与点评**：55/100 · **结论大体不错,但全靠语感,没有一条判断依据。** 而且「没想到有什么不走索引的」是危险表述——真实情况是:范围查询会**导致联合索引中该字段之后的列失效**;`IN` 列表元素过多时优化器可能改判全表扫描;`between` 在选择性差(比如只覆盖大部分数据)时也会放弃索引。**这题本该用「最左前缀 + 优化器成本估算」来答,而这两个词本场一次都没出现。**

### Q9. 隐式类型转换(bigint 列 = 字符串)是否走索引
- **面试官问**：第二个索引应用题——「假设我 id 是一个 `bigint` 类型,然后我让它等于一个字符串类型,就是 `where id = '1'` 这种,它会走索引吗?」(考点是**隐式类型转换的方向决定索引是否失效**。)
- **候选人答**：「我猜测也会。我猜测它应该是会把这个字符串转成(数字),然后这样的话就可以用索引。猜测是可以的。」补了一句「但如果对这个 id 再做函数处理,那可能就不行了」。
- **评分与点评**：55/100 · **结论是对的**(常量侧字符串转数字,索引仍有效;反向 `varchar 列 = 数字` 才会因列被转换而失效),**补充的「函数处理导致失效」也对**。但整题以「我猜测」开头和收尾,**没有说出「转换发生在常量侧还是列侧」这条判断规则**——面试官考的就是这个规则,猜对不等于会。

### Q10. TopK:100 万无序数找第 100 大
- **面试官问**：经典算法题——「长度为 100 万的无序数字序列,我怎么快速找到里面第 100 大?」
- **候选人答**：不能一次加载进内存排序,所以**分治**:100 万分成 100 份、每份 1 万 → 每份排序取前 100 → 得到 100 组「前 100」合并成 1 万个 → 再排序取前 100。补充说「不一定需要全局有序,有些算法排到前 k 个有序就行」。
- **评分与点评**：70/100 · 分治思路本身成立,而且**最后那句「不需要全局有序」很关键,已经在往正确方向摸了**——但没接下去说出**小顶堆**(维护容量 k 的堆,O(n log k)、单次遍历、内存只占 k)。TopK 的标准答案就是堆,面试官听到「不需要全局有序」时基本在等这个答案。另外「不能一次加载进内存」这个前提**本身是错的**(100 万个 int 只有 4MB),这个错误在下一题被面试官当场抓住。

### Q11. 内存估算:100 万个 int 占多少内存
- **面试官问**：就着上一题的前提往下问——「你刚才提到因为数据量比较大,所以不能一次加载到内存里面。那我们先讨论一下,100 万个(整数),比如一个 int 类型,它需要占用多少内存?」随后**层层追数字**:「大概是多大的量级?」「等于多少呢?多少兆?」
- **候选人答**：不确定 int 是 4 字节还是 8 字节,假设 4 字节 → 100 万 × 4 = 400 万字节 → 除以 1024……最后答出「大概是 4(兆)」。
- **评分与点评**：70/100 · **最终结果 4MB 正确**,推导链条也是对的。但过程暴露两个问题:① **int 是 4 字节这件事不该不确定**(Java 规范固定值,32 位);② 单位换算时犹豫「按 1000 算还是 1024 算」——这类基础换算应当条件反射。面试官反复追「等于多少兆」,就是在看他能不能干脆地给出数量级。

### Q12. 面试官质疑「4 兆为什么要分批」
- **面试官问**：**当场推翻候选人的前提**——「那为什么——其实我的疑问就是,为什么 4 兆的大小都需要分批计算?4 兆对于我们普通(的机器),不管是在服务器还是家(用)电脑来说,应该是一个不太大的空间吧?就我们为什么需要每次取 1 万来(算)?」并明确表示想听**最初的思路**:「我其实想了解一下你最初的思路,为什么(会)想(到分批)?」
- **候选人答**：没有回应「4MB 很小、不必分批」这个质疑,而是继续维护原方案——「你可以开多个线程一起去算嘛,分批之后可以开多个线程去(算),这样要稍微快一点,再归并」。
- **评分与点评**：40/100 · **本场最该被接住却完全没接住的一题。** 面试官已经把矛盾摊开了:既然只有 4MB,你上一题说的「因为数据太大所以不能一次加载」就不成立。**正确回应是先承认前提错了**(「对,4MB 确实可以一次加载,我刚才说『太大』是想太多了,分批在这题的动机应该是并行加速/外存场景,不是内存不够」),再顺势把话题引向**内存不够的真实规模(比如 10 亿条)该怎么处理**——这才是面试官想听的。候选人的「开多线程更快」答的是**另一个问题**(怎么更快),而面试官问的是**为什么需要**(前提是否成立),属于典型的答非所问。

### Q13. 排序 100 万数据的耗时估算
- **面试官问**：给了一个具体的估算题——「假设我把 100 万个数据直接排序,排序之后直接取第 100 个数。我用直接排序的算法的话,你估计它耗时会有多久?」候选人给出复杂度后,**面试官一步一步往下压**:「预估 100 万在 n log n 级别下需要多少?」「你可以估算嘛,就根据你已知的(知识)」。
- **候选人答**：
  - 「100 万乘以 log 100 万,就是 100 万乘以个 1000 左右」→ 得出「**10 亿**」数量级;
  - 再「乘以 10」→「**100 亿**」;
  - 除以 CPU 频率 → **想不起「主频」这个词**(先后说成「聚合」「巨鹤之」「距」「大剧」),卡壳约一分钟;
  - 想不起 4GHz 等于 4×10⁹,只记得「10 的 9 次方」;
  - 最终:「我没有太大的概念,我不知道它是不是 **10 秒左右**可以(跑完)」。
- **评分与点评**：30/100 · **本场最严重失分。** 三处硬伤:
  - **log 10⁶ 算成 1000**(实际以 2 为底 ≈ 20,以 10 为底也只有 6)——**这是整题崩盘的根**;
  - 由此得出 10 亿(实际 100 万 × 20 = 2×10⁷),**差 50 倍**;
  - 最终答案 10 秒,而真实量级是**几十毫秒**(10⁷ 次比较 ÷ 4×10⁹ 次/秒 ≈ 5ms,计入内存访问与分支预测失败也就在百毫秒内),**差 2–3 个数量级**。
  - 更该避免的是**术语卡壳**:「主频」想不起来时应该果断换说法(「CPU 每秒能执行多少条指令?4G 就是 40 亿次」),而不是反复硬猜发音、耗尽面试官耐心。

### Q14. 配置化报文转换组件支持到什么层级
- **面试官问**：**本场唯一一次深挖项目**,而且是从简历原文挑的——「我看到你这个报文系统里面提到一个配置化的报文转换组件」。问题分两层:① 「支持到哪一种层级?比如我的报文可以是——其实我想了解支持的程度是什么样的:这报文可以来自多个报文的转换、合并到一起吗?我的字段在不同的层级(怎么办)?」② 候选人答完配置方式后,追问**表结构**:「这个数据库配置的建表(是)表结构(吗)?」
- **候选人答**：
  - **层级处理**:按业务语义把字段归集到一个 Java 对象,即使它们不在同一层级。比如某节点下是地址、再下面是街道,「要是街道下面还有层级,我们也会考虑把这个街道下面的层级跟街道放在一起」,不希望嵌套层级太深——**有业务语义的就尽量放到一个 Java 对象里**。
  - **表结构**:① 报文类型 → 多个 Java 属性(1:N);② 属性 → Java 对象(N:M,因为一个 Java 对象有多个属性);③ 每个属性 → 一个 XML 节点的全路径(1:1);④ 节点类型(嵌套型 / 叶子节点可直接取值 / 中间节点仅作路径)。
- **评分与点评**：75/100 · **表结构讲得相当清楚**——1:N 的报型→属性、N:M 的属性→对象、1:1 的属性→节点路径、加上节点类型标记,这四层构成一个完整的配置驱动映射模型,是本场第二好的回答。失分在:**面试官第一个子问题「报文能否来自多个报文、合并转换到一起」候选人完全没回应**,只说了一个报文内部的层级归集;另外**「配置化」的最大卖点——报文标准升级只改数据库配置、不用发版**这个商业价值没主动讲出来。

### Q15. 反问:业务模式与 AI 实践
- **候选人问**：① 「你们这块是在做什么业务?我了解到你们有做一些金融数据库相关的产品,还有一些投研。」② 面试官讲完后追一层:「输出的是类似于报告嘛?而不像一些 API 来提供?」③ 「那你们有怎么使用 AI 吗?产品应用层面。」
- **面试官答**：① 做投资研究服务/投资软件服务提供商,**B 端客户为主**(券商、银行、私募、保险),靠公开数据 + 采购渠道做投资分析、生成指标与报告,帮客户做投资决策;② 主体是 SaaS 系统(卖账号),也提供 API 接入、支持私有化部署;③ **AI 转型方向是把接口数据、算法底层能力都暴露成 API,按量付费,接入客户的 AI 工具**;④ 有自己的 **Agent 产品**(做了半年多,专注投资领域,接了很多 skill 和云端 API)、有自己的 **MCP** 和公开 skill;⑤ 这类产品「底层会有一个 **harness** 的 AI 架构,基于此可以插入各种 skill、任务模块、MCP,做特定场景应用」。
- **评分与点评**：—(反问不计分) · **问题问得好,收尾收得差。** 前三问层层递进(业务 → 交付形态 → AI 落地),拿到了**高价值信息**:对方的诉求正是「API 化 + 按量付费 + Agent 产品 + harness 架构 + MCP」——这几乎就是 JD 里「AI 智能体应用、Workflow 工程化」的口语版。但候选人在这个点上只回了一句「有用过,Agent 我用过 Codex,也(用)过(Claude)」,**白白放掉了本场最好的翻盘机会**:他手上就有一个自建的 AI Agent 工具(面试复盘流水线),完全可以就着对方的 harness/skill/MCP 架构聊自己的编排设计、对 AI 输出的审查与评测。**面试官已经把话递到嘴边了。**

## 二、面试缺点

1. **基础题靠「猜」和「感觉」作答,没有判断依据(表达 + 基本功)** —— 连续四题如此:Q8「我觉得是会的」「感觉也没什么问题」「没想到有什么不走索引的」,Q9 开头结尾都是「我猜测」。**结论对了但过程是空的**,面试官无法判断这是会还是蒙对。凡是「会不会走索引」「锁怎么保证」这类问题,必须给出一条可复述的规则(最左前缀 / 转换发生在常量侧 / CAS + synchronized),而不是语感。

2. **数量级估算全面崩盘(本场最致命)** —— Q13:log(100 万) 说成「1000 左右」(实际 ≈ 20)、100 万 × 20 说成「10 亿」(实际 2×10⁷)、最终耗时估成「10 秒」(实际几十毫秒),**与真实值差 2–3 个数量级**。Q11 中 int 是 4 字节这个固定值也「忘了」,单位换算在 1000/1024 之间犹豫。这类题考的是**工程直觉**,一旦数量级错了,面试官会直接怀疑所有其他回答的可靠性。

3. **术语想不起来时反复硬猜,卡壳耗时长(表达)** —— Q13 中「主频」先后说成「聚合」、「巨鹤之」、「距」、「大剧」,**同一个词卡了五次以上、持续约一分钟**,面试官全程在等。正确做法是立刻换自然语言绕开(「就是 CPU 一秒能算多少次」)。同类的还有 Q11 里 int 字节数的自我怀疑。

4. **被面试官当场纠正前提时没有意识到(最关键的一次机会流失)** —— Q12 面试官已经明说「4 兆应该是一个不太大的空间吧,为什么需要每次取 1 万来算」,候选人**没有识别出这是在指出「你上一题说的『数据太大不能一次加载』不成立」**,反而继续用「开多线程更快」维护原方案。**丢分点不是答错,而是没听懂面试官在说什么**——这会让面试官觉得沟通成本高。

5. **回避式回答:把「不会」说成「业务上没用到」** —— Q2/Q3 两次出现「我们这边业务上用得不太多」「用得比较少」。面试官已经把范围从 ConcurrentHashMap 放宽到「JDK 里有的、第三方的都行」,**仍然用业务场景来挡**,等于关掉了自己的展示窗口。更好的说法是先承认边界、再给出已知的部分(「并发原语我实际写得不多,我能说清的是我们怎么在数据库层用幂等和乐观锁保证并发安全」)。

6. **项目主线全程没被主动带出来** —— 面试官开场就打了招呼:「后面可能结合项目问一些经历相关的」,但候选人**全程被动等问**。最典型的是 Q4(幂等)答得很好,那正是可以顺势展开「唯一索引防重 + 状态机 + 兜底重试」整套设计的时机;Q6 被要求给迁移方案时,简历上现成的「白名单引流 + 报文重放补偿」也没拿出来。**答得好的地方没有借力打力。**

7. **最有区分度的资产整场没机会出场** —— 简历里的 **AI 实践(面试复盘 Agent 工具)**、**TCC 分布式事务**、**千万级数据迁移**这三块,面试官一个都没问到。面试官在反问环节主动讲了他们的 Agent 产品 / harness 架构 / MCP,这是把 AI 项目亮出来的最佳时机,候选人只回了「我用过 Codex 也用过 Claude」。

8. **自我介绍偏长且有重复(表达)** —— 开场自述里「我有买过股票、对金融术语比较熟悉」这个意思**说了两遍**,面试官在自我介绍尚未结束时就用「行。我这个一面先主要考察一些基础知识」打断进入正题。自我介绍应控制在 60 秒内并主动埋钩子(「AI 相关我做过一个自建 Agent 工具,如果感兴趣可以展开」)。

## 三、下一步学习计划

> 排序依据:本场暴露严重度(答错 > 靠猜 > 遗漏)优先,并参考 `知识点统计.csv` 累计频次与 `weight=0.4` 权重。

### 1. 复杂度分析与工程估算(本场最严重,直接崩盘)
- **暴露情况**:Q13 把 log(10⁶) 算成 1000、把 100 万 × log 的耗时估成 10 秒;Q11 对 int 字节数不确定;Q12 没意识到 4MB 根本不需要分批。
- **为什么重要**:面试官连问三题(Q11–Q13),这是 deliberate 的压力测试;估算能力是判断「有没有工程直觉」的硬指标,且几乎每场后端面试都会以某种形式出现。
- **具体动作**:
  - 背熟数量级锚点:log₂(10⁶) ≈ 20、log₂(10⁹) ≈ 30;4GHz = 4×10⁹ 次/秒;1MB = 2²⁰ B ≈ 10⁶ B。
  - 做 10 道「n log n 在 n = 10⁴/10⁶/10⁸ 下各要多久」的口算练习,把 10⁶ → 毫秒级、10⁹ → 秒级这个映射练成条件反射。
  - 复盘 `interview/跨面试弱点汇总.md` 里有没有同类估算题的历史暴露。

### 2. 并发基础:HashMap / ConcurrentHashMap / synchronized / AQS
- **暴露情况**:Q2 只说得出「锁头节点」,Q3 只报得出 synchronized 关键字,两题都以「业务上用得不多」收场。CSV 中「并发·锁实现」本场后累计 2 次。
- **为什么重要**:这是 Java 后端一面的**必考题**,任何一场都躲不掉;本场是 AI 岗都照问,说明它是筛人的基线。
- **具体动作**:
  - 讲清 **JDK7 Segment 分段锁 → JDK8 CAS + synchronized 锁首节点 + 扩容协助**的演进,以及为什么这么改。
  - 把 synchronized(偏向/轻量/重量锁升级)、volatile(可见性/禁止重排)、AQS(CLH 队列 + state)、ReentrantLock(可重入/公平/条件队列)串成一条线,**每个都能说出「解决什么问题」**。
  - 准备一个「我项目里没怎么写并发原语,但我在数据库层用幂等 + 乐观锁保证并发安全」的**加分版**答法,替换掉「业务上用得不多」。

### 3. MySQL 索引与执行计划(连续多场高频)
- **暴露情况**:Q8/Q9 两题全靠猜;「最左前缀」「优化器成本」两个关键词整场未出现。CSV 中「MySQL·执行计划与索引选择」本场后累计 2 次。
- **为什么重要**:JD 明确写了「熟悉 MySQL,能够编写复杂 SQL 并进行性能优化(索引、执行计划分析)」——这是通联岗位的**明文要求**。
- **具体动作**:
  - 把「索引失效」的场景穷举成一张表:`OR` 两侧不同列、联合索引不满足最左前缀、范围查询后置列失效、列上做函数/运算、**列侧隐式类型转换**(反向转换才失效,记牢方向)、`!=`/`NOT IN`/前导 `%` 模糊。
  - 学会用 `EXPLAIN` 读 `type`(const/ref/range/index/ALL)、`key`、`rows`、`Extra`(Using index / Using filesort / Using temporary)。
  - 记一条判断口径:**优化器走不走索引,最终看成本估算,不是看有没有索引**——这是 Q8 该给的答案。

### 4. TopK 的标准解法:小顶堆
- **暴露情况**:Q10 给了分治思路并摸到「不需要全局有序」,但没说出堆。CSV 中「算法·TopK(堆)」本场后累计 2 次。
- **具体动作**:手写一遍「容量 k 的小顶堆求第 k 大」(O(n log k),内存 O(k)),同时掌握**快速选择(QuickSelect)** 的 O(n) 平均复杂度解法,并说清两者的取舍(堆适合流式/内存受限,快选适合一次性数据)。

### 5. 不停机数据迁移的标准流水线
- **暴露情况**:Q6 被明确要求给方案,停在「应该是有一些工具可以监听数据库日志」。CSV 中「数据迁移·断点续传/灰度/双写」本场后累计 3 次——**已是高频知识点**。
- **为什么重要**:高频 + 候选人简历上**本来就有**「白名单引流 + 报文重放补偿」的设计,属于「有货但没拿出来」,纯亏。
- **具体动作**:
  - 把 **双写 → 全量搬历史 → 增量追平(CDC/binlog) → 数据比对校验 → 切读 → 切写 → 保留回滚窗口** 这条链路背成一段 90 秒的口述。
  - 明确区分**存量迁移**(游标分批、断点续传、三重校验)与**增量同步**(binlog/CDC、乱序处理、幂等重放)。
  - 把简历上那条灰度迁移经验改写成能直接答 Q6 的版本,记熟数字。

### 6. 术语卡壳的应对策略(表达,立即改)
- **暴露情况**:Q13 中「主频」卡壳五次、耗时约一分钟。
- **具体动作**:给自己定一条规则——**同一个词卡壳超过 2 次就立刻放弃该词、改用自然语言描述**("CPU 一秒能算多少次"),并在练习时故意练几次绕开专业词还能把意思说清的表达。卡壳本身不丢分,**反复硬猜发音才丢分**。

### 7. 被面试官纠正时:先承认前提,再往下推
- **暴露情况**:Q12 面试官明确指出「4 兆不需要分批」,候选人没有接住,继续维护原方案,答非所问。
- **具体动作**:准备一个通用反应句式——**「您说得对,4MB 确实可以一次加载,我前面说『数据太大』是想多了。那如果数据量到了 10 亿条这个规模,我的做法会是……」**。把「承认 → 修正 → 借机展示更深的理解」变成条件反射,而不是本能地辩解。

### 8. 主动亮 AI 项目 + 精简自我介绍 + 反问要问到底
- **暴露情况**:① 面试复盘 Agent 工具整场未出场;② 面试官在反问环节主动讲了 Agent 产品 / harness 架构 / MCP,候选人只回了「我用过 Codex 也用过 Claude」;③ 自我介绍重复且被打断。
- **为什么重要**:本场是 AI Agent 岗,面试官**已经把话题递到嘴边**;这是本场唯一能翻盘的机会。
- **具体动作**:
  - 把自我介绍压缩到 60 秒,并按「跨境支付 2.5 年 → AI Agent 实践 → 为什么换方向」三段式重写,**结尾主动埋钩子**。
  - 就着对方的 harness / skill / MCP 架构,准备 3 句能对接的话(自建编排、输入输出契约、对 AI 输出的审查与评测),参考 `面试复盘项目讲解底稿.md` 第 3.3/3.4 节。
  - 反问清单补一条:「你们 Agent 产品的**评测**是怎么做的?」——直击 JD 里「对 AI 生成内容进行严谨的审查、评测与优化」,也接得住对方已经开的话题。
