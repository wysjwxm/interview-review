### Q7. TCC 分布式记账:整体流程 + 个人工作
- **面试官问**：跨境支付这块做了分布式记账,介绍整体流程和你在里面做的工作(面试官提议可共享屏幕画图,候选人说有白板但最终仍语言描述)。
- **候选人答**：代理行层记账需调账务中台(两个应用),要都成功/都失败,故用分布式事务。下游提供 SDK 封装 Try(冻结)/Confirm/Cancel。流程:准备借贷要素 → 本地开事务 → TCC 表插记录(处理中)→ 发 Try 冻结 → 成功后改业务状态(待支付→支付成功)→ 事务结束前注册监听器把 TCC 表改为 C/R → 二阶段 Confirm(真扣钱)/Cancel(释放)。
- **评分与点评**：88/100 · 全场最深最熟的讲述,TCC 落地细节(本地事务、监听器驱动二阶段、TCC 表状态)一步不落、因果清晰;表达仍结巴但技术完整度是本场最高。

### Q8. 分布式事务选型调研 / 为什么 TCC

- **候选人答**：方案是入职前就定好的、下游提供 SDK(自己没参与选型);了解强一致 2PC,也了解不要求强一致的业务逆向补偿;系统当然要求强一致(资金服务);从头设计 TCC 是支付主流,也可用本地消息表/事务消息、或纯业务层补偿重试,最终对账收口;TCC 特点是一致性好、性能可接受,是「强一致伤性能、弱一致一致性差」之间的折中。
- **评分与点评**：74/100 · 知识点能点到(2PC/消息表/补偿/对账),但都是被面试官逐问挤出来的,且开场一句「不是我选的、来之前就有」直接交底,没给出个人思考,主动性弱。

### Q9. TCC 异常兜底:回查 / 本地回滚但 B 已 Try 成功 / Kafka 旁路
- **面试官问**：(多轮追问)Confirm/Cancel 失败怎么办?遇到过对方回查发现你们已改成功状态的情况吗?为什么要 Kafka 旁路?最刁钻一题:本地事务整体回滚、但 B 系统 Try 已成功,它回查查不到记录怎么办?
- **候选人答**：失败写错误影像表(状态已入 TCC 表),B 系统回查记录状态做补偿;另有 Kafka 旁路(发 Try/二阶段都异步发,不影响主流程成败,下游可监听判断),两层保障、最终以回查为准;Confirm 没执行就会出现对方查到「已成功」;若本地回滚而 B Try 已成功,B 回查不到记录 → 认为无二阶段 → 把 Try 撤销。
- **评分与点评**：88/100 · 补偿链路完整,且**最后一道难题答对了**(反查无记录即撤销 Try),是本场最能打的深挖题;暴露点在「线上是否遇过」答得含糊,见 Q10。

### Q11. 异步可靠性保障(线程池+兜底+重试)实现
- **面试官问**：简历写异步可靠性保障(线程池+兜底+重试、任务不丢失),具体怎么实现?
- **候选人答**：报文实时落库(待解析)→ 转异步线程池:解析 → 按字段清分 → 发送;除第一步外全异步。失败会停,故多线程池监控任务是否卡在某状态/update_time 超阈值(如 10 分钟)或失败 → 捞起重试 → 重试过多标异常转人工。
- **评分与点评**：82/100 · 机制讲得清楚、与 Q9 呼应成体系(实时入口 + 异步 + 兜底扫描 + 人工),真实工程味足;个别地方(线程池职责分工)讲得略乱。

### Q12. 任务表设计与兜底查询(含大批量)

### Q13. 慢查询索引设计(状态/时间/联合索引顺序)

### Q14. 线程池类型、参数、核心线程数估算

### Q16. 手写 LRU KV 存储(设计题)
- **面试官问**：用 Java 写一个最多存 100 个、按 LRU 过期的 KV 存储(先不考虑并发),用什么数据结构?
- **候选人答**：先想到 Map(KV),LRU 是最久未使用淘汰;(先绕了小根堆/优先队列)后给出 Map + 双向链表,dummy 头尾节点,节点带 key 和 value;满时从链表尾移除并回删 Map 的 key,新 key 插头部;维护 size;节点带 key 是为了淘汰时能回删 Map。
- **评分与点评**：72/100 · 思路方向完全对(HashMap + 双向链表 + 伪头尾,O(1) get/put),要点(节点带 key、淘汰回删)也都在;但组织混乱、先提小根堆绕路,全靠面试官一步步引导拼完整,设计题的表达力是短板。

## 二、面试缺点

1. **表达结巴、口头禅、句子破碎(最突出,几乎贯穿全场)**：「嗯/呃/就是/那个/对对对」高频,长句常说一半换方向;讲链路类题(Q6/Q7/Q11)信息量大但结构散,靠面试官不断追问才成形。直接影响印象分——Q7/Q9 内容本可稳 90+,被表达拖到 88。
2. **概念/设计题被面试官带着走(Q13 索引、Q8 选型、Q16 LRU)**：索引先答「只加时间」、被点出大数据量命中面太广才改联合索引;选型开场「不是我选的、来之前就有」交底;LRU 思路对但先绕小根堆、组织乱。共同模式是**不主动讲「为什么、有哪些方案、怎么取舍」**,要人推着才把话补全。
3. **线上经验储备薄(Q10)**：「可能没观测过」「TCC 倒是没什么遇到」——把兜底/重试/转人工机制讲得再熟,也拿不出一个线上真实 case;金融/银行面试特别看重这个。
4. **基础中间件与查询优化有空白(Q13 索引、Q15 Redis)**：Redis 只答出一句「内存 KV、可做缓存」的定义(数据结构/场景/淘汰均未展开),被追问就浅;索引理解停在「状态区分度小」单点,没串起「区分度 → 联合索引顺序 → 最左前缀/覆盖」体系,「大数据量下只加时间索引为何失效」也要靠面试官点破。
5. **求职动机表达偏弱(Q2/Q3/Q4)**：来上海「朋友多」、毕业没去互联网「笔试没收到邀请」、想去的方向「细分没想清」——都是真实原因,但姿态偏被动,缺职业导向的主动包装,国企一面常据此判断稳定性与自驱力。
6. **口头技术英语含糊(Q7 等)**:Confirm 说成「conphone」类、术语与中文夹杂卡壳,内容对但听感显生疏。
7. **该画图时没画**(面试官两次提议共享屏幕/白板,候选人最终都用语言硬讲)——TCC 流程用图讲会省一半力气且更清楚,工具(共享屏幕/白板)适应力要练。

## 三、下一步学习计划

> 排序依据:本场暴露严重度(答错/交白卷 > 被带着走 > 遗漏)为首要,参考 `知识点统计.csv` 累计频次与 `weight` 注释。

1. **MySQL 索引与慢查询:区分度 → 联合索引顺序 → 最左前缀/覆盖索引** — 本场 Q13 直接暴露、被面试官纠正。
   - 动作:搞清「为什么高区分度字段放联合索引前面」「最左前缀原则」「覆盖索引省回表」;重练这道题:任务表按(status, update_time)联合索引为何 status 在前;想清大数据量下「时间范围太宽」时如何用「状态优先过滤 + 时间排序」;能举一个自己真实 SQL 加索引前后对比的案例。

2. **Redis 基础(含「为什么这里不用」的话术)** — Q15 只答出"内存 KV 缓存"一句定义、未能展开。
   - 动作:掌握 Redis 是内存 KV、常用数据结构(String/Hash/List/Set/ZSet)与场景(缓存/分布式锁/计数/限流)、过期与淘汰、与本地缓存区别;准备一句「支付主链路有强一致与审计要求故不用缓存,但缓存场景(如热点配置/会话)我了解如何用」,把「没用」转成「理解为什么不用」。

3. **分布式事务选型话术(TCC vs 本地消息表 vs 2PC vs 业务补偿 + 对账)** — Q8 被挤牙膏,`知识点统计.csv` 已计 2 次。
   - 动作:整理一张「方案 → 一致性强度 → 性能 → 适用场景」对比表背熟;对自己的项目准备好「为什么选 TCC」的完整回答(资金强一致 + 性能折中 + 已有 SDK 约束),把「不是我选的」改为「在给定 SDK 约束下,我用 TCC 落地了什么、还知道哪些替代」。

4. **线程池参数推导(强项,保持 + 防丢)** — Q14 高分。
   - 动作:把「CPU 密集核+1 / IO 密集公式 / 连接池封顶」固化成 30 秒版本;再补一句拒绝策略取舍(CallerRunsPolicy 不丢任务 vs Abort/Discard),以备「队列满时怎么办」的连环追问。

5. **手写 LRU / 设计题表达结构化** — Q16 思路对但表达乱。
   - 动作:练「先给一句话方案 + 复杂度,再讲细节」的答法;LRU 标准话术 =「HashMap + 双向链表,get/put 均 O(1)」→ 新访问移到头部 → 满时淘汰尾部 → 节点带 key 便于回删;用 10 分钟在白板上(不开补全)写一遍并说一遍。

6. **线上经验 case 储备(把机制讲成故事)** — Q10 直接失分。
   - 动作:从自己的 TCC/异步/迁移经历里挑 1–2 个真实异常或隐患(哪怕一次重试转人工、一次对账不平),整理成「现象 → 定位 → 处理 → 事后改进」;下次被问「线上遇到过吗」能立刻抛案例,而不是「没遇到过」。

7. **即兴表达结构化(重点练,影响全场印象)** — 结巴/句子破碎贯穿。
   - 动作:对数字人民币链路、TCC 二阶段这两段已经讲得好的长篇,写成「第一…第二…第三…」腹稿各 2 分钟版本,录音自讲;平时答题先给结论再展开;允许白板/共享屏幕讲图,减少口头描述负担。

8. **求职动机话术(低优先级,但国企一面常问)** — Q2/Q3/Q4 偏被动。
   - 动作:把「为什么来上海/为什么跳槽/期望方向」统一成职业导向口径(如:金融科技在上海的生态、想从平稳业务转向增量/从 0 到 1、看重长期方向匹配而非短期薪资),避免「朋友多」「笔试没过」这类被动措辞。
