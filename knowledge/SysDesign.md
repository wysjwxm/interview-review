## DDD

领域事件、聚合根variableSet、规约模式、工厂类、CQRS、事件总线



#### 领域层 domain

> 整个系统的业务规则、业务约束、领域模型全部在这里，不依赖 Spring，不依赖数据库，不依赖任何外部技术框架，也不能操作之

1. **聚合根 AggregateRoot**：实体 Entity，领域行为方法写在聚合根内部。业务校验、业务计算、状态变更，写成对象方法，不是一堆 if‑else 散落在 service。
2. **实体 Entity、值对象 ValueObject**（UserId、OrderId）
3. **领域服务 DomainService**：不属于单个聚合根的**跨实体**业务逻辑，放到 DomainService
4. **仓储 Repository 接口**：只定义接口，**不写实现**。定义**对聚合根的存取能力**。接口放在 domain，实现放到 infrastructure。
5. **领域事件 DomainEvent、领域异常 DomainException**
6. 举例
   1. 聚合根：Account，能做deposit和withdraw
   2. 值对象：TransferAmount，保存币种金额，无id，创建后不可变（包括内部值）

### 大数据

##### 去重

1. 使用bitmap，Java使用long[]，一个long可存64位数据，每个数算出放哪一个long里，再更新long对应位置即可

```java
// 设num为目标值
long[] bitmap = new long[2];// 可以存0~127

int idx = (int)(num / 64);
int bit = (int)(num % 64); // 算出在一个long里的偏移量

// 标记70存在
bitmap[idx] |= (1L << bit);

// 查询70是否存在
boolean exists = (bitmap[idx] & (1L << bit)) != 0;
```



##### TOPK

1. 若可全部载入内存，直接维护size为k的堆
2. 若加速可分线程求局部topk，再求全局topk
3. 若内存不够可分机器或者分批次求局部topk
4. 快速选择（QuickSelect）
   1. 思想：借鉴快排的 partition，选一个 pivot，把数组切分成两部分。
      1. 大于 pivot 的放左边，小于放右边。
      2. 如果左边元素数量 >= K：TopK 全部在左边，继续在左边 partition。
      3. 如果左边数量 < K：左边全部属于 TopK，再去右边找剩下的。
   2. 时间平均 \(O(n)\)，最坏 \(O(n^2)\)，工程会加随机 pivot 避免最坏情况。



### TCC

1. 代理结算一致性方案：我付款方设置状态为支付中，冻结自己一部份钱，然后发rpc请求给另一个实例，等另一个实例响应成功了，付款方再将冻结真正改余额；如果收到 的响应是明确的业务异常，那就将付款方的状态改为失败，然后释放冻结金额；如果是非明确的业务异常，那就停留在支付中，让定时任务兜底发送，重试n次至成功（可退避重试）。收款方这边，收到转账请求，检查，如果发生业务异常就回复业务异常，如果发现交易发生过了，就做幂等回复；如果没问题，就将钱加到自己的余额上。这样也可以保证资金的正确性与一  
   致性

2. TCC优势

   1. 双端都有持久的"在途证据”

   2. Confirm 被做成"必然成功、零业务判断"的最小操作。

      >  TCC 把"检查余额够不够、账户在不在"这些会失败的判断全部塞进 Try，Confirm 只执行一个预先承诺、不可能失败的动作

   3. 结构上保证入帐和回滚不撞车

      > 撤销和"已入账"撞车只能靠 约定不撤销 + 对账兜底"来防，是人的约定不是结构保证

3. 本地调用和rpc调用的顺序

   1. Try 的顺序影响的是业务效率，Confirm/Cancel 的顺序影响的是"失败时谁已经真动了、怎么收尾
      1.  fail fast 省钱：先冻自己的钱，余额不足就直接失败，一个 RPC 都不发，省一次跨进程调用。
      2. 先锁自己控制的资源：协调者先把自己这边"我愿意出钱"承诺住，再邀请对端，逻辑上"发起方先表态"。
   2. Confirm可先本地：协调者/发起者先扣钱
   3. Cancel都可：保证先撤掉"搭在上面的"，再撤"底下的"，避免撤了底层资源导致上层还引用着一个已经不存在的预留
